# 文档编写规范

## 1. 文档类型选择

| 情况 | 文档类型 | 说明 |
|---|---|---|
| 游戏愿景、玩家体验、范围 | GDD | 描述“做什么、为什么” |
| 战斗规则、角色规则、舞台内容 | 玩法/内容设计 | 由策划和内容制作维护 |
| 多模块组成的完整系统 | SDD | 描述边界、职责、数据流与依赖 |
| 类、资源、节点、状态机、算法 | TDD | 描述具体实现 |
| 关键技术取舍 | ADR | 记录背景、选项、结论和后果 |
| 验证需求 | 测试计划/用例 | 可追踪到 GDD、SDD、TDD |

## 2. 命名规范

```text
系统：NN_系统名称_SDD.md
模块：NN_模块名称_TDD.md
内容：内容类型_名称_版本.md
决策：ADR-NNN_简短决策名称.md
```

不要同时维护内容相同的 Word 和 Markdown 文件。当前 Markdown 为权威版本，Word 仅用于外部评审或导出。

## 3. 文档头信息

每份正式文档应包含：

- 文档状态：模板 / 草稿 / 评审中 / 已确认 / 已废弃；
- 版本；
- 负责人；
- 创建和更新日期；
- 上游需求；
- 下游实现或测试链接。

## 4. 需求标识

建议使用以下编号：

```text
GDD-FEAT-001    产品/玩法需求
SDD-COMBAT-001  系统需求
TDD-HIT-001     模块实现要求
TEST-HIT-001    测试用例
ADR-001         架构决策
```

需求应能从 GDD 追踪到 SDD、TDD 和测试用例。

## 5. 内容边界

### GDD/玩法文档应写

- 玩家体验目标；
- 规则、反馈和内容范围；
- 可调参数的设计意图；
- 验收时玩家能观察到的行为。

### SDD 应写

- 系统上下文、模块边界和职责；
- 关键流程、数据所有权和接口；
- 非功能要求、异常恢复和依赖；
- 系统级验收标准。

### TDD 应写

- Godot 场景、节点、脚本、Resource、信号；
- Fray 类、状态、transition、tag、rule、condition；
- 算法、生命周期、错误处理和调试手段；
- 文件改动范围及具体测试。

### 不应重复

- 攻击数值不得在 TDD 中维护副本，权威来源必须是 `FrayAttackAttribute` 资源。
- 招式列表不得同时存在多个权威表。
- 状态拓扑不得只画在文档中而不对应 Fray builder 实现。

## 6. 评审检查

- 是否明确目标和非目标？
- 是否与 GDD/MVP 范围一致？
- 是否遵守 Fray-First？
- 数据是否有唯一所有者？
- 是否定义边界情况、失败恢复和性能预算？
- 是否有可执行验收标准？
- 是否链接测试计划？
- 是否记录尚未解决的问题？
