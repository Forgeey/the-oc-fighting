## 1. 文档目标

本目录用于管理游戏本身的产品设计、系统设计、技术实现、内容制作、测试和发布资料。Fray 框架本身的 API/教程仍放在 `demo/addons/fray/docs/`，不要把项目私有规则写入 addon 文档。

文档层级采用：

```text
GDD / 内容设计：说明玩家体验、玩法规则和内容目标（做什么、为什么）
SDD：说明一个完整系统的边界、职责、数据流和系统协作（系统如何组织）
TDD：说明具体模块、资源、类、状态机和算法如何实现（代码如何落地）
测试文档：说明如何验证需求和技术设计已正确实现
ADR：记录重要且难以逆转的技术决策
```

## 4. 当前核心范围

当前游戏的三个突出系统是：

- 战斗系统；
- 自定义角色造型与招式搭配系统；
- 地图场景、多层视差与破墙换场系统。

要形成可发布的完整游戏，还必须补齐输入与设备、角色运行时、比赛流程、本地多人、UI/HUD、训练与教程、AI、数据存档、摄像机、音频/VFX、资产管线、设置与发布等配套系统。完整清单和优先级见“系统清单与优先级”。
截至 2026-08-01，**目录规范与模板覆盖已经完成**；活动模板已转换为 Word 文档，需要随开发逐项填写、评审和验收。具体覆盖关系和完成口径见[文档模板覆盖矩阵](./00_文档管理/06_文档模板覆盖矩阵.md)。

## 5. 文档维护原则

- 一个事实只保留一个权威来源，其他文档使用相对链接引用。
- 玩法数值写在玩法/内容文档或 `FrayAttackAttribute` 资源中；TDD 不复制维护另一套数值表。
- SDD 不展开具体函数实现；TDD 不重新定义玩法目标。
- 实现变更必须同步更新相关 SDD/TDD、测试项和变更记录。
- 未确定内容统一标记为 `待定`，并给出负责人和决策期限。
- 线上回滚、创意工坊和大规模 UGC 当前属于未来独立立项，不得默认为 MVP 已承诺功能。

## 6. Fray-First 强制约束

- 输入优先使用 `FrayController`、Fray 输入映射、组合/序列输入及输入缓冲。
- 角色流程使用 `FrayStateMachine`、`FrayState`、builder、transition、tag、rule 和 condition。
- 输入驱动转移优先使用 `FrayBufferedInputAdvancer`。
- 攻击与受击反应数据只能来自 `FrayAttackAttribute`。
- 命中使用 `FrayHitState2D`、`FrayHitbox2D` 和 Fray hitbox attribute。
- 动画联动优先使用 `FrayAnimationObserver` 与 Fray animation tracker。
- 自定义代码只处理项目特有行为；任何绕过 Fray 的实现都必须写入 ADR 并说明原因。

## 编写与评审规则

- 顺序表示依赖关系，不代表必须等上一阶段全部结束后才能开始下一阶段；无依赖文档可以并行。
- 每份文档先写目标、边界、权威数据来源和验收标准，再补充细节。
- 未确定内容标记为 `待定`，不要用模糊结论伪装成已确定设计。
- GDD、战斗规则、角色/招式、舞台/模式和版本范围发生冲突时，应先回到产品文档统一结论。
- SDD 只描述系统边界、职责和数据流；TDD 才描述类、Resource、状态、算法和实现步骤。
- 任何攻击数值扩展优先扩展 Fray-compatible attribute/resource，不在角色脚本或文档中复制维护另一套参数。
