# 模块技术设计文档（TDD）

> TDD 分组方案最后整理：2026-08-03  
> 当前开发方式：个人学习优先，每组 TDD 使用一个独立 Godot 项目实现和测试，成熟后再逐模块整理到主项目。

本目录描述具体实现。TDD 必须有上游 SDD，不应自行发明玩法规则。

## 1. 分组原则

当前采用“多个相关 TDD 组成一个学习项目”的方式，而不是立即在主项目中同时实现全部系统。

分组遵循以下原则：

1. 同组 TDD 应围绕一个可以独立运行和验收的主题；
2. 每个 Godot 项目只承担一个主要学习目标，避免一次引入过多系统；
3. 先学习 Fray 输入、状态机、攻击与命中，再学习比赛、内容和工具层；
4. 后一组可以依赖前一组总结出的接口和经验，但不直接复制出第二套 Fray 核心；
5. 每组都必须有最小演示场景、测试步骤和已知限制；
6. `00_通用模块技术设计_TDD模板.docx` 是所有分组共用的写作模板，不作为单独项目。

## 3. 各组范围与验收目标

### 第 1 组：Fray 角色基础

建议项目名：`01_fray_fighter_foundation`

包含：

- `01_战斗角色状态机_TDD模板.docx`
- `04_输入映射缓冲与指令识别_TDD模板.docx`

学习重点：

- 使用 `FrayController` 和 Fray 输入映射读取语义输入；
- 使用组合输入、序列输入和输入缓冲；
- 使用 `FrayStateMachine`、`FrayState` 和 builder 构建角色状态拓扑；
- 使用 `FrayBufferedInputAdvancer` 驱动输入状态转移；
- 避免 enum/string 状态分发和自定义平行输入系统。

最小验收：

- 一个方块角色可以待机、行走、下蹲、跳跃和冲刺；
- 输入缓冲和至少一个序列指令可以被观察和验证；
- 状态切换全部由 Fray 状态机表达；
- 项目内提供输入和当前状态的调试显示。

### 第 2 组：Fray 战斗核心

建议项目名：`02_fray_combat_core`

包含：

- `02_攻击属性命中与受击_TDD模板.docx`
- `03_连段缩放资源与防御规则_TDD模板.docx`
- `05_动画事件与Hitbox同步_TDD模板.docx`

学习重点：

- 将 `FrayAttackAttribute` 作为攻击和受击反应数据的唯一来源；
- 使用 `FrayHitState2D`、`FrayHitbox2D` 和 Fray hitbox attribute；
- 实现命中、格挡、hitstun、blockstun、击退、浮空和 KO；
- 理解连段缩放、资源变化和防御规则；
- 使用 `FrayAnimationObserver` 与 animation tracker 协调表现事件；
- 保持逻辑帧与动画表现解耦，避免让动画成为第二套攻击时钟。

最小验收：

- 两个简化角色可以完成攻击、受击、格挡和 KO；
- 至少有一条可验证的连段及缩放规则；
- strike 的攻击资源直接挂在 `FrayHitbox2D.attribute`；
- melee 和 projectile 的命中均不会重复结算；
- 测试场景可以显示 hitbox、伤害和受击状态。

### 第 3 组：舞台、段落与摄像机

建议项目名：`03_fray_stage_camera`

包含：

- `08_舞台多层视差渲染_TDD模板.docx`
- `09_破墙与舞台段落切换_TDD模板.docx`
- `10_双角色战斗摄像机_TDD模板.docx`

学习重点：

- 多层视差背景的层级、速度和边界管理；
- 舞台逻辑边界与视觉背景的职责分离；
- 破墙触发、场景段落迁移和角色重新定位；
- 双角色取景、缩放、限制区域和镜头震动；
- 保证摄像机与舞台流程不侵入 fighter 的 Fray 状态拓扑。

最小验收：

- 两个测试角色移动时摄像机可以稳定取景；
- 至少有三层可观察的视差背景；
- 达成指定条件后可以触发一次破墙并切换段落；
- 切换后角色位置、朝向、摄像机边界和碰撞边界正确恢复。

### 第 4 组：本地比赛闭环

建议项目名：`04_fray_local_match`

包含：

- `11_比赛与回合协调器_TDD模板.docx`
- `12_本地玩家设备绑定_TDD模板.docx`
- `13_战斗HUD只读投影_TDD模板.docx`

学习重点：

- P1/P2 的键盘或手柄设备分配；
- round start、fight、KO、round end 和 rematch 流程；
- 比赛协调器与 fighter 状态机的边界；
- HUD 只读取战斗状态，不反向拥有或修改战斗数据；
- 处理设备断开、重连和暂停等本地会话问题。

最小验收：

- 两名本地玩家可以绑定不同输入设备；
- 可以完成至少一局包含倒计时、战斗、KO 和结算的比赛；
- HUD 正确显示生命、资源、时间和胜局；
- 重开回合不会残留上一回合的输入、状态或 hitbox。

### 第 5 组：角色外观分层合成

建议项目名：`05_fray_character_appearance`

包含：

- `06_角色外观分层合成_TDD模板.docx`

拆分原因：

- 造型系统解决的是视觉部件组合、绘制层级、遮挡和可读性问题；
- 造型测试主要关注显示结果、资源兼容性以及不同动作中的视觉稳定性；
- 外观不得改变 hitbox、hurtbox、pushbox 或攻击数值；
- 将其与招式装配分开，可以避免视觉资源直接依赖战斗规则和攻击数据。

学习重点：

- 角色外观部件的分类、插槽和分层合成；
- 部件锚点、遮挡顺序、朝向翻转和动画跟随；
- 缺失部件、不兼容部件和默认部件的降级处理；
- 角色轮廓、阵营辨识和战斗中的视觉可读性；
- 外观资源与 fighter 战斗判定彻底分离。

最小验收：

- 可以组合并预览至少一套分层角色外观；
- 可以独立替换头部、身体和至少一个附加部件；
- 待机、移动、攻击和受击时，各层能够正确跟随并保持顺序；
- 缺失或非法部件不会导致场景崩溃，并能回退到默认资源；
- 更换外观前后，角色 hitbox、hurtbox、pushbox 和攻击属性保持一致。

### 第 6 组：招式资源包与装配

建议项目名：`06_fray_move_loadout`

包含：

- `07_招式资源包与装配校验_TDD模板.docx`

拆分原因：

- 招式装配属于战斗内容和规则系统，不属于角色视觉合成；
- 装配测试关注槽位、预算、输入冲突、状态兼容性和攻击资源完整性；
- 分开后可以只使用方块角色验证装配规则，不必等待正式外观系统完成；
- 招式仍调用第 1、2 组形成的 Fray 输入、状态机和命中接口。

学习重点：

- 招式资源包、稳定 ID、槽位类型和装配预算；
- 招式输入、状态入口、取消规则和使用条件的兼容性；
- 装配前静态校验和运行前失败报告；
- melee strike 必须提供 `FrayAttackAttribute`；
- projectile 必须使用 Fray-compatible attribute；
- 装配表只引用招式资源，不复制 damage、hitstun、knockback 等攻击数值。

最小验收：

- 可以给测试角色装配一组合法招式并在战斗场景中使用；
- 可以拒绝槽位错误、预算超限、输入冲突和资源缺失等非法组合；
- 替换招式后不需要修改 fighter 的手写状态分发代码；
- 装配结果通过 Fray transition 进入对应状态；
- 所有攻击和受击反应数值仍来自招式 strike 上的 `FrayAttackAttribute`。

### 第 7 组：内容注册、预设与数据迁移

建议项目名：`07_fray_content_data`

包含：

- `16_预设序列化版本迁移与恢复_TDD模板.docx`
- `17_内容注册表校验与加载器_TDD模板.docx`

单独成组原因：

- 外观系统和招式装配都需要稳定 ID、内容发现和预设存档，但不应分别实现两套加载器；
- 数据格式、版本迁移和损坏恢复属于共享基础设施；
- 先让第 5、6 组用少量固定资源完成领域验证，再在本组统一设计持久化和内容加载接口。

学习重点：

- 外观部件和招式资源的统一内容注册方式；
- 稳定 ID、资源发现、重复项检测、依赖校验和加载顺序；
- 角色外观预设与招式装配预设的组合和边界；
- 格式版本、迁移链、未知字段、缺失内容和损坏恢复；
- 存档只保存资源引用和玩家选择，不复制 `FrayAttackAttribute` 的攻击数值。

最小验收：

- 内容注册表能够同时发现外观部件和招式资源；
- 能报告缺失资源、重复 ID、不兼容版本和非法依赖；
- 可以保存并读取包含外观选择和招式装配的角色预设；
- 旧版本预设可以迁移，损坏或缺失内容可以安全回退；
- 第 5、6 组不需要各自维护重复的注册、序列化或迁移实现。

### 第 8 组：训练模式与 CPU

建议项目名：`08_fray_training_ai`

包含：

- `14_训练控制与假人录制回放_TDD模板.docx`
- `15_CPU决策与Fray输入适配_TDD模板.docx`

学习重点：

- 训练假人的站立、下蹲、防御和受击后行为设置；
- 输入录制、循环回放和重置；
- CPU 决策层与角色执行层解耦；
- CPU 只通过 `FrayVirtualDevice` 发出语义输入；
- CPU 不直接调用攻击、不直接修改 fighter 状态，也不绕过 Fray transition。

最小验收：

- 假人可以切换至少三种训练行为；
- 可以录制并循环播放一段输入；
- CPU 能通过虚拟设备完成移动、防御和至少一种攻击；
- 人类玩家与 CPU 使用相同的角色输入和状态机入口。

### 第 9 组：质量、诊断与回归实验室

建议项目名：`09_fray_quality_lab`

包含：

- `18_战斗诊断性能与回归工具_TDD模板.docx`

学习重点：

- 输入缓冲、状态、hitbox、伤害缩放和 juggle 的可视化；
- 战斗事件日志、断言和资源静态校验；
- 最小回归场景和可重复操作步骤；
- 性能采样、对象数量、信号连接和长时间运行观察；
- 将前八组发现的高风险行为整理为回归用例。

最小验收：

- 提供至少一个集中式战斗诊断覆盖层；
- 能发现无 attribute 的攻击资源和非法攻击时间配置；
- 为输入缓冲、攻击接触、空中攻击落地和重复命中建立回归场景；
- 输出清晰的手动测试步骤、预期结果和失败记录格式。
## 4. 每个独立 Godot 项目的共同结构

每组项目建议保持相同目录习惯，便于未来迁移：

```text
project_root/
├─ addons/
│  └─ fray/                  # 使用同一版本的 Fray addon
├─ src/                      # 本组可复用实现
├─ scenes/
│  ├─ main.tscn              # 本组入口
│  └─ tests/                 # 最小测试场景
├─ resources/                # attribute、配置和测试资源
├─ docs/
│  ├─ TDD.md                 # 从对应 Word TDD 整理出的项目实现说明
│  └─ TEST_PLAN.md           # 操作、预期结果和已知限制
└─ project.godot
```

项目目录名称只是建议；真正创建项目时可以调整，但应保持编号和主题稳定。

## 5. 每组项目的完成条件

一组 TDD 只有同时满足以下条件才视为完成：

1. 对应 TDD 已填写，不再只是空白模板；
2. 有一个可以直接启动的最小演示场景；
3. 核心流程优先使用 Fray API，没有平行输入、状态机或攻击数据系统；
4. 有正常路径、边界情况和失败路径的测试记录；
5. README 或测试计划写明操作方法、预期结果和已知问题；
6. 可复用代码与仅用于学习演示的代码已经分开；
7. 记录当前使用的 Godot、Fray 和资源格式版本；
8. 在进入下一组前，总结本组可迁移接口和不应迁移的实验代码。

## 6. 未来整理到主项目的方式

未来不建议直接把多个项目的 `project.godot`、autoload 和输入配置整体覆盖合并，而应按模块迁移：

1. 先确定主项目中的 Fray addon 版本；
2. 从已完成的学习项目中提取可复用脚本、资源和场景；
3. 每次只迁移一个模块，并修正 `res://` 路径；
4. 输入动作、autoload、插件和项目设置逐项人工合并；
5. 攻击数据继续以 `FrayAttackAttribute` 为唯一来源；
6. fighter 流程继续由 Fray 状态机表达；
7. 每迁移一组立即运行该组测试和主 Demo 回归，不等全部迁移后再统一测试；
8. 学习项目作为参考样例保留，但主项目实现成为后续唯一维护版本。

建议在每个学习项目中维护一份“迁移清单”，至少记录：

- 可复用文件；
- 依赖的 Fray API；
- InputMap 项；
- autoload 和插件设置；
- Resource 类型与资源路径；
- 信号和节点路径约定；
- 已知耦合；
- 对应测试场景。

## 7. Fray-First 审查

任何 TDD 若提出新的输入系统、enum/string 状态分发、平行 hitbox 数据或独立攻击参数表，应退回修改。确需绕过时必须先创建 ADR。

即使各组位于不同 Godot 项目，也必须遵守：

- 输入优先使用 `FrayController`、Fray 输入映射、组合/序列输入和输入缓冲；
- 输入驱动状态切换优先使用 `FrayBufferedInputAdvancer`；
- 状态类继承 `FrayState`，拓扑集中在 state-machine builder；
- 攻击及受击反应数据只来自 `FrayAttackAttribute`；
- 命中使用 `FrayHitState2D`、`FrayHitbox2D` 和 Fray hitbox attribute；
- 动画联动优先使用 `FrayAnimationObserver` 与 Fray animation tracker；
- CPU 和训练回放通过 Fray 虚拟设备输入角色，不直接跳过状态机。
