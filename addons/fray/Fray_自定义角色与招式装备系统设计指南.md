# Fray 自定义角色与招式装备系统设计指南

## 1. 目标与已经确定的设计约束

本文面向当前仓库的 Fray 插件与自定义角色功能，描述建议的业务架构，不代表插件已经自带这些模块。

本方案明确采用以下约束：

1. **角色状态机负责行为流程，不为每个可装备招式强制创建一个独立状态。**
2. 攻击行为考虑四类：**基础攻击、特殊攻击、组合式攻击、投技**。
3. 特殊攻击包括 projectile（投射物）、蓄力，以及其他需要特殊执行流程的招式。
4. 新增业务模块 **`MoveManager`**，统一管理招式装备、查询、校验和动作请求的准备。
5. 单个招式、招式集合及角色动画映射使用配置资源表达；运行时进度与配置分离。
6. **招式动画通过动画标识引用**，不直接绑定某个角色的身体精灵图。
7. **仅角色配置界面允许换装；战斗中不允许装备、卸下或替换招式。**
8. 叶子状态调用 `Movement`，由 `Movement` 负责角色实际移动；不能在父状态或 Fighter 中重复提交移动。

> 推荐架构：少量稳定的行为状态 + 数据驱动的招式定义 + MoveManager 装备管理 + 角色动画标识映射。

本文所有 `MoveManager`、`MoveDefinition`、`AttackRuntime` 等名称都是建议新增的项目类型，不是 Fray 内置 API。示例字段与方法为设计约定，需后续实现。

## 2. 总体职责与数据流

```text
角色配置界面
    ↓ 编辑草稿，校验槽位与角色兼容性
MoveManager
    ↓ 确认装备，生成并锁定本场战斗配置
输入/指令识别
    ↓ 逻辑动作请求
MoveManager 查询候选招式
    ↓ 当前状态/战斗规则验证请求
角色状态机
    ├─ 基础攻击执行
    ├─ 特殊攻击执行
    ├─ 组合式攻击执行
    └─ 投技执行
         ↓
    Movement / 动画接口 / 战斗判定与效果模块
```

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `Fighter` | 持有角色组件、生命周期与依赖接线 | 在状态以外重复执行移动 |
| `InitStateMachine` | 创建行为状态、配置转换、注册条件 | 管理装备界面、为每次换装重写整张状态图 |
| `MoveManager` | 装备草稿、验证、战斗配置锁定、招式与指令查询、请求准备 | 推进每一帧攻击、直接播放身体动画、越过状态规则强制发动 |
| 行为状态 | 当前动作流程、阶段推进、取消权限、完成和退出清理 | 修改可复用招式定义 |
| `Movement` | 速度、重力、击退、位移限制、角色碰撞移动 | 选择装备招式、判断连招是否合法 |
| 动画接口 | 根据角色动画映射解析动画标识并播放 | 决定伤害和命中结算 |
| 战斗模块 | 伤害、命中、防御、投技目标验证、效果生成 | 把所有碰撞无条件转换成受击 |

MoveManager 可以检查能量、接地等公共限制，但当前动作能否被取消、是否处于可发动阶段，应由状态/战斗规则给出结论。它不能成为第二套独立行为状态机。

## 3. 角色状态机如何划分

### 3.1 第一版使用平面状态机即可

```text
FighterRoot（FrayCompoundState）
├─ Idle
├─ Walk
├─ Crouch
├─ Jump
├─ Dash
├─ BasicAttack
├─ SpecialAttack
├─ CompositeAttack
├─ Throw
├─ Hitstun
├─ Blockstun
├─ Knockdown
├─ Getup
├─ Captured             被投技控制，按需求加入
└─ KO
```

四类攻击状态负责四种行为协议，而不是四个固定招式。不同基础攻击共享 `BasicAttack`；不同特殊攻击可以共享 `SpecialAttack` 的阶段驱动，并按机制采用不同执行逻辑。

不要求第一阶段实现所有状态。先完成移动、一个基础攻击和受击，再逐步扩展。

### 3.2 分层方案：Action 直接包含 Dash 与四类攻击

采用分层时，`Action` 下直接放置 `Dash`、`BasicAttack`、`SpecialAttack`、`CompositeAttack`、`Throw`，不再增加中间的统一 `Attack` 分组。

四类攻击作为复合状态，各自下面的具体 Attack 叶子承担实际执行：

```text
FighterRoot
├─ Neutral
│  ├─ Idle / Walk / Crouch
│  └─ Jump
├─ Action                         主动行为复合状态
│  ├─ Dash                        冲刺执行状态，复杂后可自行分层
│  ├─ BasicAttack                 基础攻击复合状态
│  │  └─ Attack                   实际基础攻击执行叶子
│  ├─ SpecialAttack               特殊攻击复合状态
│  │  └─ Attack                   实际特殊攻击执行叶子
│  ├─ CompositeAttack             组合式攻击复合状态
│  │  └─ Attack                   实际组合式攻击执行叶子
│  └─ Throw                       投技复合状态
│     └─ Attack                   实际投技执行叶子
├─ Reaction
│  └─ Hitstun / Blockstun / Knockdown / Getup / Captured
└─ KO
```

这里四个 `Attack` 是不同父状态下的局部名称，完整路径分别为：

```text
Action/BasicAttack/Attack
Action/SpecialAttack/Attack
Action/CompositeAttack/Attack
Action/Throw/Attack
```

它们是不同的状态实例，可以分别使用基础攻击、特殊攻击、组合攻击、投技执行脚本；**名称相同不代表共用一个实例或同一种实现，也不要求四个脚本声明相同的全局类名。**

#### 各层职责

| 层级 | 职责 |
| --- | --- |
| `Action` | 主动行为之间的转换与组级中断规则；其中也包含 Dash，不等同于纯攻击组 |
| 四类攻击复合状态 | 本类攻击共有的进入/退出规则、组内转换、完成语义与公共清理 |
| 具体 `Attack` 叶子 | 持有本次动作运行时、读取招式资源、推进阶段、调用动画/判定和 Movement |

只有当前执行叶子提交角色移动，父层不再执行一次 Movement。类别复合状态也不会自动因为叶子结束就判定完成，需要按当前 Fray 的完成判定实现明确的组完成条件。

删除统一 Attack 父层后，四类攻击共有但不适用于 Dash 的规则，可通过共享辅助逻辑、同层标签和条件配置复用，不能把它们无条件套在整个 Action 上。

#### 具体 Attack 可以按需要继续细分

上图以每类一个数据驱动执行叶子起步。如果确有不同执行协议，可以在相应类别下增加不同叶子，例如地面/空中基础攻击执行器，或普通施放/蓄力施放执行器。

这些具体 Attack 不必与每个装备招式一一对应：

- 直拳、重拳可以由 `BasicAttack/Attack` 读取不同 `MoveDefinition` 执行。
- 火球与蓄力火球可由特殊攻击执行器选择不同阶段流程；若拆出蓄力执行器，它仍可在释放时生成 projectile，机制不是互斥的。
- 组合攻击的内部片段默认仍由片段图驱动，不必为每个片段创建 Fray 状态。
- 确有独立行为的招式可以拥有专用叶子，但仅伤害、帧数、动画不同的招式优先使用配置资源。

分层后，组装/派发层负责把执行类型及必要的执行变体映射到**具体叶子路径**，不能只定位到类别父状态就假定招式已启动。应测试具体叶子的进入回调、参数传递和父层清理次数。

层级变化不应改变招式资源的稳定 ID，也不应要求装备存档保存 `Action/BasicAttack/Attack` 这类内部状态路径。MoveManager 仍负责装备与查询，不直接承担类别内部的状态推进。

3.1 的平面方案仍可作为第一版；选择本分层方案时，四类名称表示复合状态，实际执行职责下移到其 Attack 叶子。

### 3.3 不按招式数量扩张状态数量

例如：

```text
直拳、重拳、踢腿       → BasicAttack
火球、蓄力火球、冲击波 → SpecialAttack
三段突进、分支派生技   → CompositeAttack
普通投、指令投         → Throw
```

上面的名称表示执行类别：在平面方案中对应执行状态，在 3.2 的分层方案中对应类别下面的具体 Attack 叶子。

地面/空中使用限制、速度和伤害差异优先由配置表达。若某种行为的完整生命周期与现有执行器差异太大，再新增执行器或状态，而不是不断向通用状态塞无关条件。

## 4. 四类攻击的执行模型

### 4.1 基础攻击 BasicAttack

适合普通拳脚、简单武器挥击等：

```text
startup（起手）→ active（有效）→ recovery（恢复）→ 结束
```

招式数据提供：阶段时长、判定时间窗、位移规则、伤害和取消规则。状态维护当前进度，调用动画、判定和 Movement。

不同攻击速度、不同身体动画，不足以成为新建状态脚本的理由。

### 4.2 特殊攻击 SpecialAttack

特殊攻击至少考虑两类机制，而且二者可以组合：

- **Projectile**：在指定阶段生成独立投射物实体。
- **Charge**：进入蓄力阶段，按时间/条件选择释放结果。

例如蓄力火球同时具有 Charge 与 Projectile，不应被互斥的“特殊招式子类型”枚举限制成只能二选一。

建议把“顶层执行类型”和“具体机制配置”分开：

```text
execution_kind = special
charge_profile = 可选蓄力配置
projectile_profile = 可选投射物配置
```

简单特殊攻击可以沿用阶段计时。蓄力流程较复杂时，再在 SpecialAttack 内使用明确的内部阶段或子状态：

```text
charge_start → charging → release → recovery
```

蓄力配置需要明确：最短蓄力、最大蓄力、等级阈值、松开行为、能量扣除时机、中断处理，以及空中/地面条件。这里的“主动按住蓄力动作”和“输入识别器记录长时间后方向输入”不是同一个概念，不能混为一个计时器。

Projectile 的责任边界：

- 角色状态负责何时生成、生成方向、生成位置和使用哪份配置。
- 投射物实体负责自己的运动、碰撞、寿命、命中去重和销毁。
- 角色进入恢复或受击后，已发出的投射物默认按其自身生命周期运行；是否随施法者中断而消失必须由配置明确决定。
- Projectile 不使用角色的同一个 Movement 实例；角色运动与投射物运动是两套独立运行数据。
- 回合结束/战斗退出必须统一清理存活投射物和它们的事件连接。

角色施法动画引用角色动画标识；投射物自己的动画也使用独立的表现标识，由投射物表现配置解析，不能把二者混成同一张角色动画表。

### 4.3 组合式攻击 CompositeAttack

本文将“组合式攻击”定义为：**一个装备单位内部具有多个动作片段、自动衔接或输入分支的招式。** 例如三段连击、突进后根据输入选择上挑或横斩。

它不等同于玩家把多个独立装备招式通过取消窗口连起来：

| 类型 | 表达方式 |
| --- | --- |
| 一个招式内部的多段/分支动作 | `CompositeAttack` + 片段图 |
| 多个独立招式之间的自由连段 | 当前招式的取消规则 + 下一次招式请求 |

组合配置建议包含：

- 片段 ID 与初始片段；
- 每个片段的阶段数据、动画标识、运动与判定；
- 下一片段的条件：自动、命中确认、指定指令、计时到达等；
- 分支优先级及互斥规则；
- 可退出/取消窗口；
- 整体结束条件。

每个片段可以引用可复用的动作片段资源。不要直接调用另一个状态对象的内部回调来“借用一招”。

片段默认是该组合招式的内部资产，不要求作为独立槽位再次装备。若设计允许连到其他装备招式，应使用明确的外部招式引用，并在配置确认时校验目标存在。

必须验证起始片段、分支目标和结束路径。默认禁止无界循环；确需循环的动作必须有次数、时间或资源消耗上限。

### 4.4 投技 Throw

投技与普通打击不同，因为它可能同时约束攻击者和目标：

```text
尝试抓取 → 目标验证 → 建立抓取关系 → 同步演出/结算 → 释放 → 恢复
```

投技配置至少需要：

- 抓取距离与允许目标姿态；
- 可投条件、投技无敌及可选的拆投窗口；
- 攻击者和受害者各自的动画标识；
- 同步锚点/偏移、朝向规则；
- 伤害结算时机、释放冲量和释放后状态；
- 抓取失败的恢复行为。

由战斗层维护抓取关系，防止同一目标同时被两个角色占有。目标可进入 `Captured` 之类的受控状态。

投技期间也要保持单一移动提交：每个角色仍由自己的活动状态调用自己的 Movement。攻击者不能一边通过投技脚本直接移动目标，目标另一边又执行普通行走。

若投技采用位置约束，应交给目标 Movement 的受控分支处理。受击、死亡、目标失效或回合结束时，都必须解除双方约束并清理引用。

## 5. 资源与运行时对象

### 5.1 推荐资源类型

| 类型 | 用途 |
| --- | --- |
| `MoveDefinition` | 一个可装备招式的身份、使用条件、执行配置与表现标识 |
| `MoveSetDefinition` | 一组默认/预设招式的槽位绑定 |
| `CharacterDefinition` | 角色基础属性、运动配置、默认招式集合、表现配置 |
| `CharacterAnimationMap` | 角色动画标识到实际动画资源/播放器入口的映射 |
| 动作片段/机制资源 | 阶段、组合片段、蓄力、投射物、投技等专项配置，复杂后再拆 |

第一版不必为每个字段创建一个资源类型。可以先把简单字段放在 `MoveDefinition`，待结构复杂后再拆出机制配置。

### 5.2 MoveDefinition 的建议字段

| 分组 | 示例字段 |
| --- | --- |
| 身份 | `move_id`、显示名、版本、标签 |
| 执行 | `execution_kind`：basic / special / composite / throw |
| 装备 | 允许槽位、角色兼容标签、可选装备成本 |
| 发动 | 地面/空中限制、能量消耗、冷却或其他前置条件 |
| 时间 | 起手、有效、恢复、判定时间窗 |
| 战斗 | 伤害、硬直、击退、命中判定、可受击规则 |
| 运动 | 位移配置、惯性保留、空中控制、重力规则 |
| 取消 | 可取消时间窗、需要命中/被防御、目标标签或招式 ID |
| 表现 | `animation_key` 或阶段/参与者角色对应的动画标识集合 |
| 特殊机制 | 蓄力、投射物、组合片段图、投技等配置引用 |

以下只是字段关系示意，不是 Godot `.tres` 文件语法，也不是可直接加载的配置：

```yaml
move_id: special_charge_fireball
execution_kind: special
allowed_postures: [grounded]
animation_keys:
  charge: charge_fireball
  release: release_fireball
charge_profile: charge_fireball_profile
projectile_profile: fireball_projectile_profile
```

### 5.3 MoveSetDefinition 只保存组合关系

```text
light_slot   → basic_punch
heavy_slot   → basic_heavy_kick
special_slot → special_charge_fireball
combo_slot   → composite_three_strikes
throw_slot   → throw_forward
```

槽位数量与限制属于游戏设计，不由 Fray 固定。装备绑定的是逻辑动作槽/指令，而不是具体键盘按键。

`move_id` 应稳定且唯一。存档可以保存角色 ID、招式 ID、槽位与配置版本，而不是保存运行状态对象或内部状态路径。加载后通过受控的资源目录解析 ID，验证不存在、重复或不兼容的条目。

### 5.4 运行时数据必须独立

`AttackRuntime` 等运行时对象保存：

- 当前招式配置引用；
- 当前经过帧数与阶段；
- 蓄力等级和进度；
- 组合式攻击的当前片段与分支记录；
- 本次攻击已命中的对象；
- 本次动作是否已生成投射物、是否已扣除资源；
- 抓取目标等本次动作关联数据。

同一份招式配置可以由多个角色引用，但上述运行数据不能共享。不要把 `elapsed_frames`、命中列表等写回 `MoveDefinition`。

Fray 的 `FrayState` 虽然也是 Resource，但它承载角色依赖和行为进度时，应按角色创建独立实例；不要把共享的招式配置直接当作共享状态实例使用。

## 6. MoveManager 的职责与接口约定

### 6.1 配置阶段职责

- 从角色定义和预设招式集合创建装备草稿。
- 按槽位装备、卸下、替换招式。
- 校验角色兼容性、槽位限制、动画支持和招式引用。
- 生成面向 UI 的错误说明。
- 确认并保存装备组合，准备战斗配置。

### 6.2 战斗阶段职责

- 提供只读的已装备招式查询。
- 根据逻辑指令返回候选招式。
- 给出稳定、可解释的候选选择顺序；冲突条件不能依赖字典偶然顺序。
- 与状态/战斗规则配合验证请求。
- 准备一次动作执行所需的配置引用和初始参数。
- **拒绝所有装备修改请求。**

阶段计时、蓄力进度、组合分支推进属于当前动作运行时，不放在装备表里。

### 6.3 建议接口

以下是业务接口草案，不是已有实现：

| 接口 | 作用 |
| --- | --- |
| `begin_configuration(character_definition)` | 在配置阶段建立草稿 |
| `equip(slot_id, move_id)` | 装备；非配置阶段返回失败 |
| `unequip(slot_id)` | 卸下；非配置阶段返回失败 |
| `validate_loadout()` | 返回结构化的校验结果与错误列表 |
| `confirm_and_lock()` | 校验成功后生成本场配置并锁定 |
| `get_equipped_move(slot_id)` | 只读查询 |
| `resolve_candidates(command_id, situation)` | 从锁定配置查询候选招式 |
| `prepare_request(move_id, situation)` | 准备请求，不直接绕过状态机发动 |
| `return_to_configuration()` | 仅由战斗流程在退出战斗后调用 |

查询返回的集合应是只读视图或副本，不能让 UI 通过取得内部 Dictionary/Array 引用绕过锁定。资源对象也不能仅靠“集合只读”保护：共享招式定义需按不可变资产使用，或在确认时生成独立配置快照。

## 7. 只允许配置界面换装：完整生命周期

```text
进入角色配置界面
    ↓
MoveManager 开启配置草稿
    ↓
玩家装备/卸下/替换
    ↓
校验通过并确认
    ↓
生成锁定的战斗配置
    ↓
创建角色运行实例和状态机
    ↓
开始战斗：所有装备写入接口拒绝修改
    ↓
结束并清理战斗实例、判定、投射物和抓取关系
    ↓
返回角色配置界面，重新开启配置草稿
```

必须同时保证：

1. UI 在战斗时不提供换装入口。
2. MoveManager 的修改方法检查当前阶段，不能只依赖按钮隐藏。
3. 战斗中的菜单、暂停、回合间等待不自动解锁装备；只有返回配置流程才允许修改。
4. 战斗配置与 UI 草稿隔离，界面残留引用不能影响正在运行的战斗。
5. 多角色各自持有装备配置和运行时数据，不因一方修改草稿污染另一方。

可以通过一个受控的战斗流程协调器调用锁定/解锁接口。不能让任意状态脚本自行把 MoveManager 切回配置模式。

本方案不实现战斗中热换装，也不需要为热换装设计“正在释放的招式如何替换”的分支。当前招式仍应持有本次请求选定的配置，防止其他非预期写入破坏执行一致性。

## 8. 动画只引用标识，角色负责解析

### 8.1 身体动画映射

招式保存语义标识：

```text
punch_light
charge_fireball
release_fireball
throw_forward_attacker
throw_forward_victim
```

角色 A 与角色 B 可以把同一标识映射到不同素材：

```text
punch_light
    ├─ 角色 A → A 的轻拳动画
    └─ 角色 B → B 的轻拳动画
```

招式不直接持有“A 的身体精灵图”。实际帧图、图集、动画播放器入口及适配信息由 `CharacterAnimationMap` 或对应表现资源持有。

### 8.2 一招可以引用多个动画标识

基础攻击可能只需要一个；其他动作可能需要：

- 蓄力开始、循环蓄力、释放；
- 组合式攻击的各片段；
- 投技攻击者与受害者各自的动画；
- 地面/空中的表现变体。

不要把“只引用动画标识”误解成“一招只允许一个字符串”。

### 8.3 动画不是唯一的战斗计时来源

建议由招式逻辑时间控制伤害判定、阶段完成和取消窗口，动画跟随该时间语义。换皮肤或更换精灵帧数量，不应意外改变伤害有效帧。

如果采用动画事件驱动某些逻辑，则必须约定事件标识与时间标准，并校验每个角色动画都提供相同的必要事件，不能随意替换动画后继续假定逻辑等价。

投技同步锚点、攻击判定挂点等也需要兼容性契约；仅存在同名动画不足以证明角色可以正确执行该招式。

### 8.4 缺少动画时的策略

默认建议在配置确认时拒绝装备，并向 UI 返回缺失的动画标识/锚点。

若产品设计允许回退动画，必须显式配置并验证相应逻辑与判定，不要静默播放任意 Idle 动画来掩盖缺失资源。

投技受害者动画属于目标角色的通用被投兼容能力，不能只检查攻击者。应在角色内容校验时检查通用受害表现，运行时对不兼容目标提供明确的失败策略。

## 9. 状态机与 MoveManager 如何接入 Fray

### 9.1 组装时不按装备数量生成状态

推荐由 `InitStateMachine` 创建支持的行为状态，并维护执行类型到实际执行叶子的映射。平面方案与 3.2 分层方案分别为：

```text
执行类型     平面方案             分层方案
basic       BasicAttack          Action/BasicAttack/Attack
special     SpecialAttack        Action/SpecialAttack/Attack
composite   CompositeAttack      Action/CompositeAttack/Attack
throw       Throw                Action/Throw/Attack
```

角色生成时通过 context 注入 Fighter、Movement、MoveManager、控制器和动画接口。Fray 的 `initialize(context, root)` 会让 context 字典只读，但不会把其中引用的 MoveManager 对象自动变成不可变对象；装备锁定仍需业务层实现。

装备条目影响“候选招式与合法取消目标”，不一定影响状态节点数量。只有特殊执行机制确实需要额外状态时，再由组装层添加对应状态。

### 9.2 请求执行与提交

一次发动建议按以下顺序处理：

1. 指令识别产生逻辑请求。
2. MoveManager 从锁定装备中查询候选。
3. 状态/战斗规则验证姿态、资源、取消窗口、目标等。
4. 统一选择一个被接受的请求。
5. 在约定的提交点消费输入与资源，建立本次运行时数据并转换到执行状态。
6. 状态通过 Movement、动画和战斗模块执行动作。

请求失败不能提前扣除能量、消耗缓冲或启动冷却。是否在开始、释放或命中时扣除资源由招式配置决定，但每次结算必须避免重复。

普通请求不要直接无条件调用 `goto()`；当前 Fray 的 `goto()` 绕过普通转换前置条件。若业务层选择使用它完成派发，必须先完成全部验证，并限制在统一提交入口。

### 9.3 同一执行状态之间的连续招式

这是数据驱动方案必须单独解决的问题：

```text
BasicAttack（直拳）→ BasicAttack（重拳）
```

上例使用平面方案名称；分层方案对应 `Action/BasicAttack/Attack` 这个同一叶子执行不同招式。不能假定再次 `goto("BasicAttack")`（平面）或 `goto("Action/BasicAttack/Attack")`（分层）会重新调用进入回调。当前源码的切换逻辑会寻找共同活动祖先，目标已经活动时不保证重入启动。

建议定义明确的动作执行接口，例如 `begin_execution(request)` / `replace_execution(request)`：

- 首次进入由状态入口启动执行。
- 合法的同状态取消由统一提交入口调用执行替换。
- 替换时先清理旧判定和阶段效果，再建立新运行时数据。
- 不能只在字典里覆盖当前招式引用而保留旧的计时和命中列表。

也可以采用经过测试的状态重入机制，但不要靠重复调用 `goto()` 猜测行为。

### 9.4 其他当前源码注意点

- `active` 默认关闭，初始化后需按角色生命周期开启。
- 分层情况下，父子状态都会收到物理回调；实际角色移动只由当前叶子提交一次。
- 根层离开攻击组的 `AT_END` 不会自动递归等待最深攻击叶子完成，应使用明确完成条件。
- 初始叶子的进入回调与复合状态默认入口需要专门测试；不要在初始化后假定所有叶子启动逻辑已经执行。
- 普通转换候选并未在 `get_next_state()` 中按 `priority` 排序。招式候选优先级应由业务层明确决策，不能盲目依赖此属性。
- 自动转换与缓冲输入推进可能在同一物理帧分别推进状态机。输入消费、命中中断和动作提交需统一时序。

## 12. 总结与源码参考

本方案的关键不是“动态创建多少个状态”，而是把三件事分开：

- **状态机：**角色当前处于什么行为流程。
- **MoveManager：**本场战斗装备了什么、某条指令对应什么候选招式。
- **招式资源：**一次动作的战斗规则、运动规则和动画标识。

角色在配置界面完成换装并锁定后，战斗只读取固定装备；基础攻击、特殊攻击、组合式攻击与投技通过各自执行流程使用这些数据。身体素材由角色动画映射解析，不与可装备招式强绑定。

当前仓库的源码核对入口：

- [FrayStateMachine](src/state_mgmt/state_machine.gd)：初始化、context、active 和推进模式。
- [FrayCompoundState](src/state_mgmt/state/compound_state.gd)：状态层级、进入退出、同状态切换、完成条件和转换检查顺序。
- [FrayState](src/state_mgmt/state/state.gd)：状态回调与资源类型。
- [FrayStateMachineTransition](src/state_mgmt/transition/state_machine_transition.gd)：转换前置条件与切换模式。
- [FrayBufferedInputAdvancer](src/state_mgmt/component/buffered_input_advancer.gd)：缓冲推进时序。

本文为设计文档；新增模块尚未实现，也未进行对应的 Godot 运行测试。
