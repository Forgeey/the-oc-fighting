# 游戏输入系统设计计划

> 2026-10-23 源码核对修订：以 `module_codes/my fray demo` 当前脚本、场景和资源为准。第 6 节说明脚本／节点关系，第 9 节说明谁调度、谁切换、谁执行运动。资源字段另见 [固定招式输入接入说明](固定招式输入接入说明.md)；其中测试命令和 fixtures 属于历史说明，当前项目没有 `tests/` 目录。构建器、指令和招式资源信任作者配置，不进行防御性资源校验；运行时匹配、前置条件和候选有效期仍保留。本文明确区分已有执行链路、尚未制作的游戏内容和后续目标。

## 1. 目标、实施状态与本次计划修订

输入系统需要支持基础按键、同时按键、方向指令、特殊技、连段和起手后的择派生，同时与具体角色、状态机、命中判定解耦。

**已有基础实现：**

- 在项目 Input Map 中补齐基础键位，保留 A/D，并校正旧左右方向键的序列化键值。
- 新建 `scripts/input/`，放置游戏自定义输入脚本。
- 新增 `FighterInputBindings`，统一将项目动作注册到 FrayInputMap。
- Fighter 初始化改为调用统一注册入口，不再只注册左右两个动作。

**当前已有的适配与装配实现：**

- 面向转换、清洗后的方向采样、候选保留/消费、单键/同时键与 Fray 方向序列接线。
- 固定指令的招式资源类型、selected_moves 装配、阶段依赖和条件验证。
- inputed_fwalk 移动转换与单一 MANUAL 推进调度。

**仍未实现：**

- 实际攻击/防御/跳跃/下蹲状态、完整特殊技内容、具体招式的命中取消与择窗口规则。
- 改键 UI、手柄映射、第二本地玩家、AI 与回滚输入回放。

配置好 J/K/L/; 并不代表角色已经能攻击或格挡；当前可运行叶子仍只有 idle/fwalk。

**2026-10-23 计划确定：** 每个招式的逻辑输入指令由作者固定，直接保存在招式资源中，玩家只能选择装备哪些招式，不能修改方向序列、逻辑按钮、组合方式或触发参数。不制作自定义招式指令编辑、覆盖配置或指令栏位分配设计。继续暂不新增 `FighterInputFrame`，复用 Fray 的按钮状态、事件和序列识别。当前基础执行链路已落地，具体完成范围见接入说明；未制作自定义指令编辑。

## 2. 基础键位与动作名称

物理键位只在 `project.godot` 的 `[input]` 中维护；业务脚本使用动作名称，不能直接判断 J/K 等物理键。

| 项目动作／Fray 输入名称 | 默认物理键 | 含义 |
| --- | --- | --- |
| `move_left` | A、← | 世界向左输入 |
| `move_right` | D、→ | 世界向右输入 |
| `move_up` | W、↑ | 世界向上方向采样 |
| `move_down` | S、↓ | 世界向下方向采样 |
| `jump` | W、↑、Space | 跳跃意图 |
| `crouch` | S、↓ | 下蹲意图 |
| `light_attack` | J | 轻攻击按钮 |
| `medium_attack` | K | 中攻击按钮 |
| `heavy_attack` | L | 重攻击按钮 |
| `guard` | ; | 防御按钮 |

既有基础接线已按 Godot `KEY_LEFT/KEY_RIGHT` 校正左右方向键，替换旧的序列化键值；本次文档修订未再修改键位。

这里使用 `physical_keycode`，分号不要求按 Shift；默认布局以常见 US 键盘物理键位为基准。将来支持布局/改键时，显示名称和物理位置需要分别处理。

### 2.1 为什么上、下方向与跳跃、下蹲分开？

- `move_up/move_down` 表示方向信息，供 8 向方向和特殊技识别使用。
- `jump/crouch` 表示角色行为意图，供状态条件使用。
- 默认允许共用物理键；将来玩家可以把 jump 单独绑到 Space，而 move_up 仍用 W/↑。
- 同一个 W 可能产生 move_up 与 jump 两个事件。序列识别不能无差别接收全部事件，否则 jump 别名可能打断方向指令；按用途过滤、按同一帧去重。

### 2.2 前后不是左右

`move_left/right` 是世界方向，不能直接叫 forward/back。前后由输入轴乘角色面向决定：角色面向改变，同一个 D 应从前变后。

当前已有 `Fighter.set_facing(-1/1)`，同步输入面向、移动面向和精灵翻转。`FighterInput.inputed_fwalk()` 用 `_horizontal_axis * facing_dir > 0.1` 判断前进；`Fighter.get_forward_axis()` 仅在前进时返回世界轴，朝左时可以返回负值，并非“只保留正轴”。默认初始化仍为 `set_facing(1)`，尚无根据对手位置自动转身的系统，也没有后退状态。

## 3. 固定招式指令与物理按键设置分开

| 配置 | 例子 | 保存位置／玩家权限 |
| --- | --- | --- |
| 物理按键绑定 | J 改为 U；手柄某按钮作为轻攻击 | 玩家输入设置；只改变 `physical key → light_attack`，改键 UI 仍属后续功能 |
| 固定招式指令 | fireball 必须输入 `236 + light_attack` | 作者定义的招式资源；玩家不能修改 |
| 招式执行规则 | 消耗、地空限制、起手、取消窗口、状态入口 | 招式资源／状态与战斗规则；不属于玩家改键 |

允许物理改键不等于允许改招式指令。例如把轻攻击从 J 改为 U 后，fireball 仍要求“下→下前→前+轻攻击”，而不是可以改成“623+重攻击”。

招式资源保存逻辑按钮名称（如 `light_attack`），不保存 J/K 字符；招式选择清单只保存所装备的招式，不保存另一份可覆盖招式指令的设置。

## 4. FighterInputFrame：本阶段取消独立脚本

### 4.1 Fray 已经提供的能力

以下依据本项目现有插件源码，不是待实现能力：

| 需求 | 复用位置 | 边界 |
| --- | --- | --- |
| 按住、刚按下、刚松开、输入强度、轴 | `FrayController`、`FrayInput` | 调用者仍需使用正确设备和明确采样时序 |
| 输入名称、设备、press/release、echo、时间与帧字段 | `FrayInputEvent`、内部 `FrayInputState` | 是事件/输入状态，不是完整且不可变的角色每帧快照 |
| 同时键与组合输入 | `FrayCombinationInput` | 容错、distinct 与普通按钮的冲突需要包装层验证 |
| 方向/按钮序列、间隔、蓄力与 negative edge 配置 | `FraySequenceTree`、`FraySequenceBranch`、`FraySequenceMatcher` | 事件过滤、相对面向、指令冲突和状态权限不由它自动解决 |
| 按键持续缓冲/窗口 | `FrayInputBuffer` | 当前类标注 experimental；不等于已消费、可仲裁的招式指令缓存 |

无需再复制一套按钮 held/pressed/released 位掩码，也无需每个物理帧都分配一个 `FighterInputFrame` 对象。

### 4.2 简化后的角色输入适配器

当前已实现 `FighterInput`，复用现有 `FrayController`。除候选和识别历史外，方向采样使用以下实际字段：

```text
_sampled_physics_frame    本次游戏采样帧，避免同帧重复处理
_direction               冲突清洗后的方向：中立或 8 向之一
facing_dir               角色当前面向，由 Fighter.set_facing 更新
_facing_at_sample         上次采样面向，用于检测换面向
_horizontal_axis          采样后的世界水平轴；_direction 同时保存上次方向
```

这些字段均已在 FighterInput 中实现。普通按钮状态通过 Controller 查询；事件通过 `FrayInput.input_detected` 获取并按 device 过滤。不另建 raw-input 缓存、全套按钮状态机或设备管理器。

注意当前 `FrayInputEvent.physics_frame` 来源于输入状态记录的帧，不能无条件把持续/echo 事件上的它当作“本次检测帧”。需要当前处理帧时明确记录 `Engine.get_physics_frames()`；历史事件的 press/release 字段也不能替代整帧全量状态。不要修改共享的 Fray 事件对象以完成面向变换；如 matcher 需要相对方向事件，只创建必要的派生事件并保留来源关联。

### 4.3 不能随 Frame 脚本一起删掉的责任

- 世界左右转成相对前后；左右同按水平中立、上下同按垂直中立。
- 方向原子化：同帧下+前形成一个斜方向，不能受信号回调顺序影响。
- W 对应 up/jump，S 对应 down/crouch 的事件分流，防止别名打断方向序列。
- 面向改变不能凭空制造一串新摇杆动作；跨面向指令的保留策略需明确测试。
- 在稳定的采样阶段使用数据，不在同一物理帧的不同位置任意读出不同结果。

以后确定需要回滚、逐帧回放或网络同步时，再增加精简的可序列化输入帧/记录类型。Fray 的墙钟时间和当前事件流不等于已经实现确定性输入历史。本阶段不为尚未确定的网络功能预建类。

## 5. 确定方案：招式资源保存固定指令

### 5.1 招式资源是固定指令的唯一配置来源

每个招式资源使用一个固定的 `command` 字段，不再命名为可覆盖的 `default_command`。作者可以在 Godot 编辑器中配置；玩家只能装备或卸下招式。

资源结构示例（具体已实现字段见脚本／接入说明）：

```text
fireball.tres : FighterMoveDefinition
  move_id = fireball
  command : FighterCommandDefinition（内嵌子资源）
    input_kind = SEQUENCE
    steps = [dir_2, dir_3, dir_6, light_attack]
    trigger = PRESS
    max_step_delay_ms = 200
  entry_path = action/special_attack/fireball/startup
  states = 该招需要的阶段定义
  transitions = 该招需要的内部转换定义
```

指令作为招式 `.tres` 的内嵌子资源固定存放，不要求再创建独立的指令预设库。输入类型由 `command.input_kind` 表达，不在招式顶层再保存一份可能不一致的 input_kind。装配、识别和存档不能修改共享资源中的 command。

以下是设计边界：

- 玩家不能把 fireball 的 236 改为 623，也不能把其逻辑轻攻击改为重攻击。
- 玩家不能编辑同时键组成、步骤次序、触发方式、蓄力下限、识别容错或 negative edge 参数。
- 不新增角色级 command override、任意指令编辑 UI、指令模板选择或 slot→command 配置。
- 角色自定义体现在“选择招式”，不是“给招式重新编排输入”。
- 如果作者更新某招式资源中的指令，属于游戏内容版本更新；加载旧角色存档时重新校验，而不是把旧指令当成玩家覆盖项。

### 5.2 固定指令仍需表达不同输入结构

| 类型 | 含义 | 作者配置示例 |
| --- | --- | --- |
| `SINGLE` | 单个逻辑按钮 | light_attack |
| `COMBINATION` | 容差窗口内的多个逻辑按钮 | light_attack + medium_attack |
| `SEQUENCE` | 有先后次序的方向／按钮步骤 | 236 + light_attack、light→light→heavy |

输入结构与触发策略分开。当前 `Trigger` 只有 `PRESS/RELEASE`，SINGLE 支持二者；COMBINATION 当前只检测按下；SEQUENCE 使用 Fray 步骤和 `negative_edge`，并非通用地套用 trigger 字段。持续 held 通过 Controller 查询，不逐帧生成攻击候选。`min_charge_ms` 当前只用于序列首步骤，序列末尾同时键尚未支持。所有参数由作者固定，不是玩家编辑选项。

### 5.3 指令冲突是作者配置约束，不是现有自动校验

当前没有“选装时报错”的保护：构建器不检查重复装备、完整指令冲突或缺失依赖，资源也没有 `validation_error` 等接口。

- 多个特殊指令同时命中同一按钮周期时，只确认 selected_moves 顺序中的首个匹配；不要依赖不同来源或条件使识别层回退到另一个同源特殊技。执行时仍检查活动来源和 prereqs。
- 重叠来源中的严格序列前缀（如 light 与 light→heavy）暂不支持通用等待／回退，应避免此配置。
- 特殊指令确认后不再回退同源单键；普通单键保留等待组合键的延迟和消费处理，但这不是任意前缀解析器。
- 玩家不能通过修改逻辑指令消除冲突。将来若有选装 UI 或离线内容检查工具，再讨论错误提示；本阶段不恢复防御性装配校验。

## 6. 当前脚本层级与装配关系

### 6.1 scripts/input 是职责分层，不是继承树

该目录当前只有三个 `.gd`，彼此不继承：

| 脚本／类型 | 基类／生命周期 | 当前职责 | 不负责 |
| --- | --- | --- | --- |
| `fighter_input_bindings.gd` / `FighterInputBindings` | RefCounted；静态注册工具 | register_actions 幂等注册十个基础 action bind | 不采样、不识别招式、不推进状态机 |
| `fighter_command_definition.gd` / `FighterCommandDefinition` | Resource；作者静态配置 | 输入类型、按钮／步骤、触发与时限；create_sequence 构造 Fray 序列树 | 不监听输入、不保存运行历史、不判断能否出招 |
| `fighter_input.gd` / `FighterInput` | Node；每角色一个实例 | Controller 适配、方向清洗、事件过滤、包装组合／序列、特殊指令确认／单键回退、候选保留／消费 | 不装配状态、不直接切状态、不执行运动或命中 |

三者分别是注册工具、配置、运行时适配器，不是三级父子节点，也不是三种玩家控制器。

### 6.2 配置层与运行层的关系

```text
project.godot [input]                        物理键 → 逻辑 action
    └─ FighterInputBindings.register_actions 注册到全局 FrayInputMap

Fighter.loadout : FighterLoadout
    ├─ state_library / selected_state_paths / transition_library
    ├─ entry_path / group_start_states
    └─ selected_moves[] : FighterMoveDefinition（scripts/moves）
         ├─ command : FighterCommandDefinition（固定指令）
         ├─ entry_path / allowed_from_paths / prereqs / switch_mode
         └─ states[] / transitions[]（完整招式所需阶段和内部规则）
```

FighterMoveDefinition 是完整招式定义，不是第四个原子输入脚本。command 固定内嵌于招式资源；共享 `.tres` 只提供配置，每角色候选、匹配历史和消费标记只放在 FighterInput 实例中。

### 6.3 当前场景节点层级

```text
全局 Autoload：FrayInputMap、FrayInput

Fighter : CharacterBody2D / fighter.gd
    ├─ FrayController               按 device 查询 Fray 输入状态／轴
    ├─ FighterInput                 游戏侧输入适配和招式候选
    ├─ FrayStateMachine             活动状态更新与转换执行
    │    └─ FrayBufferedInputAdvancer（paused = true）
    ├─ FrayHitStateManager2D
    └─ AnimatedSprite2D / 其他表现与碰撞节点
```

FrayController 和 FighterInput 是同级节点，前者不是后者的父类；Fighter 初始化时通过 configure 将 Controller 传给 FighterInput。状态对象由 Builder 创建并交给 Fray 管理，不是逐个挂在场景中的 Node。FighterMovement 是 Fighter 创建的运动辅助对象，也不是输入节点。

### 6.4 谁负责初始化与装配

总入口为 `Fighter._ready() → _init_fighter() → _initialize_state_machine()`：

1. 注册基础输入、设置物理优先级、初始化运动与朝向，保持插件 advancer 暂停。
2. `FighterSMBuilder.build(self, loadout)` 收集基础状态与已装备招式的阶段／转换，按状态路径和转换资源引用去重、设置分组入口、绑定条件方法。Builder 信任配置，不验证资源合法性或指令冲突。
3. Fighter 调用 `fighter_input.configure(controller, loadout.selected_moves)`，注册组合输入、为每个序列招式创建独立 matcher，并清旧历史。这一步由 Fighter 而非 Builder 调用。
4. `state_machine.initialize(context, root, loadout.entry_path)` 注入 Fighter、Controller、FighterInput、Movement 和 HitStateManager，再设为 MANUAL 并激活。

Loadout.selected_moves 和依赖装配已实现，但玩家选招 UI、存档、战斗中完整重建未实现。默认 `demo_loadout.tres` 仍只选择 `neutral/idle`、`neutral/fwalk`，selected_moves 使用空数组默认值。

### 6.5 最小结构与边界

- 不新增独立 FighterInputFrame、CommandLibrary 或 CommandMatcher，当前由 FighterInput 包装 Fray。
- 候选缓存已经内置于 `_candidates` 等字段，没有独立 FighterCommandBuffer，也未用 FrayInputBuffer 作为当前招式候选缓存。
- 一个完整招式可以有多个阶段；固定初始指令属于整招，不在每个叶子里复制。
- 基础移动继续使用 selected_state_paths 和普通条件转换，不强行包装成 command。
- 不设计自定义指令编辑器、覆盖配置或指令栏位模板。只有实际复杂度上升后才考虑再拆脚本。

## 7. 运行时如何复用 Fray

```text
Input Map → FrayInput / FrayController
    ↓ 游戏侧过滤 device、清洗方向、去除别名与 echo
FighterInput 包装 FrayCombinationInput / FraySequenceMatcher
    ↓ 特殊指令确认，未命中才回退单键；按有效期缓冲，单键可等待组合键
Fighter.advance_commands → _try_move 验证来源、prereqs 和完成条件
    ↓ 转换成功后消费；具体取消／择窗口仍需业务实现
Fray 状态切换 → 活动状态执行行为
```

### 7.1 当前识别、单键回退与候选缓冲

- SINGLE：按钮 press／release 先交给序列匹配器；该按钮周期未被特殊指令确认时，才匹配已装备的普通单键 command。
- COMBINATION：按排序后的按钮集合生成全局 `game_combo_...` 名称，复用 FrayCombinationInput ASYNC 组合，再检查各按钮 press 帧差是否在容错窗口内。
- SEQUENCE：每个已装备序列招式各用一个 FraySequenceMatcher 和一棵树，序列名使用 move_id；不是所有模式共用一棵树，也没有“共享模式识别一次再分发”的实现。
- 方向从同帧轴采样合成为 `dir_1..dir_9`。jump／crouch 只有被该 command 显式写入时才送入序列，避免方向别名打断指令。
- 候选只保存 move、来源按钮周期标识、生成／就绪／到期帧，不保存数值优先级或具体程度。当前序列来源标识取匹配完成时的末按钮周期，不保存整条方向／按钮历史的所有来源标识。
- sample 清除过期候选；get_candidates 只过滤未就绪条目，保持生成顺序。resolve_delay_frames 仅用于普通单键等待组合键，序列与组合命中后立即就绪。特殊指令确认后撤销同源单键；即使特殊技不可执行或候选到期，该按钮周期也不回退普通攻击。
- consume 仅在执行成功后调用：标记按钮周期已消费、移除共享来源候选并重置序列 matcher；准入失败的候选保留至到期。

完全重复模式和严格前缀仍受第 5.3 节作者约束。基础 bind 可全局共用，组合名称由按钮集合稳定生成；角色运行历史不写入共享资源。

### 7.2 方向和触发规则

- 按住、防御等持续事实继续查询 Controller；普通攻击默认使用 press 边沿，不因 held 每帧重复执行。
- 斜方向是每次方向采样后的一个结果，不把信号先后次序当作手势次序。
- `FraySequenceBranch.then()` 的 max_delay/min_time_held 使用毫秒，不能直接传帧数。
- 蓄力时间、窗口和复杂度由招式资源固定，装配时只读取，不允许玩家调整。
- 当前 SINGLE 可选 PRESS／RELEASE，COMBINATION 仅 press，SEQUENCE 由步骤与 negative_edge 控制；held 不是当前 command 的第三种 Trigger。默认关闭 negative edge。
- 输入模式容错、执行缓冲时间、状态取消窗口是不同参数，不能用一个 timeout 代替。

### 7.3 连段、长序列与择派生

1. 普通取消连段：按键候选 + 当前攻击的取消/命中条件。
2. 连续按键串：如 light→light→heavy，属于按键序列定义。
3. 起手后的择：父组 startup→choice_window，再按按钮进入派生。

第三类不要求把整套派生写成全局超长指令。招式内部窗口使用相同输入适配器产生的按钮候选，但可施加窗口起始帧条件；不能把窗口前已消费的旧按键再次当作择。

招式初始指令固定，不代表内部所有派生必须使用相同输入结构。内部阶段的按钮、响应窗口和分支目标同样由作者固定在招式资源及阶段规则中，玩家不能重新绑定派生指令；物理按钮改键仍统一生效。

## 9. 谁推进状态机、谁控制角色运动

### 9.1 当前单一调度者是 Fighter

**输入识别不直接推进状态机；当前普通转换的统一调度者是 `scripts/fighter/fighter.gd`。**

```text
Fighter._physics_process()
    └─ advance_commands()                仅由此物理回调调用一次，不另设重复调用帧锁
         ├─ fighter_input.get_candidates()
         │    └─ 逐个 _try_move(candidate)
         │         ├─ 验证活动来源 allowed_from_paths
         │         ├─ 验证 move.prereqs
         │         ├─ AT_END 时验证来源与活动叶子完成
         │         └─ root._transition_to(entry_path, args, source)
         │              └─ 成功 → fighter_input.consume() → 本帧返回
         └─ 无候选执行成功 → state_machine.advance()
              └─ FrayCompoundState.advance() 处理普通条件／阶段转换
```

输入层先确认特殊指令，未命中才回退单键；不同来源的候选保持生成顺序，能否发动仍由 Fighter 判断。当前 `_try_move()` 没有通用消耗、命中确认、取消／择窗口检查；作者可用 prereqs 委托 Fighter 条件方法，具体战斗规则仍待制作。进入参数为 move_id 和 input_frame（候选生成帧），阶段窗口需要另行验证窗口起始帧。

招式入口支持跨层路径，而 Fray 公开 add_transition 仅支持本组直接子状态，因此 `_try_move()` 集中桥接内部 `_transition_to(..., source)`。这是插件执行接口耦合点，不是识别信号无条件 goto；升级插件应重点核对。

推进链路的关键开关：

- `state_machine.advance_mode = MANUAL`，不再由插件 idle／physics 自动调用 advance。
- `advancer.paused = true`，场景和初始化都保持暂停，也没有把当前识别结果投给其 buffer 接口。
- 候选成功立即返回，没有成功才调用一次普通 advance；普通规则先尝试活动子层再尝试祖先，不靠 transition.priority 全局排序。

“一帧最多一条”指此链路中的普通／招式转换；进入复合组后沿默认入口进入叶子的 enter 链不算第二次输入推进。显式 Fray travel 等扩展也不应被误述为同样的一步保证。

### 9.2 MANUAL 不等于停掉状态物理更新

FrayStateMachine 在 active 时仍由 `_physics_process(delta)` 调用 `_root.physics_process(delta)`；MANUAL 仅影响自动转换。当前物理调度为：

| process_physics_priority | 执行者 | 本帧工作 |
| --- | --- | --- |
| -100 | 全局 FrayInput（由 Fighter 初始化设置） | 更新设备 bind／composite 状态，发出检测事件 |
| -50 | 每角色 FighterInput | sample 合并方向与按钮事件，识别候选并清过期历史；同物理帧只采样一次 |
| 0（当前默认） | FrayStateMachine | 更新本帧转换前的活动状态，执行其物理逻辑 |
| 50 | Fighter | advance_commands 验证候选或推进普通规则，成功才消费 |

新状态在切换成功时立即 enter，可播放动画；首次物理更新通常在下一物理帧，不会同帧让新旧状态各运动一次。不能再打开另一套自动推进，导致双重转换。

### 9.3 基础前进的真实调用链

移动不走 selected_moves／command 候选，而走普通布尔条件：

```text
玩家按方向键 → Godot action → FrayInput 采样
  → FrayController.get_axis(move_left, move_right)
  → FighterInput.sample() 保存 _horizontal_axis
  → Fighter.advance_commands() 的普通 state_machine.advance()
  → neutral/idle → neutral/fwalk 的条件 inputed_fwalk
  → Fighter.inputed_fwalk() → FighterInput.inputed_fwalk()
  → Fray 执行切换，FWalkState._enter_impl() 播放 fwalk
  → 下一物理帧 FWalkState._physics_process_impl(delta)
  → movement.step_grounded(fighter.get_forward_axis(), delta)
  → FighterMovement 计算加速度／重力／速度 → fighter.move_and_slide()
```

松开前进或改按后方向，`!inputed_fwalk` 使 fwalk 回 idle。IdleState 也每帧调用 `step_grounded(0.0, delta)` 处理摩擦与重力；松键减速不是输入模块直接修改位置。

默认朝右时 D／→ 前进；调用 set_facing(-1) 后 A／← 才是前进。尚无后退行为，左右同按轴归零。

### 9.4 缓存与接口边界

- FrayInput 管原始输入状态，FrayController 是按 device 查询的门面，不是角色状态机控制器。
- FighterInput 内置事件、候选、press 帧／周期及消费标记，不是全量 FighterInputFrame，也未接 FrayInputBuffer。
- FrayBufferedInputAdvancer 停用；其先 pop 再尝试 advance 的失败处理不符合这里的候选失败保留语义，不能直接打开替代现有链路。
- condition_methods 仍绑定 Fighter，inputed_fwalk 是 Fighter 到输入模块的薄委托；can_ 留给能力条件。
- Builder 只创建普通 FrayStateMachineTransition，没有用 FrayInputTransitionPress／Sequence 推进当前角色。
- 输入不创建 HitState、不改运动；活动状态调用 Movement，Fray 执行状态进入／退出。识别、准入／调度、切换、行为执行不能混为一个职责。

6. 再接手柄、第二玩家、AI 与回放；全局 action bind 和毫秒墙钟序列不等于双键盘隔离、确定性输入帧或网络回滚。
