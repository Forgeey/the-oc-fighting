# 组合技路线条目与多出口设计方案

> 2026-11-11 容器式装配更新：叶子和转换不再保存父组字符串；FighterCompoundStateDefinition.states／transitions 直接持有成员与内部边，TransitionLibrary.transitions 仅持有根边。组内归属由资源放在哪个容器决定，详见[状态机资源配置说明](../说明/状态机资源配置说明.md)。旧字段说明及示例已删除，不提供兼容别名。

> 2026-11-11 插件完成语义更新：根与 Demo 两份 Fray 已同步递归等待当前子状态完成；父自然出口直接配置 AT_END，Fighter.active_leaf_done 及其资源条件已删除。下文先前父条件绕过方案属于历史，当前配置见[复合状态完成与条件作用域处理](../说明/复合状态完成与条件作用域处理.md)。



## 1. 先把四种输出数清楚

令 A=`root.light_attack`。用户列出的 AB、ABC、ABCD 是三条延长输出；加上 A 单独收招，一共四个招式表条目：

| 展示条目／完整路线 | 输入示意 | 实际运行 |
| --- | --- | --- |
| A | L | 根执行 A，不接续则根返回 idle |
| A B | L、M | 根 A→combo1(start=B)，B 完成收招 |
| A B C | L、M、H | 同一 combo1，B 合法接 C，C 完成收招 |
| A B C D | L、M、H、K | 同一 combo1，B→C→D，D 完成收招 |

L/M/H/K 是四个示例逻辑输入，并非要求四个新物理按钮或已经存在的命令；实际可用重复攻击键／方向＋攻击组合。按键序列和按键时间必须符合作者设置。

这是“招式表可以分列四条路线”的项目设计。**展示为四条不证明游戏内部必须是四套状态机，也不证明 MK 的内部资源、move_id 或 Matcher 就这样实现。**不从菜单条目数推断某商业游戏的源代码组织。

## 2. 推荐运行结构：A 同根，B/C/D 都是 FrayState

```text
root : FrayCompoundState
  ├─ idle
  ├─ light_attack A : FrayState
  └─ combo1 : FrayCompoundState（start_state=B，is_persistent=false）
       ├─ B : 攻击 FrayState
       ├─ C : 攻击 FrayState
       └─ D : 攻击 FrayState
```

- B、C、D 都是普通攻击叶子，内部处理本次动作的起手／有效／恢复和框窗口。
- combo1 管本次路线、合法连接和有限预输入后缀；不是把 B、C 各自做成 CompoundState。只有某一击本身存在真实局部多步骤协议时，才考虑再嵌套。
- 四条路线共享 A/B/C/D 的动作定义；在同一角色的 combo1 中，只需要一份 B/C/D 运行实例。每次进入重新清计时／临时框位。
- 不同角色各自实例化；如果不同组复用同一个动作，也要各自状态实例，只读配置／脚本可以共享。

## 3. start_state 与 end_state 不等于路线条目

### 3.1 start_state 固定是下一击 B

根 A→combo1 转换已经由 M＋取消条件决定，进入默认 B。不重播 A，不根据 AB／ABC／ABCD 三个菜单条目反复改默认入口。

若该组只包含一个 B，start_state 可以指向 B；B 既是入口又可作为收招点。这不要求 end_state 也必须设成 B。

### 3.2 由插件递归完成，不把唯一 end_state 当作多出口列表

两份 Fray 已同步修改：无 end_state 时等待当前子状态完成；指定 end_state 时还要求该子状态是指定末状态。指定末状态不能仅因进入就提前报告完成。

combo1 的 B/C/D 均可收招，因此保持默认空 end_state；无需动态修改入口／终点、无需 done。BasicAttackState 完整恢复后报告 true，组随当前叶子递归完成。

## 4. 继续还是收招

### 4.1 转换结构

~~~text
root：
  A --后续命令＋合法取消--> combo1（start=B）
  A --AT_END--> idle
  combo1 --AT_END--> idle
combo1：
  B --后续输入＋本组合法连接条件--> C
  C --后续输入＋本组合法连接条件--> D
~~~

### 4.2 当前父出口配置

~~~gdscript
var leave := FrayStateMachineTransition.new()
leave.auto_advance = true
leave.switch_mode = FrayStateMachineTransition.SwitchMode.AT_END
root.add_transition("combo1", "idle", leave)
~~~

不再注册 active_leaf_done 或 combo1_can_exit 来重复查询叶子完成。插件只负责处理是否结束；仍需明确父出口与 advance，不自动出栈或寻找 idle。

若未来 route_session 认领了合法但延后提交的后续，父出口另加无有效 pending 等业务条件。当前项目没有此运行对象，不伪造 API、不新增队列。组内合法接续优先于父自然收招，IMMEDIATE 取消仍由自身条件授权。

### 4.3 各种情况的结果

| 实际进度 | 后续情况 | 结果 |
| --- | --- | --- |
| A | 没有 M | 完整恢复后 A，招式表命中 A |
| B | 没有合法 H | B 完整恢复后退出组，实际输出 AB |
| B | 有合法已认领 H | 在 B→C 的规定提交点进入 C，不先退出组 |
| B | H 太晚／连接未装备／条件失败 | 不认领为有效后续，B 正常收招；不能因为原始队列还有键而永远不退出 |
| C | 没有合法 K | C 恢复后退出组，实际输出 ABC |
| C | 有合法 K | 到规定提交点进入 D |
| D | 无其他作者定义分支 | D 恢复后退出组，实际输出 ABCD |

不要刚进入 B 就根据当前“没有 H”立刻退出；第一层屏障就是 B 尚未完成。若要“窗口关闭便强制提早收招”，那是另一套明确定义的恢复／退出设计，首期不默认截断剩余恢复。

### 4.4 防止内部接续与父级出口抢跑

每次调度按明确顺序：先处理本批输入认领与已认领请求的失效／条件裁决，再尝试组内合法接续，最后才考虑父级自然出口。当前本地 Fray 普通规则后代优先可以支持这个顺序，但游戏 pending 的更新必须在条件查询前完成。

可继续的 IMMEDIATE 边成功时，本次 advance 结束；未成功时才允许父级检查。即使如此，父边仍应核对 pending，不能只靠遍历顺序遮掩条件错误。已过期、已撤销或未来不可能提交的请求先从本次路线状态明确失效，不能让一个坏 pending 卡死整组。

## 5. 四个招式表条目，不是四次输入注册或四套状态

### 5.1 三个概念分开

| 概念 | 保存什么 | 数量关系 |
| --- | --- | --- |
| 动作定义 | A/B/C/D 各段动画、判定／帧数据、执行脚本 | 可供多个路线条目引用 |
| 路线／招式表条目 | 显示名、完整输入展示、段引用／合法连接、解锁／装备身份 | 可以分别列 A、AB、ABC、ABCD |
| 本次路线会话 | 当前实际段、已接受后续、执行／输入游标、来源归属 | 每角色当前执行实例，不写进共享资源 |

A、AB、ABC、ABCD 可以各有稳定条目 ID 和名字；这与“不在转换时传 move_id”不矛盾。条目 ID 用于 UI／解锁／装备／统计，运行时仍由当前源状态＋命令＋连接条件决定下一击。

不要等 Matcher 匹配完整 LMHK 后才启动 A，也不为每条完整路线注册一套 LM／LMH／LMHK 的特殊技序列。基础命令 L、M、H、K 或方向＋攻击组合按逻辑定义去重注册一次。路线按后续输入逐段延长，同一攻击不能因为前缀同时匹配而发动两次。

### 5.2 推荐的选装规则：路线族＋前缀闭包

“招式表分别列四行”不要求玩家一定独立装备四个主动攻击。推荐把 combo1 视作一个可装备路线族，展示其中四条可输出前缀；玩家可停止继续输入，AB／ABC 自然成立。

如果产品确实要求四条分别拥有可选条目 ID，也可以：

- 定义长路线对其前缀的依赖。装备 ABCD 时，A／AB／ABC 在合法路线上自然可用；不出现“没装备 AB 所以打到 B 不允许收招”的奇怪行为。
- 只装备 AB：只开放 A→B，不开放 B→C，即使 C 因其他招式已经装配也一样。
- 装备 ABC：开放 A→B、B→C，不开放 C→D。
- 装备 ABCD：上述连接全部开放；AB 与 ABC 仍可通过不继续输入自然收招。
- 构建时对共享段依赖去重，合并所选路线允许的**连接**，不能仅把全部执行组成员装配完就默认开放所有连接。

当前资源只有 Move.command／state（叶子或复合组定义引用）和端点筛选；**尚不能完整表达上述路线依赖和连接授权**。后续可增加显式路线／连接定义，或给现有装备定义增加路线引用；本次不确定新脚本名，不恢复旧的“每招维护一份普通转换清单”作为所有动作的硬性负担。普通转换继续按端点与条件装配，路线专属连接另有明确授权范围。

### 5.3 相同阶段真的不同，才拆动作

若 AB 在 B 收招与 ABC 中的 B 只是“有无合法取消”不同，共用 B 即可；完整恢复或在取消点转 C 就能表达。

如果两者的 B 真的有不同攻击判定、不同命中效果／动画、不同不可共用的执行时序，则使用不同动作定义或明确分支配置；不能因为名字都叫 B 就强行共享，也不能仅因为菜单有两个名字就复制一样的 B。

## 6. 条件按转换 owner 注册，不设计根继承

- 根 A→combo1、combo1→idle：条件注册在 root，Callable 可以读取 A／combo1／route_session 的事实。
- 组内 B→C、C→D：条件注册在 combo1，读取本组的窗口、后续认领、资源／命中事实。
- throw 的 grabbed／capture_failed：注册在 throw 组内。
- 根的出口条件读取子组，不等于“子组继承根条件”。这是数据查询对象与条件注册位置的区别。

本轮不接全局 `$` 条件继承、不扩展查找链、不修插件取反回退。旧问题保留在审查文档，仅供以后确需该功能时处理，不是这套路线的实施前置。

## 7. 原版 advancer 与组合技预输入仍是不同职责

原版 advancer 未修改，过早命令失败会出队。要完整支持 A 期间连输 M/H/K，必须在丢弃前完成路线接收和认领，保存本次路线有限 pending，再按各段提交帧执行；不可让自动失败出队以后又凭空恢复输入。

本方案不新增通用失败重试队列、不把组 start/end 当作缓冲能力，也不把原生 is_done 判断改造成整个游戏通用的多终点解析器。

## 8. start/end 的直接回答

- B/C/D：普通 FrayState；combo1：FrayCompoundState。
- start_state：是该组内的一个直接子状态。这里设 B，B 可以同时是一个允许自然结束的攻击。
- end_state：可不配置；若配置，必须是组内已有直接子状态，不是组自身、不是任意外部状态，也不是一个动态列表。
- 只含 B 的组可同时 start=B、end=B；当前已修正插件，仍会等待 B 自身完整恢复，不再刚进入便完成。
- B/C/D 多个可收招点：end_state 留空，由插件递归完成与父 AT_END 收招；不动态切 start/end，不强迫 D 才能停，不需要 done。

## 9. 后续验收和当前范围

至少测试 A、AB、ABC、ABCD 四种结果；B/C 未完成不得退出；无后续完整收招；已认领合法后续不丢失；晚按／未装备连接不误继续；组重入从 B、每段计时重置；快速预输入不能加速实际攻击；内部接续与父出口不双提交；共享动作不共享角色运行进度。

选装验收：只装 AB 时，即使 C/D 为其他内容已装配，也不可接出未授权的 ABCD；长路线前缀可自然结束；UI 统计依据实际执行前缀，不在 A 刚进入时就记成最长条目。


### 9.1 早期临时机制验证与正式回归

使用当前插件的干净临时工程，通过公开 initialize／add_transition／advance，验证 A、AB、ABC、ABCD 四种自然停止路径，无 done 状态、不查询根继承条件；22 项检查全部通过。额外检查空 end_state 不能绕过根出口 prereqs、有效 pending 阻止提前收招、子组合法接续优先、B/C/D 各自完整恢复后才离组。

这些是原生状态机制可行性测试，未把 route_session、路线装备授权、真实取消窗口或局部预输入系统写进正式项目。测试中 pending 是示例运行事实，不代表已有完整队列实现。

2026-11-11 已增加正式 tests/input/test_compound_exits.gd，通过实际 Loadout／Builder／Fighter／advancer 验证四种停止路径、局部条件、接续优先、转向与资源保存重载。当前父出口直接使用 AT_END，不需额外叶子完成前置条件；无有效 pending 的附加条件留待相关业务实现后加入。
