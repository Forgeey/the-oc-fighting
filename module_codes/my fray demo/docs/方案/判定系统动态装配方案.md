# 判定系统动态装配方案

> 记录日期：2026-10-24；输入、执行脚本与唯一时间源约定修订：2026-10-25。
>
> 状态：设计记录，尚未实施。本文不表示相关脚本、资源或节点已经存在，也不表示已完成运行验证。
>
> 本方案修订了“在 Fighter.tscn 中预建所有判定姿态”的早期设想。状态与招式按角色装备装配，判定依赖也应随之装配。

## 1. 核心结论

**状态／招式资源声明判定依赖；角色装配时实例化所需的完整 HitState；行为切换时只选择、启停已经装配的姿态。**

职责分工：

| 部分 | 职责 |
| --- | --- |
| 状态／招式资源 | 声明需要哪些完整判定姿态及相关静态配置 |
| 依赖解析与装配逻辑 | 根据当前 Loadout 创建行为状态与判定节点 |
| 行为状态／招式执行器 | 决定何时选择姿态、何时开启攻击段、何时退出清理 |
| 唯一的 `FrayHitStateManager2D` | 管理角色当前完整判定姿态的互斥 |
| 游戏战斗层 | 推挤解算、接触汇总、命中去重、伤害和受击结果 |

`Fighter.tscn` 只保留唯一的判定管理器，不预建所有基础状态和可装备招式的 HitState。

“动态装配”第一阶段指**生成角色时，根据本次装备构建所需内容**。从 idle 切换到 crouch 时不重新实例化场景；战斗中换装和热注册不在第一阶段范围内。

## 2. 基础约定

产品与执行约定：每个特殊技固定方向序列＋指定攻击按钮，不自动提供轻中重数值版本；默认每招自己的行为叶子与专用脚本。普通 startup／active／recovery 在该叶子内部推进，逻辑帧唯一驱动判定，AnimatedSprite2D 负责显示，不使用 AnimationPlayer 节点。固定输入不排斥技术上的脚本复用，公共工具仍可共享。详见 [疑难解答](招式装配与判定时序疑难解答.md)。

1. 每个角色只有一个 `FrayHitStateManager2D`，不是按受击、攻击、推挤分别设置管理器。
2. 一个 HitState 表示一套完整姿态，包含该姿态实际需要的框。
3. 每套姿态设计一个矩形 Pushbox；Hurtbox 和 Attackbox 可以由多个矩形组合。
4. 非攻击姿态不创建无用途的攻击框；攻击姿态包含自己的受击框、推挤框和按需启用的攻击框，不能依赖另一套常驻站姿框。
5. 行为状态和 HitState 不强制一一对应。多个状态可以共用同一判定定义，也可以为不同阶段分别配置姿态。
6. HitState 是管理器的直接子节点；各 `FrayHitbox2D` 是 HitState 的直接子节点，不增加中间分组节点。
7. `WorldCollision` 负责地面、墙壁等场景实体碰撞，不等于 Pushbox 或 Hurtbox。现有下蹲实体碰撞体调整不代替战斗判定。
8. 换向同步作用于图像与判定，不能只修改 Sprite 的 `flip_h`，也不能重复镜像。
9. 保留当前输入适配、候选消费和 MANUAL 状态推进机制，不为判定接入重新启用已有的暂停输入推进器。

## 3. 资源依赖关系

### 3.1 判定绑定到状态定义

当前 `FighterMoveDefinition` 已经通过 `states` 声明行为状态依赖。因此，第一阶段统一在 `FighterStateDefinition` 上增加：

```gdscript
@export var hit_state_definition: FighterHitStateDefinition
```

新增静态资源 `FighterHitStateDefinition`。最小字段草案如下，命名与接口在实现时最终确认：

```gdscript
class_name FighterHitStateDefinition
extends Resource

@export var hit_state_scene: PackedScene
@export var default_active_hitboxes: int = 0
```

字段含义：

- `hit_state_scene`：根节点为 `FrayHitState2D` 的完整判定 PackedScene，而不是已实例化 Node；节点按角色独立创建，不保存回资源。
- `default_active_hitboxes`：进入姿态时应用的启用位掩码，不代表所有姿态共用同一套位序。

这里使用普通整数表达接口；不同场景的框数量和名称不同，Inspector 的动态掩码提示另行实现，不硬编码通用的 `export_flags` 列表。默认字段值 `0` 不表示可以用零掩码选择另一套姿态，实际常态资源应填写需要的非零掩码。

资源关系：

```text
FighterLoadout
├─ selected_state_paths
│  └─ FighterStateDefinition（例如 idle）
│     └─ FighterHitStateDefinition
│        └─ idle_hit_state.tscn
└─ selected_moves
   └─ FighterMoveDefinition（例如 light_punch）
      └─ states
         └─ FighterStateDefinition
            └─ FighterHitStateDefinition
               └─ light_punch_hit_state.tscn
```

不新增独立的 `selected_hit_states` 装备清单，不在状态和招式两处维护重复的判定依赖。

`FighterMoveDefinition` 第一阶段可以保持原有字段，通过 `states` 间接拥有判定依赖。

### 3.2 用场景编辑几何，用资源声明依赖

矩形位置、尺寸、属性和节点结构保存到 `.tscn`；状态／招式的 `.tres` 通过判定定义引用它。避免把所有矩形都展开为坐标字段，再由代码生成整棵节点树。

示例路径均为拟新增内容，相对于 Demo 工程：

```text
resource/combat/hit_states/
├─ idle_hit_state.tres
├─ fwalk_hit_state.tres
├─ bwalk_hit_state.tres
└─ crouch_hit_state.tres

scenes/combat/hit_states/
├─ idle_hit_state.tscn
├─ fwalk_hit_state.tscn
├─ bwalk_hit_state.tscn
└─ crouch_hit_state.tscn
```

如果 idle 和 fwalk 的判定完全一致，可以引用同一个定义，不要求为每个状态复制一份场景。

## 4. 判定场景与角色节点

攻击判定场景示例：

```text
LightPunch                     FrayHitState2D
├─ HurtHead                    FrayHitbox2D
│  └─ CollisionShape2D         RectangleShape2D
├─ HurtTorso                   FrayHitbox2D
│  └─ CollisionShape2D         RectangleShape2D
├─ HurtLegs                    FrayHitbox2D
│  └─ CollisionShape2D         RectangleShape2D
├─ AttackNear                  FrayHitbox2D
│  └─ CollisionShape2D         RectangleShape2D
├─ AttackTip                   FrayHitbox2D
│  └─ CollisionShape2D         RectangleShape2D
└─ Pushbox                     FrayHitbox2D
   └─ CollisionShape2D         一个 RectangleShape2D
```

第一版优先采用“一矩形一逻辑框”，便于独立启停、部位属性和调试。永远共享属性与开关的多个矩形也可以挂在同一个逻辑框下，但不需要在初版同时实现两套内容组织方案。

角色基础场景：

```text
Fighter                        CharacterBody2D
├─ WorldCollision              原实体 CollisionShape2D
├─ AnimationPlayer
├─ FrayController
├─ FighterInput
├─ FrayStateMachine
│  └─ FrayBufferedInputAdvancer 保持暂停
└─ VisualRoot                  统一图像与判定镜像
   ├─ AnimatedSprite2D
   └─ FrayHitStateManager2D     编辑时为空，运行时加入所选姿态
```

运行后管理器下面只有本角色实际需要的姿态。未选择的状态、未装备的招式不产生对应节点；资源库被加载不等于其中所有判定都已实例化。

## 5. 统一解析一次依赖

当前 `FighterSMBuilder.build()` 内部会合并基础状态选择与招式状态依赖，再根据可用端点和已装备招式从公共库自动筛选转换；State 与 Move 不维护转换依赖 ID。判定装配必须使用同一份最终结果，不能另写一套扫描逻辑。

建议分离为：

```text
collect(loadout)
  ↓
FighterBuildPlan
├─ 最终选中的完整路径及状态定义
├─ 最终转换规则
└─ 构建行为树所需的入口、分组与招式信息
  ↓
  ├─ 装配 HitState
  └─ 构建行为状态树
```

`FighterBuildPlan` 是每个角色本次构建的运行对象，不是新的编辑资源或第二份装备清单。

保留现有配置作者负责资源合法性的边界，不借此恢复大而全的防御性资源校验系统。构建器的依赖合并、完整路径区分、转换端点筛选等原有语义应保持一致。

## 6. 装配时机与生命周期

### 6.1 当前 Fray 的约束

当前 `FrayHitStateManager2D` 在 `_ready()` 中连接已有直接子 HitState 的信号。因此，管理器 ready 之后直接 `add_child()` 不等于完成运行时注册。

不能在现有 `Fighter._ready()` 内任意添加 HitState，并假定 source、接触信号和姿态互斥已经自动接好。

### 6.2 第一版初始化顺序

```text
实例化 Fighter
  ↓
设置 loadout                         在 add_child 前完成
  ↓
Fighter._enter_tree()
├─ 解析一次最终依赖，保存 BuildPlan
└─ 实例化所需 HitState，挂入尚未 ready 的管理器
  ↓
子节点 _ready()
└─ 管理器连接已装配姿态的信号
  ↓
Fighter._ready()
├─ 初始化输入、移动与 source
├─ 用同一份 BuildPlan 构建行为状态树并注入判定绑定
└─ 进入初始状态，应用首帧判定
```

注意：

- `_enter_tree()` 中不能使用尚未赋值的 `@onready` 成员，应直接取得所需节点。
- 提前装配阶段不播放动作、不推进状态、不启用攻击框。
- 所有新实例在初始化完成前保持判定关闭；不能只隐藏节点代替停用检测。
- `activate()` 不能代替正确设置 `active_hitboxes`。
- 行为切换只选择已装配实例，不反复创建、删除节点。
- 第一阶段以一次性生成角色为边界；移出后重新加入场景树、战斗中换装等能力必须另行约定，不隐含支持。

### 6.3 热装配留待后续

若后续允许战斗中换装，需要显式实现注册／注销，包括 source、框与姿态信号、当前姿态、待处理接触及命中记录的生命周期。不能仅添加一个实例化入口便称为支持热装配。

## 7. 每角色运行对象与共享边界

拟新增 `FighterHitStateRuntime`，由 Fighter 持有，可先用 `RefCounted`，不必增加场景节点。

职责：

- 按最终选中状态收集判定定义。
- 在单个角色内按同一判定定义资源去重，实例化所需场景。
- 维护“判定定义资源 → 本角色 HitState 实例”的映射。
- 供状态通过绑定选择姿态、应用默认掩码和清理当前判定。

不以节点名作为资源身份。不同分组可能有同名行为或同名判定场景，运行时节点名称只用于场景树中的唯一命名。

每个角色独立拥有：

- 行为状态与 HitState 节点。
- 当前姿态和运行时掩码。
- 可变的形状资源。
- 招式实例、攻击段、命中目标记录。

共享 `.tres` 只保存配置，不保存 Fighter 引用、运行节点或“本次已经打中过谁”。运行时改变矩形尺寸时，Shape2D 必须按角色独立；实例化节点本身不应被当成自动解决所有子资源共享的保证。

## 8. 时序、动画与动作退出

### 8.1 第一阶段

先完成：

```text
状态进入 → 选择已装配 HitState → 应用默认掩码
状态退出／中断 → 清理旧姿态 → 进入目标姿态
```

多个行为共享姿态时，明确进入、退出的调用顺序，不依赖节点名称或旧状态残留。掩码由各自实际框顺序决定；增删、重排框后同步修改引用该布局的配置。

### 8.2 后续攻击时序：已确定使用逻辑帧

布局与启用时序分开。招式专用叶子的逻辑帧是阶段、攻击有效窗、取消和正常完成的唯一来源，不沿用 AnimationPlayer 的属性轨／方法轨，不需要动态动画轨绑定接口。

- 普通三阶段在一个叶子内部推进，不为每种掩码创建行为状态。
- 起手／恢复保留当前完整姿态所需的 Hurt／Push，仅 active 打开相应 Attack 位；不要简单把整个掩码清零代替关攻击。
- 每帧明确应用、模拟、检测／结算与转换顺序；动作帧从 0 开始，避免首次推进漏掉第 0 帧。
- 正常结束、取消、受击和销毁都清理攻击段及窗口；安全阶段选择目标姿态，不在碰撞回调直接修改监测属性。
- 动作代次和命中记录按本次执行独立，拒绝旧动作的延迟写入。
- 显示由 AnimatedSprite2D 处理；精确攻击显示可由同一动作进度选帧，不能反向用图片帧事件决定战斗逻辑。
- Hitstop 统一逻辑、图像、输入及结算策略，不让两套时间独立跑动。

本次统一了设计决策，尚未增加攻击计时脚本、判定绑定或精确图像同步实现。

## 10. 实施与验收顺序

1. 核对现有 neutral 行为与测试基线，避免把尚未验证的行为问题归入判定装配。
2. 分离一次依赖收集，保证行为与判定使用同一最终结果。
3. 动态装配四个 neutral 判定资源，验证初始姿态和任意切换。
4. 验证未选状态不产生对应节点，未装备招式不产生招式判定。
5. 验证多个状态引用同一判定定义时单角色只实例化一次；不同角色节点、可变形状独立。
6. 验证完整路径同名状态不会串用判定，换向同步且无重复镜像。
7. 验证管理器信号、source、互斥和退出清理均生效，不存在旧框残留。
8. 加入第二角色及推挤解算，验证靠墙、斜向接触和姿态尺寸切换。
9. 接一个可装备攻击和受击状态，验证有效窗、多矩形去重和强制中断。
