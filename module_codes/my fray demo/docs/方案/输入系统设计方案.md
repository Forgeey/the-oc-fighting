## 0. 改造原则与边界

1. **优先使用现成 Fray 能力，再做最少游戏接线，不默认扩展插件。** 不另写底层按键采样器或序列匹配算法。
2. 本轮使用原版 `FrayBufferedInputAdvancer`，接受其失败即取出、统一缓冲期限、暂停不停止时间流逝等限制。不能一边写“原生不改”，一边要求失败重试、每招独立队列期限和事务式消费。
3. 一次镜像、一套匹配历史、一个通用待执行输入队列、一个转换提交链。不能保留旧 `_candidates` 作失败重试队列来偷偷恢复已放弃的语义。
4. `FighterInput` 保留为角色上下文、Fray 对象接线、方向／来源解释和少量单位换算的薄层，不要求每节新建一个脚本。
5. 区分物理键位配置、Fray 名称注册、招式识别配置。物理配置保留在 InputMap；**本轮将基础和招式相关输入统一放到 `resolve_selection()` 成功之后注册到 FrayInputMap**，按依赖先基础 bind 后复合输入。
6. command 由作者固定；玩家可改物理键位和选招，不改逻辑序列与触发规则。
7. 不新增整套资源防御性校验器、选招冲突编辑器或全量 InputFrame；不能表达的配置明确列为内容限制。
8. 朝向采用项目明确规则；“像真人快打”是体验目标，不代表已经复刻其内部调度／解析器。
9. 本地双人、AI、回放分阶段实现。虚拟设备存在、单位能换算，都不等于已经支持完整回放／回滚。

### 当前基线与本轮目标

| 层 | 当前代码 | 本轮目标 |
| --- | --- | --- |
| 注册 | 基础动作先于 selection；组合注册在 configure 内 | selection 后统一注册，基础 → 相对方向 → 装备组合，最后建立 matcher |
| 镜像 | FighterInput 的水平轴乘 facing_dir | 优先 FrayConditionalInput，游戏只发布当前合法朝向 |
| 方向 | 按事件发生时朝向转换为相对 dir_n | 移动用相对输入；命令保留世界方向，按完成时朝向选择整条路径；左右抵消、上下步骤保留 |
| 序列 | 当前 FighterInput 为每个序列创建一个 FraySequenceMatcher | 目标为每角色、同一兼容事件域一个 matcher，容纳多个命名序列；直接复用 get_match_branch |
| 组合 | Fray ASYNC＋游戏帧差判断 | 本轮保留；插件容错参数化仅是后续可选项 |
| 缓冲 | `_candidates` 保存／到期／失败重试 | 原版 FrayBufferedInputAdvancer，失败出队、不重试 |
| 执行 | Fighter 手动调度，跨层 `_transition_to` 桥接 | 在原有插件 API 上做最小接线，不实施转换 API 扩展 |

以下章节从低层依赖写到上层。尚未实现的目标不能表述为当前功能。

## 1. 输入时钟、动作朝向与固定更新顺序

### 1.1 要实现、解决的问题

**先区分“什么时候允许转向”和“本次输入用哪个朝向解释”。** 前者由动作／状态决定，输入模块不自行跟踪对手然后随时翻面。

本项目首期采用：

- 待机、地面移动等允许转向的状态，在统一更新点面向对手；不要求这些持续状态先“动作完成”。
- 普通攻击从进入起手到恢复结束锁定出招朝向；完成后在下一次合法朝向更新点转向。被打断则交给新状态规则，不再等待旧攻击正常完成。
- 空中动作、受击、倒地、瞬移、换边技若需要不同规则，逐类明确；首期不默认给所有动作自动跟踪／自动纠正。
- **不需要半帧模拟或新增前置发布节点。**初始化时发布首份合法朝向；此后用现有 Fighter 帧末回调提交下一帧的朝向上下文。固定“Fray 采样 → 识别 → 动作更新 → 命令／普通转换 → 帧末提交下一帧上下文”的顺序，本帧采样与识别始终读同一份已发布值。
- 本帧采样后才完成的攻击，在下一次采样前更新朝向；本帧移动意图不在中途改解释。**未完成命令另按第 5.3 节保留世界方向，到终结事件时才按该帧合法朝向解释整条路径**，不能把这一过程与逐事件相对方向拼接混淆。这样可能有一个物理 tick 的边界延迟，是项目规则而不是线程竞态。
- 区分真实按下时间、序列完成时间、入缓冲时间、提交时间；记录不是为了做半帧模拟。

#### 《街头霸王》《真人快打》能确认到什么

- 《街头霸王 IV》官方手册明确指令按角色面向解释、面向左时左右反转；它没有公开本项目所问的统一内部转向更新顺序。不能据此替整个系列，尤其 SF6，断言“只能动作全部结束才转向”。见 [S1]。
- MK1 官方 2024-09-24 补丁对 Baraka 的空中 Death Spin 最后一击，限定只有先前命中才自动纠正方向；同次补丁还取消了部分 Kameo 招式前几帧偶发自动朝向。这说明自动朝向至少存在逐动作规则，不能概括成“MK 所有动作都只在完成后转向”。见 [S2]。
- 因此本项目采用上面的“普通攻击锁朝向、合法状态更新、特殊动作另定”作为易实现的 MK 风格起点；**这是项目设计，不声称等同 MK1 的全部内部实现**。官方补丁同样没有给出 SOCD／上下同帧输入的完整解析算法；本项目按第 5 节明确自己的容错。
- 进一步拟真时用指定版本训练模式实测：攻击最后一帧换边、跳过对手、瞬移、空中追踪、受击转向和换边后取消；记录动作、版本和输入显示，不泛化成全系列规律。

### 1.2 优先使用的 Fray 能力

- 读取 `FrayInputEvent` 的 device、physics_frame、time_pressed、time_detected、press／release／echo 等已有信息。
- Fray 是底层 held／just_pressed 的事实来源，不在游戏层再建一套键盘采样器。

### 1.3 时间换算与包装位置

**Fray 已有帧时间换算函数，无需为了单位换算扩展插件时钟：**

| 当前函数 | 用途 | 核对源码后的限制 |
| --- | --- | --- |
| `Fray.frame_to_msec(frames, fps)` | 帧数转毫秒 | 默认物理 tick 下可复用，向下取整；当前实现计算时仍直接用 Engine.physics_ticks_per_second，显式 fps 参数没有实际生效 |
| `Fray.msec_to_frame(msec, fps)` | 毫秒转帧数 | 默认物理 tick 下可复用，向上取整；同样没有实际使用传入的 fps |
| `Fray.frame_to_sec(frames, fps)` | 帧数转秒 | 当前返回 int 且 floor，60 tick 下 6 帧会得到 0 秒，不能直接给缓冲期限 |
| `Fray.msec_to_sec(msec)` | 毫秒转秒 | 2026-11-07 再核对本地源码：返回 float，可直接复用；此前写成 int 是文档错误 |
| `Fray.sec_to_frame(sec, fps)` | 秒转帧 | 当前 sec 为 int，不能假设小数秒输入保持精度 |

- **本轮不改上述插件函数。** FighterInput 集中提供必要的换算入口；使用默认 tick 的 frame_to_msec／msec_to_frame，不假装支持函数中未生效的自定义 fps。
- 例如给 advancer 设置期限：`float(Fray.frame_to_msec(buffer_frames)) / 1000.0`；若需要精确小数秒，则在 FighterInput 用 `float(buffer_frames) / Engine.physics_ticks_per_second`，避免先取整毫秒再损失精度。例：60 tick 下 6 帧为 100 ms／0.1 s。
- 显式自定义 fps 确有需求时，在 FighterInput 小范围适配，并测试 ceil／floor 边界；不散落硬编码 16.67。
- **单位换算不是时钟替换。** matcher／advancer 仍按 Time.get_ticks_msec 运行；暂停、变速和掉帧下不保证恰好 N 个模拟 tick。要严格帧同步以后另立任务。
- 角色输入上下文只保存必要的设备、已提交朝向和识别状态。不要修改共享 Fray 事件来改名或改时间；派生事件新建对象并关联来源。

### 1.4 验收

动作锁向期间换边不翻面；动作结束边界解释稳定；6 帧配置不变成 0 秒；显式检查 1／2 帧取整和暂停后缓冲变旧的实际行为。

## 2. 物理按键与统一 Fray 输入注册

### 2.1 要实现、解决的问题

- 物理键位仍在 project.godot／InputMap 配置；`move_left/right/up/down` 是稳定原始名称。
- jump／crouch 行为与 up／down 方向分开，即使默认同键也不合并语义。
- 基础 bind 与招式复合输入集中处理，但名称唯一、依赖有序、重复开局不重复注册。

### 2.2 优先使用的 Fray 能力

- InputMap 负责键位，FrayInputMap.add_bind_action 等负责注册，FrayController 负责设备查询。
- 保留 FighterInputBindings 作注册工具，不扩成采样器。

### 2.3 修改插件或额外包装的位置

- **薄封装：**一个统一注册入口接收 selection／角色输入上下文，内部先注册固定基础 bind，再注册相对方向、最后注册 selection.moves 的复合定义。
- 基础输入不依赖招式数据，但完全可以安排在 selection 后的同一次初始化里；即使 selection.moves 为空也注册完整基础输入。
- 不依赖“多个 add 调用跨帧慢慢注册”：首个有效采样前完成整个依赖图。多角色共享定义幂等复用，不能因某人退场移除别人仍在用的输入。
- **不改插件。**不同定义同名需明确报出；不为每个招式重复绑一次物理键。

### 2.4 验收

空装备仍能移动；两个角色依次初始化不覆盖；物理改键不修改 command；注册完成之前不产生半配置的候选。

## 3. 设备、玩家与角色输入上下文

### 3.1 要实现、解决的问题

- 建立玩家槽／device 与角色的关联，供条件输入查朝向；解绑、失焦、重连有清理流程。
- 全局 FrayInputMap 不保存某个 Fighter 的独占朝向闭包。
- device 0 默认键鼠／首手柄的约定，不等于同键盘双人已自动隔离。

### 3.2 优先使用的 Fray 能力

- 使用 FrayController.device／disabled、Fray 连接事件。
- AI／回放未来优先使用 FrayVirtualDevice，本轮不先绕过插件另建设备协议。

### 3.3 插件检查／必要修改的具体例子

**这些是后续接入虚拟设备前的检查项，不是本轮强制改插件。**

1. 创建虚拟设备 `v` 并执行 `v.press("light_attack")` 后，它的状态可能能被直接查询，但当前 `get_connected_devices()` 枚举的是物理手柄列表／回退设备 0。虚拟负 ID 不在枚举里，自动更新／事件发射可能根本没处理它，FighterInput 就收不到 input_detected。不能用“类存在且 press 成功”代替整条链验收。
2. 如果未来简单把虚拟 ID 塞回物理更新列表，`_update_bind_input_states` 又可能读真实键位并覆盖虚拟 press。这需要区分物理采样和虚拟状态，而不是只补一次枚举。
3. 若接入真实手柄后设备 0 不在当次枚举里，键盘玩家是否继续采样也要测试；当前 `get_connected_devices()` 只在没有手柄时回退添加 0。
4. `create_virtual_device()` 用状态字典 hash 派生 ID；重复创建／销毁时需检查负 ID 和唯一性，不把 hash 当作绝对不冲突保证。

- **薄封装：**设备到角色输入上下文的注册表；首期同一个 Fray device 只服务一个独立朝向的角色输入上下文。
- 本轮先支持经测试的物理设备；上述问题确认影响所需功能后，再单独提最小修复，不批量重写设备系统。

### 3.4 验收

独立物理设备不串输入；设备切换清历史；未来虚拟设备必须同时验证查询、复合输入、press／release 事件和断开，不只验证一个 press 调用。

## 4. 角色相对方向与镜像

### 4.1 要实现、解决的问题

- 基础移动／当前方向条件把世界左右转相对前后，上下不跟随水平镜像。**序列识别保留世界方向历史，按完成时朝向选择相应世界路径**，不逐步固化为事件发生当时的前后。
- 使用第 1 节已经合法提交的角色朝向，不直接根据对手每次位置查询立刻翻面。

### 4.2 优先使用的 Fray 能力

- FrayInputMap 注册 FrayConditionalInput：forward 默认右、朝左时选左；backward 相反。
- 条件接收 device，经会话注册表查本次合法朝向。首个组件是默认组件，不给它配置有效条件。
- 对角方向复用 FrayCombinationInput；命令域用世界左／右构成世界对角，移动域可用相对前／后。不同 composite 根使用独立组件实例。FraySimpleInput.from_bind 指向基础 bind，不是假定能递归引用任意已注册复合名。

### 4.3 修改插件或额外包装的位置

- **薄封装：**提供朝向条件和必要事件过滤，不重写镜像算法。
- 不改条件输入插件；新链验收后删除 FighterInput 旧的重复镜像，避免乘两次反而变回世界方向。
- 移动速度仍可使用原始世界轴；不假设 composite 的 bool 已传播成正确模拟 strength。

### 4.4 验收

左右面向对称、不同角色独立、锁向期间稳定、完成后按新朝向识别下一批输入。

## 5. 方向清洗、上下序列与换朝向处理

### 5.1 要实现、解决的问题

**左右清洗和上下序列不能用同一个“净轴＝0就丢事件”规则。**

- 左右同时按：用于水平意图及方向步骤的有效水平分量抵消；不能合成同时前后。松开一侧后按剩余方向更新当前状态，但没有新物理按下时不虚构新按钮周期。
- **上下保留独立 press／release 事件，不对序列做上下抵消。** 先按下，尚未松开下又按上，仍然是可识别的 `下 → 上`；不能因为两个都 held 时 get_axis 返回 0，就丢掉上这一步。
- 方向“当前状态”和“输入步骤历史”分开：移动层若上下同时按，首期 crouch 优先且不顺带触发普通跳跃；序列层照样保留上这次按下。命令识别不等于立即执行跳跃。
- 同帧若 Fray 事件不能还原物理先后，先归成同帧事件批，不用输入名字遍历顺序冒充时间顺序。对作者明确声明的 `下→上` 指令，游戏薄层采用显式同帧容错：把这两个真实 press 按“下、上”的步骤顺序送入该 matcher，保留相同 physics_frame，不伪造跨帧时间、不要求先松下。不同帧事件保持实际采样顺序；这叫允许同帧组合，不声称物理上测出了先下后上。
- 同帧同时存在 `下→上`、`上→下` 两条相反指令时，需要作者消歧，不能靠循环顺序随便选招；本轮不改 matcher 为整个引擎添加排序协议。
- 对角步骤仍需避免把一次斜下前重复解释为“下、前、斜下前”三次输入，但这一去重不能顺手删掉独立上／下序列事件。不同 command 可以按声明接收不同输入域，不全部强压成单一 dir_n。
- **普通转向不清未完成的世界方向序列、不重建 matcher。**命令按终结事件时的合法朝向解释整条世界路径；不把转向前后的相对前后串接。第 5.3 节记录本次按用户参考优先级作出的依据与选择；替代此前“默认清旧半条”的暂定规则。

### 5.2 优先使用的 Fray 能力

- 复用 composite priority、distinct、decompose、press／release／virtual 标志；把上下原始事件传给 FraySequenceMatcher。
- 上下步骤可在 command 编译时使用独立 up／down bind 名，或与之对应的独立方向事件，不能只依赖二维轴快照。

### 5.3 转向时保留半条指令：资料与本项目决定

#### 5.3.1 参考优先级与能确认的范围（2026-11-06）

用户指定：优先 MK，其次其他格斗游戏；只有都没有明确说明时，才使用清理旧历史的保底方案。

| 优先级与资料 | 能支持的结论 | 不推断的内容 |
| --- | --- | --- |
| MK（以 MK1 官方补丁为主，另检索 MK11 相关资料） | 本次能确认逐招自动转向等调整，但没有找到普通“半条方向指令跨转向”保存／清理的通用解析规则 | 自动朝向、Input Shortcuts、buffer window 都不能证明半条历史必清或必留；不称为已经复刻 MK |
| Capcom 官方 SF Seminar，SFII 蓄力专题 [S3] | 特定跨换边蓄力有明确条件：换边时同步切到另一物理方向，可维持后蓄力；否则会失去蓄力 | 不推广为 SF6 所有普通方向序列的统一历史规则，也不把蓄力计时等同未完成方向串 |
| Skullgirls 开发者 Mike Z，2014-06-18 原帖 [S4] | 明确解释：记录世界方向，在指令完成、按下终结按钮时，按该时刻角色朝向检查整个 motion；输入过程中的朝向变化不单独清掉这段历史 | 这是开发者对其游戏的说明，不替 MK／街霸全系列作证，不承诺移植所有容错／优先级 |

**决定：已有直接说明，不满足“所有参考都不明确”的保底条件。普通序列采用上述 Skullgirls 的世界方向历史／完成时朝向规则；不再因为普通转向清历史。** MK 若后续取得同等可靠、更适用于本项目的规则，再按既定优先级评估替换，不在资料不足时猜测。

#### 5.3.2 保留的是什么，不是什么

- 保留原始世界方向、press／release、时刻与间隔；不是把旧朝向的“前”直接接到新朝向的“前”。
- 树和 matcher 不因普通转向重建；只更新移动／当前意图的相对方向映射，以及终结事件使用的合法朝向。
- 例如角色原来朝右：先输入世界 `下→左下`，然后转为朝左，再输入世界 `左＋攻击`。完整世界路径是 `214＋攻击`，符合完成时朝左的向前四分之一圆，可以识别。转向前的左下当时是“后下”并不使它自动失效。
- 相反，世界路径是 `236＋攻击`，完成时却朝左，就不能把它当成朝左的向前四分之一圆。**不清历史不等于忽略朝向或让错误方向免费成立。**若它符合另一个明确装备的指令，则另按该指令检查，不能隐式回退。
- 按钮型序列在 press 或配置的 negative-edge 终结事件发生时解释；纯方向序列在最后一个方向步骤时解释。后者是本项目为无按钮指令定义的对应规则，不冒称开发者原帖覆盖了所有纯方向情况。
- 以角色当前实际合法朝向为准，不按对手位置猜测未来会翻哪边；动作锁向期间越过对手但未实际转向，不更换判定朝向。
- 蓄力保留真实世界方向持有时间；成功与否仍检查完成时朝向对应的整套输入要求。不把两个不同物理方向的持有时间无条件相加，不新增“转向等于重新按下”或自动补足蓄力。
- 方向超过原有间隔／蓄力约束仍失效；转向不刷新时限，不修改历史事件时间。
- **已经匹配完成、已经进入 advancer 的命令是另一个阶段。**单纯转向不调用 clear_buffer，也不把它拆回方向重新识别；实际尝试仍走状态权限／合法来源和原生队列期限。

#### 5.3.3 Fray 接线与清理边界

- Fray matcher 不读取 facing_dir。采用稳定的世界方向事件与预编译的左右世界路径，转向时无需改树／重建实例；移动查询继续优先使用 FrayConditionalInput，两者不是重复镜像。
- 普通转向只更新会话当前朝向，不生成假的方向按下／释放，不重放旧事件，也不调用 get_match_branch().clear()。
- 正常匹配到无后继终结叶子后，Fray 会自动 reset；短序列有后继时遵守原生行为。不能为了“保留历史”绕过它的正常完成／超时机制。
- 设备切换、失焦、回合重置等失效事件调用公开 Matcher.clear_history，复用当前对象与编译树；重新配置才 initialize 新树，插件 initialize 现在完整重置历史。游戏不调用私有 _reset。
- **本轮仍不改插件。**兼容事件域合树，world 路径到 move 的静态映射与终结朝向筛选放在 FighterInput 薄层，具体见第 9 节。此层不另写匹配算法或重放全量历史。
- 原生 advancer 的失败出队、统一时限和 FIFO 完全不变；保留未完成的 motion 不等于新增失败出招重试缓存。

### 5.4 验收

- 左右同时按抵消；下未释放就按上及同帧上下容错继续成立，对角去重不破坏上下事件。
- 世界 `2→1` 后转朝左再 `4＋攻击`，可按左向完整指令识别；错误世界方向不会仅因保留历史而被接受。
- 普通转向复用同一个 matcher／树，不伪造 press，不延长间隔；朝向未实际改变时不清历史。
- matcher 的真实超时、设备切换／失焦／重配清理仍有效；单纯转向不删除 advancer 已完成命令。

### 6.3 修改插件或额外包装的位置

## 7. Loadout 与统一指令配置

### 7.1 要实现、解决的问题

- 只调用一次 resolve_selection，得到 selection.moves／states；状态机、判定与输入共用结果。
- command 是固定逻辑指令来源；当前状态入口按 Move.state 解析（叶子或复合组静态定义），不倒回旧 required_state_paths 协议。
- selection 后统一处理基础和装备输入，即使未装备招式，基础 bind 也正常注册。

### 7.2 优先使用的 Fray 能力

- command 编译为 Fray simple／combination 与 SequenceTree／Branch；不编译成新的自建匹配语言。

### 7.3 修改插件或额外包装的位置

- **薄封装：**统一注册入口先建立基础 bind、相对方向，再建立装备所需组合、最后创建角色 matcher；全部完成后才启用输入。
- 全局复合名考虑按钮、模式和定义参数，同名不同定义不能互相覆盖；共享资源不存 matcher 进度。
- 第一阶段适应原生 advancer：同一实例统一 max_buffer_time；现有 command.buffer_frames 不再承诺每招独立重试期限，保留迁移说明或停用该语义，不静默声称还生效。
- 完全同指令和方向按键重叠由作者约束／明确优先规则消歧，不按能量等条件隐式回退成另一招。
- 不改插件资源系统；保存／重载仍由资源测试保障。

### 7.4 验收

未装备招式不识别，空装备能移动，两个角色配置互不覆盖，统一注册不遗漏基础动作。

## 8. 单键、方向加按钮、同时键

### 8.1 要实现、解决的问题

- SINGLE 区分 press／release，echo／长按不重复出招。
- 前＋M 在 M 按下时读取方向，不等于先前再 M 的序列。
- COMBINATION 要求实际按键重叠和指定时间容错；普通单键延迟确认，不先执行再撤销。

### 8.2 优先使用的 Fray 能力

- Fray 事件处理单键，FrayCombinationInput 判定组合；FrayInputTransitionPress／Sequence 接入状态机。
- 本轮继续 ASYNC＋FighterInput 的帧差过滤，明确这是最少接线，不另建组合匹配器。

### 8.3 原插件容错问题的具体例子与决策

- ASYNC 例：L 已按住 1 秒，再按 M，只要都 held 就成立；若 command 规定 2 帧内组合，原生 ASYNC 不能单独表达，需要游戏帧差检查。
- SYNC 例：本地实现 `_is_combination_quick_enough(..., tolerance=10)` 默认是约 10 ms 的内部参数，builder 没有暴露 command 所需帧容错；60 tick 下 2 帧约 33.3 ms，不能当成相同窗口。
- 多键例：现算法累计相邻时间差再除组件数，不是 max(time)−min(time)。三个按键相差 0／15／30 ms 时，可得到 10 ms 的平均值，却有 30 ms 总跨度，接受语义与“所有键在 10 ms 内”不同。
- **本轮不改 CombinationInput。**保留 ASYNC＋FighterInput 内显式的 max−min 帧差检查。未来只有决定把通用容错下放插件时，再单独加参数与兼容测试，不作为本轮依赖。
- advancer 原生 `time_held` 是条目入队后经过的毫秒；Press 转换期望秒且含义是持键时间。比如只按了 30 ms、队列暂停等了 200 ms，不能把 200 当成真实持键时长。首期不启用依赖此值的 min/max_time_held、蓄力转换；蓄力在序列识别层用原始事件处理。

### 8.4 验收

同帧／边界／超时组合、按住方向再攻击、释放后剩余按键、错误 time_held 使用均有覆盖。

## 9. 方向序列、蓄力与松键

### 9.1 要实现、解决的问题

- 支持固定步骤、相邻间隔、首步蓄力、negative edge 与明确配置的容错分支。
- 支持下上重叠、同帧容错及纯方向终结，不继续依赖“最后一个按钮 ID 非空”才生成识别结果。
- 序列匹配与出招合法性分开，识别结果不直接 goto。

### 9.2 Matcher、Tree、Branch 与世界方向路径

```text
角色 A 的角色输入上下文（独立运行历史）
  └─ FraySequenceMatcher（每个兼容事件域一个）
       └─ FraySequenceTree（稳定的世界方向路径）
            ├─ route_world_236_l → 世界 2、3、6、轻攻击
            ├─ route_world_214_l → 世界 2、1、4、轻攻击
            └─ route_down_up → 独立的世界下、上步骤

world 路径命中 + 终结事件时合法朝向
  → 当前装备的具体 move_id

角色 B → 自己的 matcher，不共用角色 A 的历史
```

- Tree.add(name,branch) 可以有多个命名序列；同名也可有多个不同容错分支。Matcher.initialize 会编译整棵树，不是一招只能用一个 matcher。
- 目标为每角色、每兼容事件域一个 matcher；配置可只读共享，运行历史不可共享。过滤语义不兼容时再拆域。
- **适配第 5.3 节：序列历史不再逐事件固化为当时的相对前／后。**command 仍由作者写成相对指令，战前一次编译出对应的左右世界路径；运行时匹配稳定世界事件，在完成回调根据终结时朝向挑选符合的命令。
- 同一世界路径可能对应“朝右的向前招式”与“朝左的向后招式”。原生树一个终点只能登记一个名字，不能重复注册两个 move 名碰撞；先登记一个稳定 route 名，再由只读映射按完成时朝向和装备选择关联的 move。仍冲突时由作者消歧，不变成能量／状态隐式回退。
- 不同路径的时限存各自 branch；完全相同世界路径但时间／负边要求不同，不能假装两个名称可共用一个终点。按兼容规则拆输入域，或用现有 FraySequenceMatcher.is_match 对 get_match_branch 的事件做命令级要求复核；不自写匹配算法，也不要求改插件。
- 短指令是长指令前缀时仍按原生发信号行为处理，不自动得到最长匹配。借用开发者明确的坐标解释策略，不宣称 Fray 已与 Skullgirls 的完整解析器、容错和冲突优先级等价。
- 当前运行代码仍是每个 move 建 matcher、读相对 dir_n、实际转向时重建。本轮只改方案，不能因文档目标已改就声称跨转向连续识别已经实现。

### 9.3 不扩展插件的接线示意

以下 world 名称是**目标方案的示例命名**，不是现有工程已经注册的 Fray 内置输入；world_1／world_3 等由世界 bind／composite 的归一化层提供，角色转向不改名。

```gdscript
    var tree := FraySequenceTree.new()
    tree.add(&"route_world_236_l", FraySequenceBranch.builder()
        .then(&"world_2").then(&"world_3").then(&"world_6")

        .then(&"world_2").then(&"world_1").then(&"world_4")
        .then(&"light_attack").build())

    route_moves = {
        &"route_world_236_l": {1: &"forward_special"},
        &"route_world_214_l": {-1: &"forward_special"},

    matcher.initialize(tree)

func feed_filtered_world_event(event: FrayInputEvent) -> void:

        return  # 匹配了世界路径，但不符合当前朝向的这个命令。
    var move_id: StringName = moves_for_facing[facing_at_finish]
    # 用 matched_events 关联来源，完成入队前归属判断。
    # 再 buffer_sequence(由 move_id 编译的命令名)，不重新匹配方向。
```

- 使用现有 match_found 与 get_match_branch，不加详情信号。同步回调里复制数组，自动 reset 后原数组可能清空；事件对象按只读使用。
- 多输入域场景必须从实际发信号的 matcher 取 branch；matcher 不替角色过滤 device，也不会自己订阅全局输入。
- 方向历史只在首次编译时组织世界路径；**普通转向不 initialize、不 new、不重放历史**。完成时按朝向选择符合的静态命令映射，错误方向不变成合法指令。
- 已入 advancer 的命令不因再次转向被重解码；真正发动时仍检查来源／前置条件。普通转向不清缓冲；失焦、设备切换等会话失效仍按生命周期清理。
- get_match_branch 不附带本项目的按键周期 ID，也不让原生 advancer 突然具有 payload／按来源删除能力；第 10～11 节限制不变。
- 纯方向终结也从本次匹配事件关联来源；蓄力按真实世界方向时间和正确方向要求复核，不把翻面生成的 composite 状态变化算成真实按下。

### 9.4 验收

- 一个 matcher 识别多个命名世界路径；角色转向前后仍是同一实例／同一树。
- 朝右时开始世界 2→1，朝左时完成 4＋攻击，可以识别朝左的向前招式；错误世界路径、已过原有间隔的路径不通过。
- 世界路径相同、当前朝向不同的静态映射不会重复登记终点；完全同路／前缀冲突有明确内容约束。
- 信号内取完整 branch，复制数组在自动 reset 后仍可读；不同设备／域不串历史。
- 下上 overlap／同帧、纯方向、蓄力、negative edge、错误步骤和失焦清理继续覆盖。

此前临时最小工程的 7 项验证支持 Fray 的多序列、实例复用、branch 回调读取等 API 能力；**不代表本轮“世界路径＋完成朝向”迁移已实现或已通过完整集成测试**。新策略按上述用例单独实现与验收。
## 10. 入队前的指令归属与单键回退

### 10.1 要实现、解决的问题

- 同一按钮周期避免同时产生普通攻击和已确认特殊技；组合 L＋M 不能又分别提交两个普通攻击。
- 归属竞争尽量在入 advancer 前解决；原生队列不提供 source_ids、按来源删除与消费回执。
- 不同真实来源可独立入队；同帧相反方向序列／同指令由作者消歧。

### 10.2 优先使用的 Fray 能力

- 使用事件及复合输入分解关系；序列通过原生信号及回调内 get_match_branch 获取本次来源。distinct／priority 不等于招式选择评分。

### 10.3 必要游戏薄层及限制

- 来源至少区分 device、bind 与按下周期；组合／终结事件关联用于入队前的重复抑制。
- 普通单键等待组合确认，可保留短暂“尚未决定归属”的识别状态；这不是已失败命令的重试队列，也不保存第二份可执行候选。
- 特殊指令确认后可以立即取消尚未入队的同源单键；**已经入 advancer 的同源条目不能承诺按来源移除**。因此先裁决后入队，不先塞单键再等特殊技撤回。
- 同源被认领不等于已经出招／扣费。即使原生 advancer 首次执行失败而丢弃，也不再自动回退同源普通攻击。
- 按识别完成顺序入队，不添加每帧评分／任意前缀延长解析。需要更强行为时先改内容约束，不偷偷恢复自建 Buffer。

### 10.4 验收

同源只入队一次；普通单键等待正确；特殊技执行失败不会自动变普通攻击；独立第二次按键可以重新入队。

## 11. 原版 FrayBufferedInputAdvancer 的缓冲行为

### 11.1 要实现、解决的问题

- 把 Fray 的 press／sequence 结果接到现成队列；本阶段的缓冲指“保存到一次被允许的尝试”，**不是失败后每帧重试**。
- 使用一个实例的统一期限和 FIFO 顺序。若需要动作期间暂不尝试，可由游戏控制 paused，恢复后的合法性由转换层判断。
- 不让旧 FighterInput._candidates 与 advancer 同时持有可执行候选。

### 11.2 组件选择与原生实际逻辑

- **暂不使用 FrayInputBuffer**，不安排它的窗口／device 修复，也不把它作为本轮依赖。
- **必须使用现有 FrayBufferedInputAdvancer，且不改其逻辑／字段／队列类型。**入口为 buffer_press、buffer_sequence；公开清理用 clear_buffer；查看用 get_buffer。

原生 `_advance()` 的实际过程：

```text
while 队列不空 且 paused=false：
    pop_front 取出一个条目
    计算是否在统一 max_buffer_time 内
    生成 state_machine_input
    若未过期 且 state_machine.advance(input) 返回 true：
        更新接受时间并结束本次循环
    否则：
        该条目已经出队，继续处理下一个
```

- paused=true 时不尝试、不 pop；墙钟仍走，过期条目可留在内存队列，到恢复时才被取出跳过。
- 同一帧可尝试／丢弃多个失败条目，遇第一个 true 才停；不是“每帧只检查队首一次”。
- 队列原生只存 press 或 sequence 及时间戳；没有 move payload、ready_frame、独立 expiry、来源消费或成功信号。

### 11.3 不改插件时可能的问题：按现状接受并写入测试

| 例子 | 原生结果 | 本轮处理 |
| --- | --- | --- |
| 第 10 帧识别攻击，当前动作第 12 帧才结束，advancer 未暂停 | 第 10 帧尝试失败后立即丢弃；第 12 帧不会自己再出招 | 接受此语义；确需预留可在不允许尝试期间 paused，但不能据此保证所有取消窗口 |
| paused 时输入，过了统一 max_buffer_time 才恢复 | 恢复后出队并丢弃，不会执行；暂停没有冻结时钟 | 接受并设置合理统一期限；不加逻辑帧暂停时钟 |
| 招式 A 想缓冲 2 帧，B 想 8 帧 | 同一 advancer 只有一个 max_buffer_time | 第一阶段统一值；不宣称 command.buffer_frames 还在逐招控制队列 |
| 识别后才发现某条输入已入队且与另一个输入同源 | 原生没有按来源删除 API | 第 10 节先仲裁再入队；不进入私有数组删项 |
| 一个输入被普通自动移动边接受，advance 返回 true | 原生认为已成功并停止，但不保证攻击已发动 | 允许此原生行为；true 仅表示有转换，后续条目留到下帧，不据此扣除攻击资源 |
| 多条有效命令同帧入队 | 按顺序 pop；遇 true 就停，剩余条目留待后续帧 | 不加招式优先级队列，内容避免无意冲突 |
| 状态入口需要 args["move"]，但调用 buffer_sequence 只传了名称 | advancer 不会自动提供招式 args | 静态命令名→招式定义映射，由游戏侧状态机接线补齐，见第 12 节 |

- **本轮不扩展 advancer 的 payload、失败保留、单条期限、手动驱动和事务式确认接口。**旧 `_candidates` 移除前先测清这些改变，旧“失败保留”的测试应另存为已放弃行为说明，不以新断言谎称等价迁移。
- 新增虚拟方法／继承来重写 `_advance()` 也算改变其逻辑，本轮不用。禁止失败后自动重新 buffer 同一命令来变相实现重试。
- `max_buffer_time` 在统一输入配置时换算；真实 held 与缓冲 age 不混用，首期不配置依赖错误 time_held 的输入转换。

### 11.4 验收

用测试明确观察失败即丢弃、暂停排队、恢复丢过期、FIFO、一个 true 后停止；不能用“场景能启动”代替这些队列行为验证。

## 12. 原有转换接口上的命令接线

### 12.1 要实现、解决的问题

- advancer 的输入先经过权限和规则检查；输入信号不绕过状态机直接 goto。
- 保留活动来源、招式级／规则级条件、AT_END／IMMEDIATE 与进入参数。
- 原生 bool 的“发生了转换”和“这个命令被接受”可能不同，需要在允许范围内接线，不能靠插件扩展作为本轮前提。

### 12.2 优先使用的 Fray 能力

- 优先用 FrayInputTransitionPress／Sequence、FrayStateMachine.advance(input,args) 和原版 advancer 的自动处理。
- 命令识别完成后可用稳定 `sequence=game_cmd_<move_id>` 标识；它只是识别标识，不要求状态机再次匹配方向。
- 使用现有 FrayStateMachine._advance_impl 虚拟入口，通过**游戏侧派生脚本替换现有 FrayStateMachine 节点的挂载脚本**作薄接线。不新增状态机 Node，不改插件，不新增第二套状态树；新增脚本文件与新增节点是两件事。

### 12.3 暂不实施插件扩展；适配方案与限制

- 不新增公开全路径转换 API、命令接受回执／过滤 API，也不修改插件层级 AT_END 行为。
- 游戏侧状态机接线可按命令名查只读招式注册表，构造原有 move／move_id 参数，调用现有游戏权限检查和跨层桥接；命令拒绝后允许尝试普通转换；true 仅代表本轮发生转换，不代表攻击发动。返回后 advancer 仍按第 11 节原生逻辑丢弃／继续／停止。
- 当前 `_try_move(candidate)` 的 candidate.created_frame 等协议要在迁移时调整；原生队列不提供这些元数据，不能把缓冲时间戳当作完整原始输入帧。暂不实现依赖精确原始帧的战斗规则。
- 无命令的普通推进由单一调度路径处理；状态机保持 MANUAL，不能同时启用自动 advance。advancer 自动喂入与普通推进要有同帧成功标记，避免两次切状态；这是游戏侧协调，不改 advancer 的 while 循环。
- 游戏适配在招式或接续普通边成功时均更新本角色本帧提交标记；只有两者都不成立才返回 false，不补发／重排旧命令。
- 跨层桥接继续集中使用当前已存在的 `_transition_to`，源与最深叶子完成检查留在一个游戏入口；承认它是内部接口耦合，不把它包装成已存在的稳定 Fray 公共 API。
- 如果后续发现必须重写 advancer 或插件转换算法才能满足新要求，先停在明确限制并另外讨论，不在本轮顺手实施。

### 12.4 验收

合法／错误来源、完成等待、跨组返回、args、普通移动允许接续，但不能触发攻击扣费，以及同帧最多一次游戏转换；所有拒绝仍遵循原生缓冲出队行为。

## 13. MK 风格的组合技预输入、取消和派生

### 13.1 要实现、解决的问题

- 想要的体验：可提前输入后续按钮，实际攻击按规定衔接帧执行，输入接收和动作切换不是一回事。
- 普通动作默认锁向；组合技换边／取消是否刷新方向，逐条动作规定，不假设整条路线随时跟踪对手。
- **原生 advancer 本身不是完整 dial-a-combo 路线系统。** paused 是全局尝试开关，不能同时表达每段独立输入窗口和所有取消时机。

### 13.2 优先使用的 Fray 能力

- 继续复用事件、原生 matcher、advancer 队列和状态转换；不启用 FrayInputBuffer。

### 13.3 必要游戏包装与分期

- 本轮先完成第 11～12 节原生缓冲基本接入，不承诺高级预输入已经可用。
- 后续需要精确 MK 风格路线时，用游戏动作局部的有限 pending_followups、输入窗口、规定提交帧；它保存已认领路线，不是第二份全局失败重试队列，也不改 advancer。
- 必须先验证“由 advancer 接受为路线认领”如何与真正换状态区分；没有明确协议前不实现。原生不带来源／payload／原始帧的限制可能要求缩小内容范围。
- 已消费起手不能复活，窗口外旧输入不能接续。取消、资源、命中条件属于游戏，不能塞进插件。
- 详细时序参考[招式设计计划](../计划/招式设计计划.md)；本文只定义现阶段限制和接口边界。

### 13.4 验收

当前先验收原生缓冲行为；路线后续单独测快速预输入、衔接帧、中断、换边、错误分支，不能因为选用了 advancer 就标为完成。

## 14. 统一初始化、帧调度与清理

### 14.1 selection 后统一注册：目标顺序

**可以统一安排，且本方案采用此方案。**这不要求玩家物理改键也等到 selection：已有 InputMap 物理配置由项目／设置系统管理。

1. 角色及 Controller 准备好，暂不启用输入识别、advancer 提交和状态推进。
2. 调用一次 loadout.resolve_selection()，得到 selection.moves／states；失败就停止装配，不注册半套角色输入。
3. 在现有 FighterInput 中建立设备→角色输入上下文，初始化并发布首份合法朝向／设备上下文；不创建单独的 Context Node。
4. **统一注册到 FrayInputMap：基础 bind → 相对方向／对角组合 → selection.moves 所需输入组合。**即使 moves 为空也注册基础输入；已有相同定义幂等复用。
5. 用已注册的名称创建本角色序列 matcher、单键／组合识别配置、命令名→招式定义表；配置原版 advancer 的统一 max_buffer_time／AdvanceMode.PHYSICS。
6. 用同一 selection 装配状态、转换与判定，注入上下文和游戏状态机薄接线；清理初始化历史，advancer.clear_buffer()。
7. 设置优先级、启用采样和唯一提交链；状态机保持 MANUAL。现有 Fighter 的帧末回调统一发布后续上下文，初始化已发布值保证首帧没有空档。

统一注册入口放在 FighterInputBindings／FighterInput 配置接线中即可，不为了“统一”新建大型管理器。当前基础注册在 selection 前，实施时需要移动，不声称现在已按本顺序运行。

### 14.2 无新增节点的物理帧顺序

```text
初始化／上一物理帧末：
Fighter 检查活动状态朝向权限，提交合法朝向
  → 现有 FighterInput 保存已发布的 facing/device/session 上下文

本物理帧：
FrayInput：bind → composite → 事件       priority -100，读取已发布上下文
FighterInput：分流 → matcher → 入队      priority -50，仍使用同一份朝向
FrayStateMachine：活动状态物理更新        priority 0，MANUAL 不关闭状态更新
原版 advancer：自动 _advance            PHYSICS，示例 priority 25
Fighter：未有成功提交时做普通推进         priority 50
Fighter：统一帧末收尾，发布下一帧上下文    同一 priority 50 回调的末尾
```

- **不新增 FighterInputContext，不要求 priority=-150 的独立回调。**条件输入直接按 device 查询现有 FighterInput 会话中的已发布朝向。
- set_facing／设备切换入口在采样期间只登记请求，不能立刻修改全局条件回调读取的值；帧末由 Fighter 查询当前活动状态权限后统一提交，并同步表现／运动使用的合法朝向。初始化可显式立即提交首份值。
- 本帧命令终结事件使用本帧已发布朝向；帧末转向不重解码本帧已经识别或入队的命令。普通转向仍保留世界方向历史。
- 新攻击本帧已进入且锁向时，不因为帧末有旧的转向请求就翻过去；新状态权限优先。旧攻击本帧结束且允许转向时，提交的新朝向供下一帧输入使用。
- Fighter._physics_process 不能因本帧命令已成功而直接 return、跳过收尾；“跳过普通推进”和“始终执行上下文发布／清理”要分开。对同一角色本帧发布只进行一次。
- 不承诺同步到输入之前才更新的外部转向请求可以无延迟生效；这套设计明确接受下一次采样生效的边界。断线／失焦可立即禁用并清理会话，但不能用停用时的陈旧上下文继续识别。
- advancer 保持原生自动处理，不增加手动驱动接口；仍不能同时启用状态机自动 advance。
### 14.3 暂不扩展插件；用现有能力清理

- FighterInput 负责 configure／reset／dispose 的游戏生命周期接线；普通转向保留世界方向历史，复用 matcher。失焦、设备切换和回合重置调用公开 clear_history；重配时 initialize 重编译，不新建 Matcher；同时清理 advancer 缓冲；不能因普通转向清掉已完成命令。
- **不新增插件 reset／缓冲 API／生命周期 API，不依赖公开化 `_transition_to`。**设备／焦点切换只通过已知接口停用和清理。
- 暂停不等于冻结 Time.get_ticks_msec；不要把 paused 当成所有输入系统停止计时。明确失焦策略为清空而不是回来后继续执行旧招。
- 保持一个转换提交链：原版 advancer 处理命令，Fighter 只在本帧未成功提交时做普通推进；不打开状态机自动推进，不额外手动调用 advancer._advance。
- 回滚、严格逻辑帧时钟、虚拟设备完整支持以后单独实施，不在此处提前安排插件扩展。

### 14.4 验收

失焦回来不出旧招；设备切换不继承半条序列；回合重开清空原生队列；重复配置无重复连接；一次成功不导致本帧第二次普通转换。

## 15. 实施顺序、插件边界与回归

### 15.1 分阶段实施

| 阶段 | 范围 | 下一阶段前的要求 |
| --- | --- | --- |
| A | 1～3：单位换算、selection 后统一注册、物理设备绑定 | 原生换算精度明确；基础／装备输入都在首采样前注册 |
| B | 4～6：移动镜像、世界方向流、上下步骤、转向策略 | 左右抵消、下上重叠／同帧、转向不清世界历史且完成方向正确 |
| C | 7～10：左右世界路径编译、完成朝向映射、原生 matcher、入队前仲裁 | 转向保持同一 matcher，错误完成朝向不通过；不能表达的内容明确限制 |
| D | 11～12：原版 advancer 与游戏状态机接线 | 失败即丢弃等原生语义有用例；不误消费、不重复转换，删除旧重试队列 |
| E | 14：生命周期与完整场景回归 | 失焦、设备切换、重开清理通过 |
| F | 13：未来路线预输入 | 先明确不改插件时能做到的范围，再做逐条招式内容 |

## 16. 目标结构与资料边界

```text
Loadout.resolve_selection()
  → 统一注册 FrayInputMap（基础 → 相对方向 → 装备组合）
  → 为本角色配置原生 matcher、命令映射与 advancer

运行时：
已提交合法朝向 + 设备输入
  → FrayInput／ConditionalInput／CombinationInput
  → FighterInput（世界方向输入域、上下步骤保留、组合帧差）
  → FraySequenceMatcher／原生识别 → 按终结朝向映射命令、入队前仲裁

```

包装只补游戏协议和当前插件接口的必要接线；不借“薄层”重写原版缓冲逻辑。本阶段明确接受缓冲行为限制，以后要改必须另行确认。

## 18. 扁平运行状态方案（2026-11-10，替代旧层级接线）

### 18.1 结构与配置


Loadout 使用 selected_state_names、selected_move_ids、entry_state；删除 group_start_states。转换端点一律写直接名称，不提供旧路径兜底。默认返回边明确为 light_attack→idle，不把“任意 action”组出口自动扩散到其他动作。

### 18.2 原生转换与执行顺序

Builder 直接 add_state／add_transition。命令边使用 FrayInputTransitionSequence；普通条件边使用 FrayStateMachineTransition。注册顺序为命令优先，再普通边；每类按 priority 小者优先，同值按资源顺序。输入边开启原生 advance_conditions 检查，但 accepts 仍要求匹配的命令，空输入不能发动攻击。

AT_END 查询当前被离开的状态，组会递归等待子状态完成；Fighter 朝向权限仍通过 get_active_leaf 找到实际动作，重复的 active_leaf_done 条件已删除。攻击命令拒绝后可按原生扫描继续普通边，advancer 原逻辑不变。

### 18.3 本轮文件范围

运行脚本：state_definition、fighter_loadout、sm_builder、transition_definition、fighter。资源：默认 Loadout、转换库、五个状态定义；测试全部使用扁平名称，并新增 flat suite 验证正式 Builder 的原生根、直接叶子和运行行为。正式场景节点和 Fray 源码不变。

所有产品条件检查均由原生边执行，Builder 直接创建 FrayCompoundState。无自定义根类、跨层规则表或空类型包装。

### 18.4 原生根与流程组

根直接使用 FrayCompoundState.new()，没有空类型包装。基础移动、输入命令与恢复返回由同一正式 Builder 注册的原生边验证；以后新增局部流程组仍使用 CompoundState，不为根增加转发类。

## 19. 多数同根、流程按需复合的目标修订（2026-11-10）

### 19.1 不再把全部扁平作为永久限制


### 19.2 输入与注册

- SINGLE：无方向攻击键。
- 方向＋攻击：选择相对前后／下等条件组件和攻击组件，使用 FrayCombinationInput 注册；先按方向再按攻击允许，不要求短同步容错。新攻击按钮才触发，单纯翻面使 held 变化不自动出招。
- COMBINATION 的两攻击键同步窗口与方向修饰＋攻击语义分开；精确方向和普通按钮竞争需要明确约束。
- SEQUENCE／单角色一个 FraySequenceMatcher：快速特殊技，保留既定世界历史和终结朝向语义，不用于整串组合技输入完才启动第一击。
- 当前 required_direction 快照和 buttons-only 组合注册还没有迁成上述方向复合注册。本轮只修订目标，不声称已修改运行接线。

### 19.3 组合技与投掷的组边界

根起手 A 在后续 M 和合法取消／提交点成立时，根 A→combo；combo.start_state=B，进入的就是下一击，不重打 A。内部 B→C 由本段输入窗口／后续请求决策，父组保存本次路线事务。组可在 B/C/D 任一段完整恢复后由根出口返回 idle；出口同时确认无合法待执行后续，不强制 done，也不指定 D 为唯一终点。

投掷根合法来源→throw_group(start=grab)，captured 确认才 grab→throw_attack；未抓到走 whiff 恢复，需要时设 break 恢复。对方受投状态、目标绑定和清理是双方战斗协议，不由 CompoundState 自动产生。

命令与取消仍需明确条件。AT_END 等动作完整结束；跳过恢复用 IMMEDIATE＋取消条件。组 start 只选默认子状态，不替代取消和序列识别。

### 19.4 保留原生 advancer，但不冒称它提供路线缓冲

原版 advancer 失败出队／统一期限不变。M 在窗口前已经尝试失败就丢掉，不会到 commit 时重试。完整 dial-a-combo 的早期 M、H 接收要另外设计本次路线局部的有限认领／pending 协议，不能通过新建组自动获得，也不绕过此前不改 advancer 的决定。

### 19.5 后续落地点与插件结论

- Builder 未来需要显式组定义和转换 owner/scope，分别注册同一父组的直接边；不是把任意深路径适配复活。
- Fighter 当前直接 cast 根叶子查询转向；有组时需按真实活动叶子和父组事务约束查询，不把 CompoundState 当 FighterState。
- start 固定为下一击 B；允许 B/C/D 多个收招点，不强制 done。end_state 不是可结束状态列表；保持默认空值时用根出口前置条件检查当前动作恢复和待提交后续，也可定义准确的局部完成查询。
- 临时测试证明历史版有默认叶子漏 enter，正确局部组也会触发；不因修正概念就整包撤掉生命周期补丁。真实缺陷修复保留，父子优先／导航扩展按项评估。
- 条件按规则 owner 明确注册：组内边只用本地绑定，根的出入口绑定在根并读取本次组事实。当前不考虑根条件继承，不把插件回退查找列为路线实施依赖。

完整拓扑、时序、装配边界以[角色动作与复合状态组织方案](角色动作与复合状态组织方案.md)为准；已落地的 flat 基线和资源接口仍以当前状态机说明为准。新增局部组直接使用 FrayCompoundState 表达，不需要重新增加根包装。

## 20. 多出口前缀路线与条件作用域约定（2026-11-10）

组合技起手 A=root.light_attack，combo1 内 B/C/D 均为普通攻击 FrayState。A 不接续、AB、ABC、ABCD 是四个可展示前缀；combo1.start_state=B，正常执行不随菜单条目动态改 start/end，也不为每条前缀复制相同状态。

不强制 done；根 combo1→idle 的前置条件检查可收招叶子、动作完整恢复且无合法待提交后续。B→C／C→D 合法接续先于自然收招，并有明确窗口／取消条件；坏的过期 pending 先失效，不能堵住组出口。

同一命令仍可由不同活动状态的边接受。路线表条目不是 SequenceMatcher 的完整启动指令：L 发动 A，后续按钮按本次路线逐段接续；只注册去重后的基础／组合命令，不注册 LM／LMH／LMHK 三套整串特殊技来竞争启动。

选装身份与状态复用分开；建议路线族＋长串前缀闭包。若每条串单独装备，需要明确连接授权／前缀依赖，不能仅靠组内成员装配与端点存在开通所有路线。当前代码还没有这些路线资源，本轮只更新设计。

条件一律在所属 owner 显式 set_condition；本地组可读取角色方法，不需要继承根条件。该功能和修复暂不考虑。详细条件示例见[复合状态完成与条件作用域处理](../说明/复合状态完成与条件作用域处理.md)，路线结构见[组合技路线条目与多出口设计方案](组合技路线条目与多出口设计方案.md)。
