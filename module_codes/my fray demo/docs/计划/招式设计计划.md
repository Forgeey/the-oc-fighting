# 招式设计计划：同根基础动作＋局部流程组

> 2026-11-11 容器式装配更新：叶子和转换不再保存父组字符串；FighterCompoundStateDefinition.states／transitions 直接持有成员与内部边，TransitionLibrary.transitions 仅持有根边。组内归属由资源放在哪个容器决定，详见[状态机资源配置说明](../说明/状态机资源配置说明.md)。旧字段说明及示例已删除，不提供兼容别名。


> 修订日期：2026-11-11。目标设计以[角色动作与复合状态组织方案](../方案/角色动作与复合状态组织方案.md)为准；本文件整理招式制作和时序。当前已有同根移动／轻攻击、一个 Matcher、原版 advancer、Attribute 帧窗口；显式局部组装配和插件递归完成与父 AT_END 已实施；方向＋攻击复合注册、完整路线授权／局部预输入和投掷捕获业务尚未实施。
>
> 本轮通过两份 Fray 的递归完成修复简化父出口，不再重复读取叶子完成，不新增场景节点。输入资源、状态／转换、判定属性保持职责分离；不把作者分类目录机械变成运行分组。

## 1. 招式类型

| 类型 | 输入 | 状态组织 |
| --- | --- | --- |
| 基础无方向攻击 | SINGLE：L／M／H 等真实攻击事件 | 多数直接位于角色根 |
| 方向修饰攻击 | 方向条件输入＋攻击按钮，**注册为组合输入** | 多数为根的直接攻击状态 |
| 组合技 composite_attack | 无方向／方向＋攻击的固定后续顺序，按时间窗口接续和取消 | 根起手 A，下一合法攻击输入使根 A→组合技 CompoundState，start_state 是下一击 B |
| 特殊技 special_attack | 快速方向／按钮 SEQUENCE，也可有纯方向序列 | 单角色唯一 FraySequenceMatcher；执行叶子多数仍在根 |
| 投掷 throw | 投掷输入和合法性检查 | 专属 CompoundState，grab→确认→throw_attack，失败另走恢复 |

不再维持旧的“首期不计划投技”结论。类型与资源编号沿用[招式编号模板](../方案/招式编号模板.md)，不按动作分类生成运行路径。

## 2. 三阶段、三段攻击与流程组

- 单段 startup／active／recovery 在一个攻击 FrayState 内按 Attribute 配置推进，不为三个时间阶段强行建三个子状态。
- 组合技 B、C 等是独立动作／叶子，各自从 0 帧开始，有自己的时间、动画与判定。
- CompoundState 表示“本次组合路线／本次投掷”整体：默认入口、局部转换、完成和退出事务。
- 根中普通移动、基础攻击、独立特殊技多数保持同级。只有流程需要层级，不因为文件夹嵌套就创建层级。

## 3. 基础攻击输入

### 3.1 无方向单键

按钮 press／作者允许的 release 产生逻辑 command，由当前状态的原生输入边检查允许来源、prereqs、advance_conditions 与完成／取消模式。command 不对应唯一 move_id；同一输入可以在不同姿态走不同边。

### 3.2 方向＋攻击

例如 6＋M、2＋L：前后由条件输入依角色当前合法面向选择左右，组合通过 FrayCombinationInput 注册。方向可以预先按住，不要求方向与攻击同时按；只由新攻击按钮触发命令，不能按住攻击后靠翻面／移方向重复触发。

普通 M 与 6＋M 的归属在入队前裁决；精确前／下前是否互容由作者明确。现有 SINGLE.required_direction 是当前快照实现，不冒称已完成本次要求的组合注册；后续迁移以目标方案第 3 节为准。

## 4. 组合技：A 后进入组，组入口是 B

### 4.1 示例结构与合法接续

```text
根：light_A --M + 取消／连接条件--> string_lmh
string_lmh（start=B）：
  B --H + 本段连接条件--> C
  C --下一输入＋合法提交条件--> D
根：string_lmh --当前 B/C/D 完整恢复且无合法后续--> idle
```

M 被接受为 A 的后续输入时，进入组后的第一击是 B，不能重播 A。子组可有 B→C／D 的局部分支；不同根入口需要不同默认下一击时，首期用明确的不同路线组，避免每次改 start_state。

### 4.2 仍须分清输入接收和转换提交

| 数据／事件 | 用途 |
| --- | --- |
| input_window | 某段／本次路线何时允许认领后续按键 |
| pending_followups | 本次路线已合法认领但尚未执行的有限后缀；不是全局失败重试队列 |
| commit_frame／明确提交区间 | 当前攻击到何时才真正取消并换到下一段 |

按键被认领时 A 不必马上退出。A 到提交点复核后才走根 A→组；B.start 从 0 计时，已预输入 H 也必须等 B 的提交点，不能因为队列里有 H 就在 B.enter 当帧跳过 B。

窗口、帧数和请求协议属于本项目设计，不是已公开 MK 引擎源码。“start=B”只解决进入哪一击，不解决接收窗口或延迟执行。

### 4.3 原版 advancer 的实际限制

本阶段仍不修改 FrayBufferedInputAdvancer：尝试失败就出队、统一期限、暂停不冻结时间。过早 M 会被拒绝并丢弃，因此只建一个组不会自动获得 dial-a-combo。

先实现“合法窗口按下才即时接段”可直接用原生输入边；若要 A 期间连拨 M、H，则另做本次路线的接收／认领／有限后缀协议。必须明确输入在进入 advancer 前被哪层认领，不能在已失败出队后偷偷恢复重试。

取消剩余恢复使用 IMMEDIATE＋明确窗口／命中／资源条件；AT_END 表示等动作完成，不当作取消窗口的替代。普通恢复出口和特殊技取消的优先级显式配置。

### 4.4 中断和结束

打断、死亡、转入特殊技等离开路线时，清后缀、来源认领及临时目标；不恢复已消费的起手 L。当前正在执行的 B/C/D 未完整恢复时不能按自然收招出口离组。

两份 Fray 已修正组完成：无 end_state 时递归等待当前子状态；有 end_state 时等待指定子状态自身完成。B/C/D 各自完整恢复后都可收招，combo1 不设置 end_state，不需要空 done。

### 4.5 动作完成与真正退出

BasicAttackState 按 Attribute 帧数报告完成；插件把叶子完成沿活动组递归传播。父 combo1→idle 使用 AT_END、auto_advance=true，prereqs 不再添加重复的叶子完成条件。

组内合法 IMMEDIATE 接续仍可取消未结束恢复，内部接续优先于父收招；未来的无有效 pending 条件属于业务，不由插件猜测。没有父出口 transition 或没有 advance，完成也不自动返回。

详见[复合状态完成与条件作用域处理](../说明/复合状态完成与条件作用域处理.md)。

## 5. 特殊技：Sequence／Matcher 即可，不与组合技串混同

- 固定相对输入，例如 236＋L；纯方向下→上仍允许，输入层保留上下独立事件和统一同帧下上容错。
- 一个角色一个 FraySequenceMatcher，作者只配置一套相对步骤，构建时编译左右世界分支。换边不注册两份招式、不重建 Matcher；保留世界历史，按终结时合法朝向解释。
- 命中 command 后，由活动状态的转换边决定能否发动，不从 match_found 直接 goto。
- 下→上与普通跳跃同次输入的归属需明确，不能既发动特殊技又凭空跳起。
- 组合技取消为特殊技仍由 Matcher 识别，再按当前段合法窗口提交；成功离组清未执行组合后缀。
- 独立特殊技多数一个同根 FrayState 即可，只有真正多步骤／共享事务才再建专用组。

## 6. 投掷：grab 和 throw_attack 分离

根中允许投掷的状态经命令和条件进入 throw_forward，start_state=grab。

- grab 的窗口负责尝试抓取；战斗层确认具体目标、可投状态、距离、冲突、拆投等事实。
- 真正 captured 才进入投掷专属 throw_attack；未确认不得因为 grab 完成就自动攻击。
- 窗口结束未抓到走 whiff_recovery；需要拆投／中断时另外配置 break_recovery 或明确父组出口。
- throw_attack／恢复完整结束且目标事务允许清理后，由根出口条件离开投掷组，不强制 done。父组负责本次目标的绑定与释放，叶子负责阶段动作，不把目标写进共享 Attribute。
- 被投角色使用自己的状态机。双人位置、受投状态、伤害／释放和目标失效须协议同步，CompoundState 仅提供流程结构。

## 7. 数据、装配与属性

- Move：装备身份、固定 command、只读状态依赖与已有公共条件；不存攻击帧数，不把运行实例塞进共享资源。
- State：执行脚本／动画／判定配置。当前直接叶子用全局唯一名字；未来子组内部使用 owner 局部名字，组定义／scope 尚未实现。
- Transition：直接 owner 的 from／to、接受的 command、条件、switch_mode、priority；跨组通过父层兄弟组边进入 start，而非任意叶子深路径跳转。
- FighterHitboxAttribute：框类型和只读帧窗口。状态从 context Manager 获取本姿态，保存自己 elapsed_frames；中断即时清框。

## 8. 后续实施顺序与验收

1. 保持现有扁平基础行为回归，先迁移方向＋攻击的组合注册与真实攻击事件触发。
2. 加最小路线组 A→combo(start=B)，根按当前 B/C/D 完整恢复且无合法后续返回 idle；测试 A／AB／ABC／ABCD 四个前缀结果、合法取消和重入，不强制 done。
3. 明确组资源／边 scope、Fighter 活动叶子权限与完成查询，再接 Builder；当前 flat Builder 不具备这些能力。
4. 再增加本次路线有限预输入协议；没有它时不声称已实现完整 MK 拨入体验。
5. 建投掷组，先测试捕获／失败分支，再接目标判定、对方受投和双方中断清理。
6. 条件按实际 owner 注册：组内边本地绑定，根出口在根绑定、读取组事实。当前不使用或研究根条件继承，也不为此修改插件。

验收包括：方向可以先按住、攻击新 press 才触发；A→组只进入 B 不重播 A；输入早晚不加速段动画；C 未完成不可退组；没抓到不进 throw_attack；中断不漏框／目标；单一 Matcher、原生 advancer 语义保持。

## 11. 同一 combo1 的 A／AB／ABC／ABCD 条目

A 是根 light_attack；combo1 包含普通 FrayState B/C/D，start_state=B。只输 A、到 B 停、到 C 停、到 D 停是四个可展示结果（AB／ABC／ABCD 本身只有三条，第四条是 A）。

可以分别登记四个展示／解锁条目，但共享一份动作链，不为每条前缀复制状态或注册整串特殊技 Matcher。推荐路线族＋前缀闭包：允许 ABCD 就能自然打出 A／AB／ABC，不强迫玩家必须接完；只装 AB 则不开放 B→C，即使 C 已因其他内容装配也不可误接。

现有 Move.state 只表达单一执行入口与组装配，还不足以表达所有路线连接授权，不能仅靠端点存在自动开全串。路线条目、连接授权、局部 pending 属于后续数据协议，详见[组合技路线条目与多出口设计方案](../方案/组合技路线条目与多出口设计方案.md)。

招式表有多个名字不等于商业游戏内部必须有多个状态机；本方案依据本项目需求设计，不声称已核实 MK 的源代码资源模型。
