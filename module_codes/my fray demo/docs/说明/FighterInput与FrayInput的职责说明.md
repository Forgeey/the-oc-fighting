# 为什么保留 FighterInput：与 FrayInput 的职责划分

> 2026-11-11 当前职责：FighterInput 负责设备接线、规范方向、指令识别与入队前来源裁决；执行队列只有原生 FrayBufferedInputAdvancer，不维护失败重试候选。首轮已删除未用接口和初始化兜底；清历史通过公开 Matcher.clear_history，不新建 Matcher。旧候选队列与重建描述仅作历史，当前事实见[FighterInput 首轮精简](FighterInput首轮精简与历史清理.md)。

> **2026-11-10 最新组织目标：**多数动作仍同根；无方向单键、方向＋攻击组合、MK 风格顺序／取消组合技、快速序列特殊技分开。方向＋攻击按复合输入注册；组合技后续／投掷用真正局部流程 CompoundState，不按分类机械建组。当前运行代码尚未装配这些组，旧的全部扁平永久限制／分类多层骨架／不做投技描述均以[角色动作与复合状态组织方案](../方案/角色动作与复合状态组织方案.md)为准。本轮仅整理文档和审查插件，未回退源码。

> **2026-11-10 运行状态已扁平化：**分类不再生成运行分组；当前使用 selected_state_names／entry_state 和 idle、light_attack 等直接名称，删除 group_start_states。根直接使用 FrayCompoundState，命令／普通边由 Fray 原生执行。以下旧层级、旧路径及跨层桥接描述仅作历史；最新接口与迁移范围见[扁平状态机迁移说明](扁平状态机迁移说明.md)。

> **2026-11-09 单 Matcher 已实施：**每角色仅一个 FraySequenceMatcher，由 Fighter 构建时调用 FighterInput.configure 配置并存于 FighterInput.matcher。三个指令辅助函数已合并为 create_branch(facing)，旧的兼容域分组已移除；前后条件输入转向不重注册，世界历史和完成朝向规则保留。旧描述以[单角色单 Matcher 接入记录](单角色单Matcher接入记录.md)为准。本轮不新增节点、不改插件、不添加配置兜底。

> **2026-11-08 最新命令协议：**已恢复原版 FrayStateMachine 节点；command_id／转换 command 独立于 move_id，同一命令可触发多条条件边。Fighter 不再按 move 分派或传入 move 参数；跨层边由根 Resource 接线。旧协议仅作历史记录；当前事实及通过 context Manager 获取 Attribute 的边界见[命令驱动转换与攻击配置获取](命令驱动转换与攻击配置获取.md)。

> **2026-11-07 输入接线已迁移：**当前事实以[输入系统方案实施记录](输入系统方案实施记录.md)为准。已接入原版 FrayBufferedInputAdvancer；移除 get_candidates／consume 和每招 buffer_frames；世界方向序列按终结时朝向判定；set_facing 在帧末按状态权限提交。以下旧版接口、候选失败保留及转向重建等内容保留为历史对照，不再是当前输入调用协议。

> 修订日期：2026-11-06。依据 `module_codes/my fray demo` 当前源码说明。本文解释现有分层，不新增输入系统、状态脚本、双人绑定或网络功能。

## 1. 先说结论：可以直接用 FrayInput，但不能同时省掉游戏规则

**不是 FrayInput 不够用，也不是必须给每个插件包一层。** 如果游戏只是“按住右键向右走，按一下按钮触发固定动作”，角色或状态脚本直接使用 FrayController / FrayInput 就可以，未必需要 FighterInput。

本项目已经超出这个范围：所有角色可以自定义装备招式，前后方向相对角色朝向，存在指令识别、组合窗口、候选缓冲，以及同一次按键在不同招式之间的归属与消费规则。

因此，当前 FighterInput 不是简单的 `is_pressed()` 转发器，而是：

> **每个角色自己的输入解释器：把 Fray 输入事实转换为移动意图和逻辑命令，先裁决来源，再交给原生 advancer 缓冲和执行。**

删除文件本身很容易，但这些规则仍需放在 Fighter、各状态、另一个模块或插件里。只有明确不再需要相应规则时，才能真正删除对应逻辑。

## 2. 先区分 Fray 提供的不同组件

不能把整个 Fray 输入系统都等同于 FrayInput 单例，也不能把 FighterInput 的全部职责都归给 FrayController。

| 组件 | 已有职责 | 不应默认由它掌握的本项目规则 |
|---|---|---|
| `FrayInputMap` | 登记绑定和复合输入 | 哪些招式被某个角色装备、哪些输入属于某个招式 |
| `FrayInput` | 全局输入管理，维护设备输入状态，提供查询和 `input_detected` 事件 | 当前角色面向哪里、某个候选是否已被角色成功发动 |
| `FrayController` | 角色持有的设备查询入口，带 `device`、`disabled` 等设置 | 本项目的前后移动语义、候选归属、招式装配与发动权限 |
| `FraySequenceMatcher`、复合输入 | 提供序列匹配、组合输入等通用机制 | 本项目规定的普通攻击回退、同源候选消费策略 |
| `FrayInputBuffer` | 通用按键缓冲和输入窗口 | 已装备 MoveDefinition 对应的候选及跨招式来源关系 |
| `FrayBufferedInputAdvancer` | 缓冲输入并尝试推进 Fray 状态机 | 自动遵守本项目按 move_id、输入来源和装备集合定义的整套规则 |
| `FighterInput` | 使用上述机制，解释角色输入、识别已装备指令、管理候选 | 决定伤害、执行运动、装配状态、绕过转换权限 |
| `Fighter` 与状态机 | 判断能否发动候选、执行转换、成功后通知消费 | 重复维护一套底层输入采样与匹配历史 |

**Fray 已经有匹配和缓冲能力。保留 FighterInput 的理由是游戏语义与现有数据协议，而不是“插件完全没有这些功能”。** 当前序列识别也确实在复用 FraySequenceMatcher，并没有另写一套底层序列匹配器。

## 3. 当前实际数据流

```text
物理输入 / Godot Action
          ↓
FrayInputMap + FrayInput
          ├─ 状态查询 → 当前角色的 FrayController
          └─ input_detected 事件
                         ↓
                   FighterInput
          ├─ 输入快照、角色相对方向
          ├─ 基础移动意图
          ├─ 已装备指令的匹配
          └─ 招式候选、期限、来源归属
                         ↓
             Fighter.advance_commands()
          ├─ 检查活动来源、条件、完成模式
          ├─ 成功：转换并 consume(candidate)
          └─ 未成功：不消费，候选按自己的期限保留
                         ↓
              状态脚本 / FighterMovement
              执行动作与实际物理运动
```

FighterInput 同时读取 Controller 的轴快照、收集 Fray 的输入事件，而不是用自己的采样完全替代 FrayInput。

当前代码将 FrayInput、FighterInput、Fighter 的物理处理优先级分别设置为 `-100`、`-50`、`50`，确保输入先产生、解释后供角色决策使用。实际物理帧还包含状态机等节点的更新，不是只运行图中的三个对象。

## 4. 为什么前进、后退等不能只看全局按键

### 4.1 相同输入，在不同角色身上可能有不同含义

例如世界水平轴为 `+1`：

| 角色朝向 | 本游戏解释 |
|---|---|
| 朝右 `+1` | 前进 |
| 朝左 `-1` | 后退 |

FrayInput 可以告诉调用者右方向是否按住，但“这是前进还是后退”必须结合角色朝向。

另外，当前游戏规定：下蹲意图优先于前走、后走。角色按住下蹲和水平方向时，不能同时让前走条件与下蹲条件成立，造成状态切换抖动。

这些是本游戏的解释规则，不是所有游戏的底层输入规则。集中在 FighterInput 后，条件和状态不需要各自复制朝向、下蹲优先级等判断。

### 4.2 为什么现在使用通用查询

当前公开查询为：

```gdscript
fighter_input.has_intent(&"fwalk")
fighter_input.has_intent(&"bwalk")
fighter_input.has_intent(&"crouch")
fighter_input.get_movement_axis(&"fwalk")
```

`get_movement_intent()` 是当前基础移动意图的统一解释位置，返回 `idle / fwalk / bwalk / crouch`。`has_intent()` 查询它，`get_movement_axis()` 按指定意图返回世界水平轴，下蹲不提交水平移动。

Builder 将 `inputed_fwalk` 等条件键通用绑定到 `has_intent(&"fwalk")`。因此不再需要为每个条件创建 Input 方法、Fighter 转发方法和同名映射项；否定仍使用 `!inputed_fwalk`。

这里简化的是接口接线。**并不表示只写一个 `inputed_jump` 字符串，就已经实现跳跃输入或跳跃动作。** 新的输入识别规则仍需实现；未来若需要多个并存意图，也可以调整内部表示，不必恢复“一意图一转发函数”。

## 5. FighterInput 当前实际增加了哪些能力

### 5.1 按当前装备配置识别，而不是每个状态自己检查按键

`configure(controller, moves)` 接收当前角色的 Controller 和已解析的招式集合，然后建立相应匹配器、组合输入关联及候选识别。

这意味着：

- 同一逻辑按钮可以由不同自定义角色的装备解释为不同招式。
- 招式资源保持与 P1/P2 等玩家身份无关。
- 状态脚本不必知道每个招式的完整方向序列、按钮和窗口参数。

代码中遍历 `_moves` 是为了**运行时识别已装备的指令**，不是在现场检测两招是否冲突。未来选招阶段的冲突表、解锁树，不能取代战斗中的指令识别。

### 5.2 方向清洗与已有 Fray 匹配器的接入

当前实现先读取同一帧方向轴，再根据朝向构造九宫格方向事件，送给 FraySequenceMatcher。按钮事件也进入相应识别流程。

因此不必让每个招式各自解释世界左右或处理方向别名。当前代码在朝向改变时会重建序列匹配器并更新方向基准，这是“丢弃跨朝向半条指令”的游戏清理策略，不是镜像要求。FraySequenceMatcher 本身不读取角色朝向；上游继续提供相同相对方向名称时可复用实例。一个 matcher 能容纳多个命名序列，当前每招一个只是接线方式；后续按[输入系统设计方案第 5、9 节](../方案/输入系统设计方案.md)明确输入域、实例复用与清理时机。

这不等于朝向改变时清空所有输入：当前代码重置的是序列匹配历史和方向基准，不能把它描述为删除全部已有候选。

**2026-11-06 计划修订：**上段仍是当前运行代码事实，不是新目标。对 MK 未找到普通半条 motion 跨转向的明确通用规则；依据 Skullgirls 开发者的一手说明，目标改为保留世界方向历史、按终结事件时朝向判断整条指令，普通转向不再重建 matcher。只有失焦、换设备、重配等失效事件清历史；已完成候选／advancer 条目也不因普通转向清空。来源与接线约束见计划第 5.3、9 节。本轮仅修改文档，代码尚未迁移。

### 5.3 单键等待、组合窗口与候选有效期

FighterCommandDefinition 提供 `resolve_delay_frames`、`combination_window_frames`、`buffer_frames` 等参数。

FighterInput 将其解释为候选的 `created_frame`、`ready_frame`、`expires_frame`，并检查组合按钮的按下时间差。单键等待期可以为组合输入留出确认机会，超过期限的候选被移除。

这类“输入已经识别，但暂时不允许提交或还在等待”的状态，不等同于一个 `is_just_pressed()` 布尔值。

### 5.4 同一次按键在不同招式之间的归属

例如普通攻击和“方向序列 + 同一个攻击按钮”共享了最后一次按键。

只分别调用按键查询和序列查询，可能同时得到两个成立结果。本游戏还需要决定这次按键应该归谁，而不是由两个状态分别响应。

当前 FighterInput 为按键周期记录来源 ID，并维护：

- `_special_ids`：已经确认属于特殊指令的来源。
- `_consumed_ids`：已经成功发动并消费的来源。
- 候选的 `source_ids`：该候选使用哪些来源。

特殊指令确认后，会撤销缓冲中重叠的普通单键候选。当前规则还规定：特殊候选过期或暂时不能执行，也不因此回退为同源普通攻击。

这是一个明确的游戏策略，并非所有格斗游戏都必须如此；若以后改变回退规则，应修改这一处策略，而不是改 Fray 的原始按键事实。

### 5.5 成功才消费，失败可以继续等窗口

FighterInput 生成“请求尝试某招”的候选，Fighter 决定它现在能否发动。

- 条件不满足：Fighter 不调用 `consume()`，候选可继续等待，直到过期。
- 发动成功：消费该候选及与它共享按键来源的候选，并重置相应匹配历史。

例如，提前输入下一招时，它可以在剩余有效期内等待合法状态，而不是因为当帧不满足条件就一定丢失。

FrayBufferedInputAdvancer 的当前 `_advance()` 实现会先从队列取出输入，再尝试推进，未成功项不会在该方法中自动放回队列。因此不能不比较语义就用它直接替换当前候选队列。这不是说它不能扩展，而是扩展后仍需承载同样的业务规则。

### 5.6 每角色的历史与生命周期清理

即使只有两个自定义角色，也仍需分别保存朝向、匹配器、候选和消费记录。共享全局输入管理器，不等于这些运行历史也应全局共享。

当前会在设备切换、禁用/断开和应用失去/恢复焦点等情况下清理历史，避免旧指令在恢复后误触发。

## 6. 为什么“识别招式”和“允许发动招式”分开

**识别到指令，不等于获得转换权限。**

FighterInput 不应因为识别到攻击按钮，就直接 `goto()` 攻击状态。当前 Fighter 仍检查：

- 规则对应的招式是否匹配；
- 规则来源是否为活动状态；
- 招式与转换的前置/推进条件；
- `AT_END` 等完成要求。

因此，输入层只负责提出请求，不负责执行运动、决定伤害或放开取消权限。

同理，它也不负责状态 ID 查库、招式解锁和选招冲突检测。这些职责分别属于装配、内容/选招和战斗决策层，不能因为都与“招式”有关就堆进输入节点。

## 7. 为什么不直接把这些规则放进 FrayController 或各个状态

| 放置方案 | 可以做到什么 | 主要代价 |
|---|---|---|
| 各状态直接使用 FrayInput | 简单固定输入可直接驱动状态 | 面向解释、窗口、消费等容易散落或重复；输入历史容易被状态生命周期切断 |
| 全部放进 Fighter | 能承载同样功能 | 角色协调代码与输入细节混在一起，测试和修改范围扩大 |
| 写入 FrayController/插件 | 技术上可以扩展 | 通用设备组件混入本游戏装备与候选规则，增加插件维护负担 |
| 保留 FighterInput | 每角色集中解释，向外提供稳定查询/候选接口 | 多一个节点及其运行状态，需要明确边界并维护测试 |

当前选择最后一种，不代表其他方案永远错误。关键不是文件数量，而是规则归属是否清晰。

## 8. 这层包装没有自动解决的事情

### 8.1 不是完整的双人设备隔离

当前 FrayController 只有 `device`、`disabled` 等设置，没有原生 `prefix` 字段。demo 使用的 FrayInputBindAction 忽略传入的 `_device`，实际调用的是 Godot 全局 Action 查询。

所以不能声称“有 FighterInput”或“分别设置 Controller.device”，就已经让当前 Action 绑定获得完整的双人隔离。

若未来采用 `p1_/p2_`，还需配套注册、物理绑定、读取、组合输入命名及事件过滤/还原。业务适配层是承接这种差异的合理位置，但本轮尚未实现；共享招式仍应使用无玩家前缀的逻辑指令名。

### 8.2 不是装备冲突检测或反作弊

候选仲裁解决“当前这次输入归谁”，不等于验证“这两个招式是否允许同时装备”。输入层也不能证明客户端内容可信。

### 8.3 不是已经完成的回放、回滚或 AI 输入协议

分层可以让未来替换输入来源更容易，但当前并没有公开的确定性回放/回滚协议。序列时序使用毫秒，候选窗口使用逻辑帧，不能据此直接宣称已经具备确定性网络输入。

未来使用 Fray 虚拟设备或其他来源时，也仍要定义候选来源、时序和消费规则。

## 9. 怎样避免 FighterInput 自身变成多余包装

保留这层的同时，应遵守以下限制：

1. **不恢复“一按钮一转发函数”。** 通用查询与稳定接口足够时，不再逐个复制 Fray 的所有方法。
2. **继续复用 Fray 的匹配、绑定和设备能力。** 不因存在业务层就另造一套相同的底层机制。
3. **不把运动和战斗决策搬进输入层。** 输入报告意图，状态和物理模块执行动作。
4. **不提前堆未来功能。** 没实现的双人前缀、冲突表、解锁树不当作现成功能描述。
5. **真正变复杂后再拆内部模块。** 必要时可分离快照、指令解析、候选缓冲，但先保留清晰的外部接口，不现在新增一组空管理器。

减少插件输入 API 的直接散落可以降低输入接线的修改范围，但不代表整个项目已与 Fray 完全解耦：状态机、判定等模块仍然使用 Fray 的类型和接口。

## 10. 什么时候可以删除 FighterInput

以下情况可以考虑不用这一层：

- 仅有少量固定按钮行为，直接查询即可。
- 不需要装备驱动的指令配置、相对方向解释、候选缓冲及来源消费等规则。
- 或者已将这些职责完整迁移到另一个明确模块/插件扩展，并验证行为等价。

不应采用“删除 FighterInput，但让每个状态各写一遍现有规则”的方式减少文件数。

对当前项目，建议保留该层，继续简化它的公开接口。若将来实际只剩一两个无业务含义的转发方法，再评估是否合并，而不是仅因为 FrayInput 已存在就删除它。
