# 状态、招式、输入指令与判定资源关系说明

> 记录日期：2026-10-25；本次修订：组合技输入接收／路线缓冲与规定衔接帧分离，保持每段独立状态。
>
> 性质：基于当前 Demo 源码的架构讨论与设计约定，不是已完成的功能清单。本文不新增实现，也不表示已运行验证。
>
> 配套阅读：[招式设计计划](../计划/招式设计计划.md)、[招式参与角色构建方案](../方案/招式参与角色构建方案.md)、[判定系统动态装配方案](../方案/判定系统动态装配方案.md)。本次只更新文档，不代表输入／取消与判定业务已经实现。
>
> 本次撤销“窗口内按键合法就立刻转换、不做预输入”的默认规则。现在是每段一个状态，窗口内先记录有界接续，到规定衔接帧才重新校验并转换；允许 A 执行期间连续预输入 M、H。依据与来源见招式设计计划第 12 节，具体队列／帧数是本项目设计，非 MK 源码断言。

## 1. 总体结论

四个概念分别回答不同问题：

| 概念 | 回答的问题 | 不负责什么 |
| --- | --- | --- |
| 输入指令 Command | 玩家做了什么输入，是否形成发动候选或本次合法按键接续请求？ | 不直接切换状态、不决定受击结果、不创建判定节点 |
| 招式 Move | 玩家装备、请求执行的是哪一个完整动作？入口、依赖和发动规则是什么？ | 不充当每帧更新的状态实例、不保存本次执行进度 |
| 行为状态 State | 角色此刻正在做什么，允许什么行为，如何更新与退出？ | 不重新识别一套输入、不独立结算每个碰撞回调 |
| 判定姿态 HitState | 当前身体和攻击范围是什么，由哪些框组成，哪些框启用？ | 不等同于行为状态、不负责完整战斗结果或角色推开算法 |

**推荐关系：基础攻击声明固定按钮；组合技声明起手依赖、后续状态、输入窗口、按键连接和规定衔接帧；特殊技声明 Fray matcher 指令。Loadout 从 MoveLibrary 选择招式并决定装配内容（目标接线见[构建修改计划](../方案/招式参与角色构建方案.md)）；局部接续缓冲记录输入路线，当前段到期才请求合法状态转换，战斗层统一结算。**

招式定义、状态定义与执行脚本不是同一个对象。建议每招有独立完整路径和独立状态实例，但同一执行协议的多条路径可以引用同一个脚本类；各招的帧数和数值由只读 Move 配置提供，动画标识统一由 StateDefinition.animation_key 提供；将来角色外观解析动画标识，当前只预留原样返回的解析入口。逻辑帧统一驱动战斗时序与显示映射。外观不自动改变战斗判定。判定几何暂不接入，本阶段只在招式或状态定义上预留引用位置；未来仍由单个 HitState Manager 管理包含 Push/Hurt/Attack 的完整姿态。详见[疑难解答第 2.1 节](招式装配与判定时序疑难解答.md#21-执行脚本动作配置与角色外观如何解耦)。
依赖装配和运行控制是两件事：

- 装配依赖顺序是 `Loadout → Move / StateDefinition → HitStateDefinition → PackedScene`（后续接入；当前不实现）。
- 运行控制顺序是 `输入 → 候选 → 发动检查 → 行为状态 → 判定启停 → 接触 → 统一结算`。

不要因为输入最终能引发攻击，就把这些职责全部写进输入脚本；也不要因为判定姿态随行为变化，就把两种状态树合并成一棵树。

## 2. 现状、已确定方向与尚未实现内容

### 2.1 当前代码已经具备的关系

| 对象 | 当前字段／行为 |
| --- | --- |
| `FighterCommandDefinition` | SINGLE／COMBINATION／SEQUENCE；Fray matcher 支持方向终结，demo 候选接入、方向快照及组合技按键边仍需补齐 |
| `FighterMoveDefinition` | `move_id`、`command`、`entry_path`、`states`、`transitions`、`allowed_from_paths`、`prereqs`、`switch_mode` |
| `FighterStateDefinition` | `state_name`、`group_path`、`state_script`；尚无判定引用 |
| `FighterLoadout` | 选择基础状态完整路径及 `selected_moves`，引用公共状态库和转换库 |
| `FighterSMBuilder` | 合并所选状态与招式依赖，创建状态实例，按可用端点筛选普通转换 |
| `FighterInput` | 为已装备招式识别指令，保存带来源标识和有效期的候选 |
| `Fighter.advance_commands()` | 逐个尝试就绪候选，成功消费；没有候选成功则执行一次普通状态推进 |
| `FrayHitStateManager2D` | 角色场景已持有唯一管理器，尚未按动态判定方案接入资源依赖 |

现有 neutral 已有 idle、fwalk、bwalk、crouch 脚本与资源。较早文档中“只有 idle/fwalk”“没有下蹲”的描述属于历史记录，不作为本次设计的现状依据；存在这些代码也不等于已经验证判定或完整战斗功能。

### 2.2 已确定、待实现的方向

- 三类统一为 basic_attack（基础攻击）、composite_attack（组合技，TC 仅作术语对照）、special_attack（特殊技）。不另设 tc 类型。
- 基础轻／中／重保持固定输入；特殊技不因替换轻中重按钮自动产生数值版本。
- 下→上只用于特殊技，使用现有 FraySequenceMatcher.read() 识别方向事件，无需重写 matcher；需要修补的是匹配后的候选来源／一次消费接线。
- L 当下发动 A，M／H 可在合法接收区间先录入本次组合技的有界后缀；A、B 分别到各自规定衔接帧才执行 A→B、B→C，不在按键到达时切换。
- 每段仍是独立叶子，三阶段内部处理；实际执行进度与提前接受的输入路线进度必须分开。无需重播已消费起手，但需要本次路线局部缓冲。
- 输入窗口内新按下只认领并排队，到 commit_frame 再复核／执行；支持多步预输入而非只缓存紧邻一键。窗口关闭后已合法接受的记录可保留到约定衔接点。
- 仅装配已选内容的状态与合法边；同组使用原生输入转换，跨组需统一验证后 external 执行。
- 强化是独立、明确的窗口派生，不自动等同组合技或强度版本；具体输入／资源待定。
- 逻辑帧控制窗口／判定／完成，AnimatedSprite2D 显示，不恢复 AnimationPlayer。
- 判定定义随最终状态集合装配，一角色一个管理器，每姿态完整包含所需框；资源只读，运行数据独立。

FighterHitStateDefinition、FighterHitStateRuntime、FighterBuildPlan 和组合技按键边／分类是目标设计，不是当前已存在字段或类。当前没有攻击／取消完整业务闭环。

## 3. 静态资源图：谁引用谁

    FighterLoadout
    ├─ selected_state_paths → 基础行为定义
    └─ selected_moves
       ├─ basic_attack：固定单键／方向快照输入
       ├─ composite_attack：固定起手依赖与逐条连接
       │  ├─ states → 后续攻击段的 FighterStateDefinition
       │  └─ connections【拟扩展】→ 源、按键、接收时钟／窗口、衔接帧、目标
       └─ special_attack：固定 command → FraySequenceMatcher

    每段 FighterStateDefinition
       ├─ state_script → 执行协议脚本（可按协议复用），内部三阶段
       └─ hit_state_definition【拟新增】→ 判定定义 → PackedScene
           → 本角色 FrayHitState2D → 直接子 FrayHitbox2D／形状／属性

当前通过 MoveLibrary + Move.required_state_paths 表达招式与状态依赖，由 Loadout 选择 Move ID 后统一解析。State 和 Move 不维护转换清单；Builder 从公共转换库按可用端点与已装备 move_id 自动选择规则，转换自身 transition_id 保留。新增按键／跨组路由可扩展相应业务资源，确切字段见[构建修改计划](../方案/招式参与角色构建方案.md)，不重复维护两套互相覆盖的边。

组合技整串按法可以用于 UI 展示，但不能一面注册成全局 SEQUENCE，另一面又通过当前状态的按键边启动同一后续段。当前 configure() 默认每个 selected_moves 都有 command，需显式区分组合技装备与主发动识别；不把 command 留空当作已经支持。

基础攻击 A 可作为组合技起手依赖，后续 B、C 随组合技装配，不要求它们各有独立可装备 Move 或 neutral 发动指令。状态定义不反向持有运行实例，判定不反向决定输入或招式。

entry_path 是行为入口，不是 HitState 路径；move_id 是装备身份，不是行为路径。同一份窗口／数值只保留一个权威来源。

## 4. 各层的数量关系与共享粒度

| 关系 | 约定 |
| --- | --- |
| 基础攻击 → 输入／状态 | 固定按钮或方向快照，一个专用叶子 |
| 组合技装备 → 输入 | 固定起手＋连接按钮，可先录入多个后续键；不以全串 matcher 重播第一拳 |
| 每次组合技 → pending | 每角色有限路线缓冲，区分已接受输入与真实执行段 |
| 每条连接 → 两段时序 | 输入接收区间与实际源局部 commit_frame 分开，不因按键早晚加速动作 |
| 组合技装备 → 状态 | 后续每段一个攻击叶子，可有分支；不复制已经执行的起手 |
| 一段状态 → 阶段 | 起手／有效／恢复内部推进，不再拆三份叶子 |
| 特殊技 → 指令 | 固定 Fray matcher 序列，可用下上方向终结 |
| 状态 → 判定定义 | 首版每段一个完整姿态，不强制多姿态集合 |
| 多个状态 → 判定定义 | 相同布局可共享只读定义，各自应用正确掩码 |
| 判定定义 → 实例 | 角色内去重，角色间分别创建 |
| 一姿态 → 框 | 完整 Hurt／Push，按需 Attack，各类别可有多个框 |

组合技多个攻击状态与“单段三阶段在一个状态”没有矛盾。只有执行语义、后续权限也一致时才共享攻击状态；动画相同但合法后续不同，应使用不同路径，避免来源权限丢失。

### 4.1 不把多矩形误认为多攻击段

两个攻击矩形只是同一段攻击的组合范围，三个人体受击矩形只是同一个角色的受击轮廓。它们不自动产生两次或六次伤害。

真正的多段攻击由攻击段身份和时序表达，不能通过“每个矩形各自算一击”实现。

## 5. 输入：物理键、逻辑动作、指令、候选分开

### 5.1 四层输入含义

```text
物理键／手柄
  ↓ 项目 Input Map
逻辑动作（move_left、light_attack 等）
  ↓ Fray 注册与每角色采样
基础／特殊技固定发动指令，或组合技接收窗口内的后缀预输入
  ↓ 匹配
某个招式的候选请求（move、来源、创建帧、就绪帧、过期帧）
```

- 改键改变物理键到逻辑动作的映射，不改变招式指令。
- `light_attack` 是按钮语义，不等于已经选择“站立轻拳”。
- 数字方向是相对面向，不直接等于世界左右。
- `move_down` 是方向信息，`crouch` 是行为意图；默认可以同键，但不能把别名事件重复当作方向步骤。
- 缓冲、消费标记、匹配进度属于角色输入运行时，不写回 FighterCommandDefinition。
- 方向＋按钮基础技建议在攻击按下时读方向快照，允许先持有方向，不等同方向序列或必须同帧按下两个键；当前尚缺少相应规则。
- 下→上只用于特殊技，matcher 可以识别；游戏侧还需补来源标识和与跳跃的竞争，不能伪造攻击确认键。

### 5.2 连续意图不是所有都要包装成招式

idle、前进、后退、下蹲当前通过普通条件转换执行：

```text
采样轴／按钮状态 → inputed_* 条件 → 普通转换
```

它们不必为了统一资源外观而伪装成每帧生成、消费的 Move 候选。招式候选主要处理离散动作请求；连续意图与离散请求共用采样基础，但不强行共用消费语义。

### 5.3 指令识别成功不代表可发动

`FighterInput` 负责识别已装备招式的指令。`Fighter` 在尝试发动时再检查：

1. 当前活动状态或父组是否匹配 `allowed_from_paths`。
2. `prereqs` 是否满足。
3. `switch_mode` 的完成条件是否满足。
4. 执行行为转换是否成功。

只有成功发动才调用消费。失败候选保留至原期限，不刷新创建时间，也不因每帧重试而重复扣资源。

当前候选直接指向 FighterMoveDefinition，这与固定指令和装备约定一致，不增加独立 CommandLibrary。但未来窗口内取消／强化须同时检查源权限与目标规则，不能只靠这四步已有检查。composite_attack 接续使用已装配的源→目标状态边，不能把下一段当作无条件 goto 或重新执行整条组合技入口。

### 5.4 保留现有特殊指令归属规则

当前规则是：

- 序列确认先于同源普通单键候选生成。
- 普通单键可以短暂等待组合键确认。
- 组合确认后移除共享来源的普通候选。
- 同一个按键周期已归属于特殊指令，即使暂不能发动或到期，也不回退普通攻击。
- 成功消费会移除使用相同来源标识的其他候选。

不要把“尝试失败保留”解释为“特殊技不能用时自动出普通拳”。上述规则描述当前按钮终结的候选模型，不代表 composite_attack 按键边或纯方向特殊技的候选接入已实现。

### 5.5 组合技预输入：接收不等于马上转状态

L 发动 A 后，合法窗口里的 M、H 可按顺序转换为本次路线的待执行记录。M 对应 A→B，随后 H 对应 B→C，即使 B 尚未进入；有界输入路线游标只允许沿已装配路线延长，不能凭 H 跳过缺少的 M。

提前输入 H 的时限用显式组合技起手时钟或当前实际段的接收区间，不假装 B 已有局部执行帧。实际 B→C 到 B 进入后才按 B 自己的 commit_frame 执行。仅支持 B 开始后才能接收 H 的单步缓存不等同本项目要的完整拨入体验。

接收时认领／移出原输入，防普通攻击和其他路线重复使用；到规定衔接点才弹出 pending、复核并实际转换。正常 A→B 保留未执行后缀，受击／特殊技取消／整条结束清掉；不能每个旧状态 exit 都清空，也不能无限保留回灌普通输入。

当前 FighterInput.consume() 会重置全局序列 matcher。不要依赖其历史恢复本串，也不要把通用 candidate.buffer_frames 当固定串缓冲期限；应在同一个输入／动作调度中明确转接到本路线专用 pending，不另建全局万能指令系统。

FrayInputTransitionPress 可以在到期时接收带原事件身份的已缓冲按钮数据；采样瞬间不调用 advance()。原按下的接收窗口与当前提交点分别校验，不能要求执行时物理按钮再次按下或输入窗口仍打开。

### 5.6 方向特殊技复用插件 matcher，候选接线待补

FraySequenceBranch.then(StringName) 与 FraySequenceMatcher.read(FrayInputEvent) 不限制终结为攻击按钮，dir_2→dir_8 可作为特殊技。

Demo 已经合成方向事件；_feed_direction() 传空 source_ids，而 _add_candidate() 拒绝空数组，所以是匹配之后无法进入候选链，不是 Fray matcher 识别不了下上。后续加方向终结来源／一次消费标识，保留现有 matcher。

下上与普通跳跃在离散执行前仲裁，持续按上不重复发动，不重复投递 jump／crouch 别名。此能力仅用于 special_attack，不移用成组合技全串输入方案。

## 6. 招式：装备单元，不是状态实例

一个 `FighterMoveDefinition` 应表达：

- 招式身份和固定指令。
- 初始行为入口。
- 需要的状态路径；普通转换与发动规则在公共转换库配置，按端点自动选择。
- 允许从哪些行为发动、有哪些发动前置条件。
- 后续拟增加的类型、组合技固定连接、各段配置及取消／强化窗口；不误说成当前字段，不默认要求通用内部段图。

它不保存：

- 当前已经播放到第几帧。
- 本次攻击打中过谁。
- 当前 Fighter 或判定节点引用。
- 是否已经消费本次输入、是否已经支付本次资源。

### 6.1 没有玩家指令的状态不必变成招式

受击、倒地、起身等状态可以由战斗结果触发，不要求给每个状态配一个玩家输入定义。当前资源接口也允许用空的 `allowed_from_paths` 表达某招式不接受玩家直接输入；不等于现有输入配置已经支持把 `command` 留空。

攻击结束返回 idle 是行为转换，不需要伪造一条“idle 指令”。AI、投射物等额外入口如果以后引入，应复用明确的动作执行接口，而不是伪造物理按键，也不是无条件绕过发动规则。

### 6.2 发动与组合技按键转换

| 请求 | 识别和准入 | 执行 |
| --- | --- | --- |
| 基础主发动 | 固定按钮／方向快照、姿态与资源条件 | 进入基础攻击叶子 |
| 组合技接续接收 | 接收窗口内新键、沿合法输入路线、静态装备条件 | 认领事件，追加有限 pending，不换状态 |
| 组合技接续执行 | 实际源到规定衔接帧、有匹配队首、动态条件仍合法 | 弹出对应 pending，退出当前攻击并进入下一段 |
| 特殊主发动／取消 | Fray matcher 匹配固定指令，再检查中立或源取消权限 | 进入特殊技叶子 |
| 强化 | 固定派生输入及强化窗口／资源，输入仍待定 | 就地变化、追加效果或明确独立动作转换 |

组合技段本来就是独立叶子，其同组连接可以成为原生 Fray 按键转换；不是上一版“所有段连接均不属于状态转换”的内部执行图。只是窗口和未装配权限不能被省略。

同组端点必须为直接子状态；跨 basic_attack／composite_attack／special_attack 的路线由统一入口先检查合法业务边再 external 转移，不能把完整深路径填入同组普通端点，也不能直接 goto 绕过条件。

正常完成用 AT_END 等待恢复。组合技由业务层到 commit_frame 才提交转换，IMMEDIATE 仅表示此时不再等源 done，不是收到按键就执行。需同时验证原输入接受记录、当前实际源／规定帧和动态条件；输入窗口此时可能已经关闭。当前 auto_advance=false 不检查 advance_conditions，必要提交条件放 prereqs 或等价每次检查。

不得把组合技全串 SEQUENCE 与按键转换并联处理同一事件。

## 7. 行为状态：执行单元与资源身份

### 7.1 一个招式是否拆阶段，按控制规则决定

普通攻击可以只用一个行为叶子，在动作时序中开关攻击框。只有阶段之间确实有不同控制规则、移动逻辑、取消权限或独立入口时，才拆成多个状态。

“动画有三段”或“有三个不同掩码”不是创建三个行为状态的理由。composite_attack 每段一个专用叶子，接收窗口先记录后缀，衔接点管理实际段间转换；每段内部三阶段，已执行基础攻击不重播，后缀输入也不令源段提前消失。

### 7.2 独立招式叶子与可复用执行脚本

```text
action/basic_attack/punch → PunchState
action/basic_attack/kick → KickState
action/special_attack/fireball → FireballState
```

每招默认保留独立状态定义与完整路径，不统一塞进一个通用 Attack 叶子。若执行协议相同，不同路径可以引用同一脚本类，Builder 为每条路径创建独立状态实例；帧数和数值由只读 Move 配置提供，动画语义由各自的 StateDefinition.animation_key 提供。协议不同的动作使用专用脚本或机制组件。

脚本复用不会派生轻中重强度，也不等于多个招式共享同一个活动叶子。状态实例、动作进度和命中记录不可写回共享资源。详细执行脚本/动作数据/外观边界见[疑难解答第 2.1 节](招式装配与判定时序疑难解答.md#21-执行脚本动作配置与角色外观如何解耦)。

判定定义可在布局与语义相同的状态间显式共享，但不同招式的专属路径不靠同路径覆盖表达差异。

### 7.3 当前同路径合并需要作者约束

当前构建器按完整路径建立定义索引，招式定义会写入同一索引；同路径不同定义可能表现为后写覆盖。它不是一个明确的“装备覆盖优先级”功能。

本方案规定：

- 不同分组的同名状态用完整路径区分。
- 同一个完整路径如果来自多个依赖，应该表示同一份定义或相同语义的明确共享。
- 不同招式需要不同配置时使用不同完整路径，不依赖装备数组先后覆盖。
- 不按脚本文件或局部 `state_name` 去重状态。

当前仍由内容作者保证配置有效，不借此恢复全量装配预检或静默兜底。未来若要诊断冲突，可单独做编辑器／测试工具，不混同于运行时招式判定。

### 7.4 专用叶子仍需明确动作上下文

当前 `_try_move()` 传入 move_id 与 input_frame，但这不表示计时、命中去重和资源结算已经实现。后续须区分装配绑定（状态定义、判定实例、角色模块）与执行数据（本次动作代次、逻辑帧、攻击段、命中记录）。

可复用或专用的状态脚本都不能把当前 Fighter、计时或节点写回共享资源。当前构建器只 `.new()` 叶子，尚未把状态定义与未来的判定引用绑定到运行状态；这仍需显式实现。

普通招式覆盖 `_is_done_processing_impl()`，在恢复结束才报告完成。相同招式合法再发动时重置整次执行，测试当前 external 自转移的退出／重入顺序，不靠覆盖引用或重复 goto 猜测。

## 8. 判定资源：完整姿态，而非攻击框清单

### 8.1 定义与运行节点分开

拟新增 FighterHitStateDefinition 引用完整 FrayHitState2D 场景和默认掩码，FighterHitStateRuntime 为本角色实例化。判定定义的引用归属可预留在 Move 或 State；具体选一个权威位置，避免重复维护。本轮招式参与构建计划不实例化或管理判定节点；后续判定阶段再确定完整姿态与分段绑定，不为组合技预设单叶子多姿态集合。

- `default_active_hitboxes` 表示该定义的默认入口配置，不代表攻击有效窗已经完成设计。
- 同一套布局在动作中改变掩码，不需要反复创建节点。
- 两个状态共享同一判定定义时，不能通过修改共享默认掩码区分各自行为；不同入口启用语义应由明确的状态／动作时序表达，或使用不同定义。
- 判定实例通过资源映射访问，不从 `move_id` 或状态局部名称猜节点路径。

### 8.2 几何配置、攻击配置与结算数据

判定场景保存矩形与节点布局。框属性资源区分 Hurt／Attack／Push，定义检测过滤和调试颜色；按当前指南，攻击属性也可保存伤害、硬直等静态字段。

同一个数值只保留一处权威来源。例如轻拳伤害如果放在 Attack 属性资源里，就不要又在 Move 中维护另一份互不关联的 `damage`。

以后需要把几何与伤害数据分开时，可以让框引用统一攻击定义，但不是现在就同时实现两个互相覆盖的数据系统。近端／尖端有不同伤害时，需要明确候选选择规则，不能按物理回调到达先后决定。

运行时命中记录、实际扣血、受击硬直和击退执行属于战斗运行层，不写进判定场景或共享属性资源。

### 8.3 完整姿态与无敌、防御不是一回事

- 攻击姿态也有自己的受击和推挤布局。
- 防御一般仍保留受击区域，由结算规则决定防御结果，不是简单关闭所有 Hurtbox。
- 无敌、穿身等需要明确改变有效检测范围或结算规则，不隐式改变全部实体碰撞。
- 投技、投射物等专用检测可以以后扩展，不为统一外观强行塞进近身打击框模型。

## 9. 统一装配流程与生命周期

### 9.1 只解析一次最终依赖

```text
读取 FighterLoadout
  ↓
收集 selected_state_paths 对应定义
合并 selected_moves 的 states 与 transitions
  ↓
FighterBuildPlan【拟新增】
  ├─ 最终状态及完整路径
  ├─ 最终转换与原有入口信息
  └─ 所选招式及必要引用
  ↓
  ├─ 为所选招式配置输入识别
  ├─ 为最终状态装配判定依赖
  └─ 为最终状态构建行为树
```

主发动指令不因三阶段重复注册；组合技按每条窗口按钮边配置，不注册成全串 matcher。未装备内容不装配其专属后续状态、连接和判定；依赖资源被加载不代表已经创建运行对象。

### 9.2 判定必须赶在管理器 ready 前装配

依照《判定系统动态装配方案》：先在角色 `_enter_tree()` 解析并挂入所需判定节点，等待子管理器 `_ready()` 接线，再在角色 `_ready()` 初始化 source、输入、移动与状态入口。

这不是要求所有模块都在 `_enter_tree()` 完成初始化；该阶段只做不依赖子节点 ready 的资源解析和节点准备。

当前 Fray 管理器主要在 `_ready()` 建立连接，不能管理器 ready 后直接 `add_child()` 就假定动态注册已完成。

### 9.3 当前装备在战斗内按只读使用

第一阶段只支持按确定的 Loadout 生成角色。热换装必须作为单独能力设计：清理旧动作和候选、注销判定信号及接触、重建运行映射，再进入有效默认状态。不能只替换 `selected_moves` 数组就认为整个角色已重建。

## 10. 当前发动流程与未来控制请求

```text
Fray 采样 → FighterInput 清洗方向与按钮事件
  ↓
按已装备 Move.command 识别
  ↓
保存候选，带来源标识与原始期限
  ↓
唯一推进入口检查当前来源、prereqs、完成条件
  ├─ 失败：保留候选至过期，不消费、不扣费、不创建判定
  └─ 成功：进入 move.entry_path，消费本次来源
             ↓
          建立／绑定本次动作上下文【待实现】
             ↓
          状态使用已装配姿态，动作时序控制有效窗【待实现】
             ↓
          框接触只上报，统一战斗层处理【待实现】
             ↓
          正常结束／合法取消／强制受击
             ↓
          清理旧动作写入和攻击框，进入目标行为
```

上图是当前主发动入口与待实现战斗流程的组合示意。组合技还需独立按键边通道：

    A 接收窗口内收到 M／H
      → 校验固定路线、认领新事件、记录 A→B／B→C
      → A 继续起手、有效、恢复，不立即切换
      → A 到自己的 commit_frame
      → 检查匹配队首、实际源、装备、命中／资源与未中断
      → 只提交 A→B，关闭 A 旧框、B 从自己的第 0 帧开始
      → 保留 B→C，等 B 到自己的规定帧再提交

接收阶段不要求未来段已活动，不应以 get_next_state() 的当前可切换结果否决所有早按；执行阶段才是严格复核真实状态机准入。旧输入窗口关闭不清掉已接受 pending，逾期新输入不录入。

到固定点没有输入或条件失败，首版放弃该边及依赖后缀，继续当前段恢复，不在任意未来帧补出。发生受击／特殊技取消等时整体失效，正常 A→B 则只清掉已执行队首。

当前 Demo 尚无上述接收／缓冲／定点提交业务。保留 MANUAL 唯一安全入口，同帧特殊技、强化、受击、自然完成最多选一个控制结果，不能多个回调分别 goto。

## 11. 身份、两个进度与清理范围

| 数据 | 用途 |
| --- | --- |
| move_id／组合技归属 | 哪个装备条目与固定合法路线 |
| 实际状态／实例／段局部帧 | 当前真正执行到哪里，何时到衔接点 |
| 路线起手逻辑时间＋输入游标 | 后缀输入已经合法接受到哪里；不能用未进入段的局部帧 |
| pending_followups【拟新增】 | 有限的连接、预期前驱、原事件身份、时间／顺序，支持多步预输入 |
| 输入事件认领／已执行状态 | 防重复使用，不把“已认领”误当“已出招” |
| 路线代次与段代次 | 正常接段保留路线，丢弃旧段延迟事件；真正中断时全部后缀失效 |

只用当前攻击状态无法表示“A 还在执行，但玩家已输入到 C”。需要本次动作局部的输入路线记录；这不是恢复已消费 L，也不强制所有段共用一个 Fray 叶子。

每段进入初始化自己的帧／命中身份，正常退出清段内判定与窗口，但剩余路线缓冲由外层生命周期管理，不能所有 exit 无条件清队列。受击／特殊技取消／死亡等清整条缓冲，已认领事件不回灌普通候选。

多矩形同段不重复伤害。持续重叠时新伤害段不保证 Area2D 再发 entered，应按有效窗采样／去重。接触快照保留原段身份，不能结算时读已变化的新状态编号。

## 12. 相似输入、同执行内容与冲突

### 12.1 主指令固定不等于执行内容不能相同

当前每个 Move 仍只有一个主 command。未来不同指令可各自拥有独立 move_id，并显式引用相同只读执行配置／兼容内容；这不要求多个角色共享运行状态，也不自动开放多 command 数组。

若产品以后要求同一 move_id 真正有多个别名，需设计独立绑定身份、去重和仲裁，不在本次悄悄改变现有接口。

### 12.2 共享起手与有限预输入分支

L→M→H 与 L→M→L 若共享执行 A／B，可以沿合法连接录入到 B，再用新 H／L 选择后缀；允许在 A 仍活动时记录分支，按各段规定时点执行，不重播已完成起手。

同一个实际／预期源、同一按键与重叠条件要求不同执行 B 时，需要消除歧义或显式互斥；不能等未来键出现后倒改 B。缓冲有最大长度、顺序、输入截止与失效政策，不是无限排队或任意改已接受路线。

### 12.3 完整指令前缀需局部规则

下→上 与 下→上→L 同时装备时，前者可能先完成。必须为该组合明确等待、上下文互斥或禁止同时装备等策略；不能拿全局“最长优先”让基础攻击或组合技等待整串输入。

方向快照＋按钮与普通按钮重叠也需明确当前方向、装备及回退语义。没有定义的冲突首版可由作者避免，不恢复大而全运行时预检。

### 12.4 同输入上下文分派尚未实现

当前按 selected_moves 顺序确认同源序列，并使用 _special_ids 认领；前一个候选不合法时不会自动退回另一同源招式。地空／组合技段不同上下文复用相同输入，未来必须显式扩展为统一上下文派发，不能靠后写覆盖或重复 command 资源。

不同指令“类似”不等于资源冲突，相同终结 token／共享前缀导致竞争时才按明确策略仲裁。保留当前已认领特殊指令失败不出普通拳的规则，组合技使用有界待执行连接记录，不重用已经消费的基础起手事件。

### 12.5 priority 不能补齐语义

FighterTransitionDefinition.priority 不是当前输入候选评分，也不保证普通自动边必然排序；它不能解决源窗口权限、同源输入归属、特殊技纯方向终结或同帧战斗结果。统一入口应按明确规则决策，不以监听或装备先后作为隐藏玩法。

## 13. 动画、角色适配与时间的边界

### 13.1 动态装配不意味着把所有表现硬绑进招式

通用招式可以引用动画语义，角色提供实际帧图和兼容映射。对于不同体型、骨架或动作轮廓，不能因为招式 ID 一样就默认同一组矩形一定适用。

第一阶段的直接状态判定引用适用于当前 Demo 的内容组织。以后支持多角色适配时，可让角色内容包提供相应状态／判定定义，或在资源解析阶段做显式映射；不在输入层临时决定换哪套身体框。

不要把“可共享资源”解释成“任何角色都可以无条件复用所有几何布局”。

### 13.2 已确定唯一时间源：招式逻辑帧

2026-10-25 定稿：专用招式叶子以固定物理节拍推进逻辑帧，唯一决定阶段、判定掩码、取消窗口、生成时机和正常完成。AnimatedSprite2D 只负责显示，不用 AnimationPlayer 节点或属性／方法轨驱动判定。

- 普通起手／有效／恢复在同一叶子内部，不依据图片帧数拆状态。
- 判定通过装配绑定选择实例，不写死到 Fighter 预建的全部招式节点。
- 退出、中断、取消关闭旧攻击段与窗口，拒绝旧动作的延迟结果。
- 基础移动保留现有 sprite.play()；后续精确攻击显示可从同一进度映射 SpriteFrames。
- 更换素材不改变战斗数值；Hitstop 需显式统一逻辑、显示与输入策略。

此决策替代先前 AnimationPlayer 驱动方案以及“时间源待定”的表述；尚不表示帧数、判定绑定或精确显示同步已实现。

## 14. 三个内容制作示例

### 14.1 基础下蹲

```text
Loadout 选择 neutral/crouch
  → CrouchState 定义
  → crouch 判定定义
  → 装配一套蹲姿矩形

按住 crouch
  → 普通条件转换进入 crouch
  → 选择已装配蹲姿，执行现有停止运动及实体碰撞调整
```

没有独立的 CrouchMove 或“每帧下蹲候选”也能正常表达。

### 14.2 一个单状态轻拳

```text
LightPunchMove
├─ command：SINGLE light_attack
├─ entry_path：action/basic_attack/light_punch
├─ states：light_punch 定义
│           └─ light_punch 判定定义
└─ transitions：结束后的必要转换
```

一个状态内部用动作时序区分起手、有效、恢复。两个攻击矩形共用一次招式实例和同一攻击段；攻击被中断时统一关闭，不依赖末尾关键帧。

### 14.3 一个缓冲后定点接续的 composite_attack

    A：action/basic_attack/light_punch
    装备路线：string_lmh
    ├─ 后续状态 B、C，各自内部三阶段与判定绑定
    ├─ 固定连接 A --M--> B --H--> C
    ├─ 接收规则：可在 A 期间接收 M、H，明确路线时钟／截止／间隔
    └─ 执行规则：A 的规定帧提交 A→B，B 的规定帧提交 B→C

例：A 帧 2／3 分别按 M／H，只录入 pending。A 到帧 12 转 B，B 到局部帧 10 转 C；示例帧数是本项目演示，不是 MK 实测。输入快不让 A／B 提前退出，窗口关闭不清已接受记录，受击或特殊技取消则清剩余串。

A→B 跨组统一验证后 external 执行；B→C 同组可以原生转换，但都必须等业务规定的提交点。IMMEDIATE 不提供缓冲调度，当前资源字段与运行接线仍未实现。

### 14.4 一个可强化的特殊技

    FireballMove
    ├─ 主 command：2→3→6→L 固定
    ├─ entry_path：action/special_attack/fireball
    ├─ states：FireballState 专用叶子及完整判定依赖
    └─ execution_plan【拟新增】
       ├─ 起手／施放／恢复
       └─ 强化窗口：固定派生输入、条件及资源政策待定

不接受 M／H 自动选择帧数伤害。起手强化可选择尚未生成的强化效果；恢复强化可追加段，不追溯改变过去命中。需要改变已发投射物时必须显式设计实体转换，不能默认重发。

### 14.5 一个纯方向特殊技

    VerticalSpecial
    ├─ 主 command：2→8
    ├─ 终结：进入符合规则的上方向事件
    ├─ 来源：方向 token【待实现】，不伪造攻击键
    └─ 专用叶子：三阶段、判定、与跳跃竞争的准入规则

Fray matcher 本身可以读取此方向序列，不限末项为攻击键；当前缺的是方向匹配后进入候选的来源／一次消费接线。此例仅用于特殊技，不是组合技指令；持续按上不重复触发，失效／回中／新输入政策需明确。

## 15. 实施建议与暂不增加的复杂度

### 15.1 先做必要扩展

1. 实现 BuildPlan 与统一依赖收集，不改变当前输入消费规则。
2. 给 StateDefinition 增加判定引用，实现每角色判定装配与状态绑定。
3. 用四个 neutral 状态验证整个资源关系和共享边界。
4. 接入一个基础攻击与受击闭环，明确逻辑帧、命中与取消，不预建通用多招执行器。
5. 增加方向快照基础技；实现接收窗口、路线游标和有界 pending，先验证 A 早按 M 到固定帧转 B，再验证 A 期间 M、H 拨入与 B 到期转 C、分支及中断清理。
6. 保留 Fray matcher，补下上特殊技的方向候选来源及与跳跃竞争；确定强化输入／资源后实现一招强化。
7. 具体内容需要时再处理严格前缀、不同指令同执行、同输入上下文；本期不做战斗热换装。

### 15.2 暂不新增

- 玩家自定义招式逻辑指令编辑器。
- 独立的指令装备栏和判定装备栏。
- 第二套全局 CommandLibrary、万能组合技图、完整串匹配后重播起手、已消费起手恢复或泛化评分；但本次局部路线缓冲／输入进度是实现拨入体验的必要扩展，不再排除预输入。
- 按 Hurt／Attack／Push 拆分的多管理器。
- 每次行为切换都实例化判定节点。
- 为每个矩形、每个掩码阶段都创建行为状态。
- 大而全的运行时配置预检、静默兜底和隐式资源覆盖。
- 在尚无需求时实现多套动作计时与适配；组合技各段仍使用相同物理逻辑时钟，窗口不是新时钟。

## 16. 核对与验收问题

资源关系和执行链落地后，至少验证：

- 删除一个已装备招式，是否同时移除其专属识别、状态依赖和判定实例，而不误删其他招式共享依赖？第一阶段可通过生成不同 Loadout 的角色验证，不要求战斗内热卸载。
- 每招／每段独立完整路径是否有独立状态实例；相同协议的脚本是否安全复用且不共享运行态？后续判定接入时是否有唯一的完整姿态依赖？
- 同路径冲突是否被内容明确避免，没有靠装备顺序隐式覆盖？
- 多角色使用同一资源时，节点、可变形状、候选和命中记录是否独立？
- 特殊指令失败或过期后，是否仍遵守不回退普通攻击的既有规则？
- 共享输入来源是否只消费一次，资源是否只支付一次？
- 同一段的三阶段变化是否保留命中身份，转入下一攻击状态是否初始化其新身份，旧段是否不重复结算？
- 攻击／受击矩形组合是否仍对同一目标每段只结算一次？
- 强制中断后，旧动作、旧框和旧延迟回调是否彻底失效？
- 判定场景的动态名称与路径变化，是否不会破坏动作绑定？
- 三类类型与输入形状是否解耦，特殊技没有轻中重隐式版本，方向结尾不被错误要求补攻击键？
- A 是否即时打出，而早按 M／H 只入队，分别到 A／B 的规定帧才转换，输入速度不改变实际动作时点？
- 接收窗口与执行点是否分离，A 期间 H 可为未来 B→C 记录，未进入 B 时不使用虚构 B 局部帧，窗口关闭不丢已接受后缀？
- 接收认领与实际执行消费是否分开，正常接段保留队列、被打断清全部，原事件不会回灌普通攻击？
- 强化是否只扣费一次、只生成一次，不追改过去命中；输入与资源未定的内容是否仍标注待定？
- 下→上能否携带方向来源生成候选，并在离散执行前与跳跃仲裁，而非同次输入双发？
