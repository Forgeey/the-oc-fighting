# 招式装配与判定时序疑难解答

> **2026-10-25 组合技修订：**普通单段仍在一个状态内处理三阶段，composite_attack 则每段一个状态。下一段输入可以先缓冲，必须到当前段的规定衔接帧才实际转换，不能收到键就切状态。快速输入 M、H 可以早于 B 开始。最新目标与 MK 资料核验见 [招式设计计划](../计划/招式设计计划.md)；历史问答不表示取消系统已实现。

## 1. 本次确定了什么？

- 每个特殊技由作者固定一套方向序列和一个指定逻辑攻击按钮；玩家选择装备，不修改逻辑指令。
- 一个招式 ID 对应一套明确的帧数、伤害等配置，不根据轻／中／重按钮自动派生三个强度版本。
- `light_attack`、`medium_attack`、`heavy_attack` 仍然是现有按钮名，不自动表示特殊技强度。
- 默认每招保留自己的行为叶子与完整状态路径；执行脚本可按相同协议复用，不以“每类一个通用 Attack 叶子”作为装配前提。
- 普通招式的起手／有效／恢复在该招式叶子内部推进，不机械拆成三个 Fray 状态。
- 招式逻辑帧是阶段、攻击窗口、取消窗口和完成条件的权威；`AnimatedSprite2D` 负责显示。
- 当前 demo 不使用 `AnimationPlayer` 节点或动画轨控制判定；插件的通用适配代码不因此删除。
- 目标是在角色构建时按 Loadout 装配所需判定场景，不在每次攻击时创建，也不在角色场景里预建全部可装备招式；当前 Demo 尚未实现。

这套选择适合本项目控制内容组合复杂度、明确每招身份的目标，不是对其他格斗游戏输入体系的普遍优劣判断。

## 2. 不做轻中重版本，就不需要复用执行脚本吗？

**两者没有必然关系。** 输入／数值版本属于游戏设计，脚本复用属于实现组织。

即使火球只能用 `236 + light_attack`，另一招也只有自己固定的指令，只要两者执行协议相同，技术上仍可复用脚本；复用不会自动增加版本或让玩家面对隐藏的随机帧数。反过来，给每招写一个脚本，也不会自动解决重复代码与维护成本。

**行为叶子与执行脚本可以分开复用。**推荐每招保留独立完整状态路径和独立状态实例；若多招遵守相同执行协议（例如进入→按逻辑帧起手→开启/关闭有效判定→恢复→完成），这些路径可以引用同一个脚本类，由 Builder 分别 `.new()`，而帧数、伤害等差异来自各自只读动作配置。这样既保留招式身份，也避免只因数值不同复制状态脚本。

抓取同步、投射物生命周期、蓄力等待等协议差异明显的动作，仍可采用专用脚本或专用机制组件。当前脚本资源仍按专用实现配置；角色构建修改计划将调整为允许相同协议复用脚本类，这尚未实现。公共移动、计时和清理工具也可继续复用。

固定一套基础数值也不禁止将来显式设计多段、蓄力、命中／防御结果差异；这些若被采用，必须是可描述、可验证的规则，而不是由其他攻击按钮暗中选强度。本文不新增这些机制。

## 2.1 执行脚本、动作配置与角色外观如何解耦？

推荐拆开三种职责，而不是把每个动作烘焙成一个角色专属整体资源：

- **状态脚本**描述执行协议：如何推进逻辑帧、阶段、取消与退出清理。相同协议可供不同招式路径复用。
- **招式配置**描述本招内容：身份、显示名、固定输入、状态依赖、阶段帧数和数值。**状态定义**统一保存动画语义 animation_key 与预留判定引用；基本状态和招式状态使用同一动画配置链路，Move 不重复维护动画键。配置只读，不保存本次运行进度。
- **角色表现映射**将来把语义动画标识解析为该角色/外观实际使用的 SpriteFrames 或其它显示资源；当前 Fighter._resolve_animation_key() 只原样返回，尚未实现完整映射。具体皮肤素材不应反向决定伤害、攻击帧或判定尺寸。

动画表现与判定需要同步，但不应各自拥有战斗时钟：招式逻辑帧驱动阶段与判定启停，也映射显示帧。外观变化默认只改变画面；若以后身材或武器确实改变战斗规则，应显式选择兼容的战斗配置，不从贴图透明像素或视觉缩放自动推导碰撞框。

“动画＋判定”可以在一个动作配置/姿态依赖中一起装配，但建议保存动画**标识**而不是角色专属图片。推挤、受击、攻击框在语义上分别配置，运行时仍按 Fray 当前单一 `FrayHitStateManager2D` 选择一套完整姿态；攻击姿态应包含自己需要的 Hurt/Push 与按需启用的 Attack，不依赖并行常驻姿态。当前实现计划暂不接入判定场景，只为招式或状态定义保留扩展位置。
## 3. 起手、有效、恢复最好放在一个状态吗？

普通拳脚、简单挥击、简单施放：**是。**

```text
action/basic_attack/punch → PunchState
    内部阶段：startup → active → recovery → done

action/special_attack/fireball → FireballState
    内部阶段：startup → release/active → recovery → done
```

进入状态时重置本次计时、动作代次、命中记录和生成标记；在固定物理节拍推进；退出时统一关闭攻击框和取消窗口、释放临时约束。

例如一招起手 5 帧、有效 3 帧、恢复 12 帧，以动作帧索引 `0..19` 表示：

| 区间 | 阶段 | 判定 |
| --- | --- | --- |
| `[0, 5)` | startup | 保留该姿态 Hurt／Push，不开 Attack |
| `[5, 8)` | active | 启用该攻击段的 Attack |
| `[8, 20)` | recovery | 关闭 Attack，保留所需 Hurt／Push |
| 完成第 19 帧的模拟后 | done | 允许正常完成转换 |

制作时明确“先应用当前帧、再完成该帧、再推进”的边界；不能在首次采样前自增而跳过第 0 帧。物理检测更新、命中结算和转换顺序需另行验证，不能仅凭计数器就宣称恰好采样三次。

### 什么时候才拆分？

当抓取目标、搬运目标、释放目标，或开始蓄力、等待松键、释放等阶段具有独立入口、控制协议、约束和复杂分支时，可以另设内部控制流程，必要时增加专用叶子。仅仅三段时长、三个掩码或三段图片不是拆状态的理由。

当前 `FighterStateDefinition` 只支持可无参构造的 `FrayState` 叶子，不能直接把 `FrayCompoundState` 脚本填进去；复杂招式的多叶子方案必须符合构建器现有分组能力或另行扩展。

### Fray 的完成条件别漏了

`FrayState._is_done_processing_impl()` 默认返回 `true`。招式叶子应覆盖它，仅在恢复结束后允许正常完成；否则 `AT_END` 不会替你等待三阶段。父组完成也不自动递归委托给最深叶子，需明确组级退出条件。

## 4. 为什么不让 AnimationPlayer 负责开关判定框？

Godot 3 参考场景 `addons/fray_demo/demos/example/2d/player/player.tscn` 确实有 `HitStates/HitState2D:active_hitboxes` 属性轨，角色脚本也使用动画结束信号。这证明该路径可用，不表示动态装配必须沿用。

本项目已排除按固定节点路径维护判定轨、由动画编辑器决定战斗窗口的方案，因此不需要这个节点：

```text
专用招式叶子读取只读数值
    ↓ 逻辑帧推进
阶段／取消窗口／判定掩码／完成条件
    ↓
AnimatedSprite2D 显示身体动画
```

判定写入只归执行逻辑，不由 `frame_changed`、`animation_finished` 或图片数量决定。不能保留一套动画轨再让脚本同时写掩码，也不需要“动画轨辅助开框”的双写方案。

基础待机和行走继续使用现有 `sprite.play()` 即可。后续攻击若要精确同步图像与逻辑帧，可以由同一动作进度选择 SpriteFrames 中的显示帧，暂停自主播放；这不需要 AnimationPlayer，也不表示本次已实现图像帧映射。

Hitstop 必须明确暂停动作逻辑、图像和结算的哪些部分，以及输入如何缓冲；删除 AnimationPlayer 不会自动实现暂停、确定性或回滚。

## 5. 多个招式什么时候能复用一个执行脚本？

如果它们都遵守同一协议，例如“进入→定时起手→开框→关框→恢复→完成”，差异只是配置，可以复用。抓取控制、投射物实体生命周期、蓄力等待等协议差异大时，应该专用实现或拆出机制组件。

需要区分：

1. 复用脚本类：同一脚本可 `.new()` 出多个运行对象。
2. 共享状态定义：同一完整路径在一个角色里只装配一次。
3. 共用同一个执行叶子：多招进入同一路径，必须有完整招式上下文和可靠重启协议。
4. 多个角色引用同一 `.tres`：配置只读，角色、计时和命中记录各自独立。

本项目目标不采用第 3 种通用派发方案：默认每招独立路径和状态实例，但相同执行协议可复用脚本类。不能把脚本文件、状态对象与招式资源当成同一个东西。当前代码/资源接线尚待[招式参与角色构建方案](../方案/招式参与角色构建方案.md)落地。

## 6. 为什么基础状态不与招式合并？

idle／行走／下蹲表达持续意图；受击／倒地来自战斗结果；招式是装备单元和离散执行请求。它们都可以参与同一行为树，但不必都包装成玩家输入招式。

```text
Loadout.selected_state_paths → neutral/idle、fwalk、bwalk、crouch
Loadout.selected_move_ids    → MoveLibrary 中的数字招式 ID（当前轻攻击为 "01010001"；move_name 仅用于显示）
```

“每招一个叶子”不等于为每个来源姿态复制一个招式。若同一招能从 idle 与 fwalk 发动，使用 `allowed_from_paths` 和条件即可，不需要 `IdleFireball`、`WalkFireball`。只有地空等执行规则真的不同，才按需求定义差异。

把所有基础状态都包装为 Move 在技术上并非做不到，但会额外引入无指令 Move、常驻能力与可卸装备区别、连续输入消费、强制受击入口等约定；把招式逻辑塞进 Idle 则使它承担数值、判定和清理等无关职责。本项目保留职责分离，在装配层统一收集依赖。

## 7. FrayHitState2D 是角色行为状态吗？

不是：

- `FrayState` 继承 `Resource`，描述角色行为生命周期。
- `FrayHitState2D` 继承 `Node2D`，管理一套完整姿态的直接子判定框。
- `FrayHitbox2D` 是 `Area2D`，Hurt／Attack／Push 都可以用属性区分。

一个角色一个 `FrayHitStateManager2D`，同一时间选择一套完整姿态。攻击姿态必须包含自己需要的 Hurt／Push，不能依赖另一个常驻 HitState 与它同时激活。清理攻击段通常只清掉 Attack 位，不要把当前完整掩码误写成 0 而让角色消失于受击／推挤检测。

`active_hitboxes` 的 bit 按直接子 `FrayHitbox2D` 的实际顺序计算。`activate()` 只标记／显示姿态，不会替你启用全部框；隐藏节点也不等于停用检测。

## 8. 添加 HitState，最好是资源引用场景吗？

是，**引用 PackedScene，而非已经实例化的 Node**。为避免依赖重复，采用现有动态装配方案的单向关系：

```text
FighterMoveDefinition.states
    → FighterStateDefinition
        → FighterHitStateDefinition【拟新增】
            → hit_state_scene: PackedScene
                根为 FrayHitState2D
                直接子为 FrayHitbox2D
                框下为 CollisionShape2D
```

基础状态也从 StateDefinition 引用判定定义。几何在 `.tscn` 编辑，默认掩码在判定定义保存；同一个数值只保留一个权威来源。不要另外又在 Move 上维护一份相同场景依赖或把节点反向写回共享资源。

每名角色按最终 Loadout 实例化自己的判定节点，角色内同一判定定义可以去重；运行时改变形状时还需处理 Shape2D 共享问题。当前代码尚无上述判定定义字段和绑定流程，本次仅统一设计，不虚称装配已经实现。

## 9. 动态 add_child 后 Manager 会自动接线吗？

当前插件不能这样假定。Manager 在运行期 `_ready()` 遍历初始直接子 HitState，设置 source 并连接掩码变化及接触信号；编辑器的 ChildChangeDetector 不等于运行时完整注册 API。

优先在 Fighter `_enter_tree()` 等不依赖子节点 ready 的阶段，根据 Loadout 解析依赖、创建禁用判定的子节点，让 Manager 在自己的 `_ready()` 看到完整集合；Fighter 的 `_ready()` 再完成状态绑定和真实初始姿态进入。详细顺序见动态装配方案。

若在 Manager ready 之后新增，必须明确注册 source、HitState 与 Manager 信号、当前姿态以及注销清理，不能只 `add_child()`。本阶段不增加战斗中换装。

## 11. 真人快打式组合技：窗口内输入是否立即取消？

不应采用上一版的“收到合法按键就立刻换招”默认规则。当前计划明确分为输入接收窗口、有限待执行接续、规定衔接帧三部分。比如 A 期间早按 M、H，先认领并记录 A→B、B→C；A 到其规定帧才进入 B，B 到自己的规定帧才进入 C。

每段仍然有完整起手／有效／恢复，早按不缩短有效帧、不加速动画。普通 A→B 保留路线后缀；受击或取消到特殊技清掉未执行部分。IMMEDIATE 只在到期真正提交时跳过剩余恢复，不负责采样时自动执行或替业务建立缓冲。

MK 官方补丁能证实存在组合技缓冲与可调整的取消时点，但不能证明所有作品全部招式共享同一窗口，更不能把 MK11 恢复末 4 帧的一般输入缓冲当串内拨入时限。本项目队列字段、固定衔接帧和示例数字是设计选择，来源和限制见计划第 12 节。本次只更新文档，不增加实现。
