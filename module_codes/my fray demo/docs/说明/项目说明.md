# My Fray Demo：FighterMovement 与分层状态机使用指南

> 输入与固定招式接入以 [固定招式输入接入说明](固定招式输入接入说明.md) 为准。

> 当前装配入口见 [状态机资源配置说明](状态机资源配置说明.md)：角色通过 `FighterLoadout` 选择状态库中的完整路径，由构建器自动筛选转换。后续招式库与选招接入计划见[招式参与角色构建方案](../方案/招式参与角色构建方案.md)。脚本已按 `scripts/fighter`、`scripts/states`、`scripts/transitions`、`scripts/state_machine` 分类；下文分层和移动代码主要用于说明设计，不代表当前资源装配代码。

## 游戏装配原则

游戏计划只有一个角色，角色状态、招式、转换、动画等所有资源通过自定义装备的方式添加。不在对战中动态添加，在战斗前可以动态添加。

这里的“一个角色”指同一套角色模板；测试或对战可以生成多个互相独立的实例。状态、招式和判定节点根据战前最终 Loadout 一次构建；战斗中的状态/姿态切换只使用已装配内容，不热添加资源。当前外观动画映射仍只预留入口，不表示已完整实现所有资源的装备界面。

## 1. 本项目采用的职责划分

本文针对当前项目内的 Fray 源码，而不是其他版本插件的假定行为。编写时已核对仓库根目录 `addons/fray` 与本项目插件副本的核心状态机文件，内容一致。

采用以下设计：

> 状态决定当前允许做什么，并调用运动接口；FighterMovement 计算速度、应用重力并执行实际碰撞移动。

| 部分 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `FighterMoveEnv` | 速度、加速度、重力、持续帧数、场地边界等配置 | 当前状态、实时速度、受击事件 |
| `FighterMovement` | 操作角色速度、重力、摩擦、冲量、边界与碰撞移动 | 判断招式取消是否合法、选择下一个战斗状态 |
| 叶子状态 | 当前行为的输入解释、计时、动画/判定协调、调用运动分支 | 重复实现重力与碰撞算法 |
| 复合状态 | 包含子状态、组内转换与公共生命周期规则 | 再执行一遍子状态已经执行的运动 |
| `FighterSMBuilder` | 创建状态对象、连接转换、注册条件、返回状态图 | 每帧推动角色运动 |
| `Fighter` | 持有节点和模块、准备依赖、初始化状态机 | 与当前状态同时重复调用运动更新 |

`FighterMovement` 可以保存冲刺剩余时间、击退速度等运动执行数据，但不要再维护一套独立的 `idle/walk/attack/hurt` 行为状态机。否则容易出现“Fray 已进入受击，FighterMovement 仍认为正在自由行走”的冲突。

源码继承与状态层级是两回事：

- `IdleState extends FighterState`：复用 GDScript 代码。
- `neutral/grounded/idle`：运行时的状态树路径。
- 一个 `FighterState` 基类不会仅凭继承关系自动成为 Fray 的父状态。
- 容纳子状态的对象需要是 `FrayCompoundState`；当前 `FighterState extends FrayState` 适合作为叶子状态基类。

## 2. 应该把哪些状态放在同一组？

### 2.1 判断标准：相同的控制规则与生命周期

适合放进同一复合状态的子状态，通常有以下共同点：

1. 进入这一组后，角色遵循相似的输入权限与行为限制。
2. 组内经常互相转换。
3. 有相同的对外中断规则，例如这组动作都能被有效受击中断。
4. 离开整个分组时，有需要统一清理的资源或效果。

不要仅因为“都要受到重力”“都播放动画”就归为一组。这些属于可复用能力，放在 FighterMovement、动画接口或基类里即可。

**本项目推荐顶层按行为控制权划分：**

- `neutral`：自由操作，包括站立、行走、蹲下、普通跳跃等。
- `action`：正在执行主动动作，包括攻击和具有独立规则的冲刺。
- `reaction`：受战斗结果约束，包括受击硬直、防御硬直、击飞、倒地和起身。
- `disabled`：回合结束等不可正常操作阶段；确有需求时再加入。

如果当前主动动作只有攻击，`action` 也可以直接命名为 `attack`。保留 `action/attack` 这一层是为了以后容纳冲刺、投技等不同动作，不是 Fray 的强制要求。

### 2.2 推荐的扩展状态树

下图是设计目标，不是当前已经实现的功能，也不要求第一天全部创建。

```text
fighter_root
├─ neutral                         自由操作
│  ├─ grounded                     地面自由操作
│  │  ├─ idle
│  │  ├─ walk                      前进/后退可以先共用一个状态
│  │  └─ crouch
│  └─ airborne                     空中自由操作
│     ├─ rise
│     └─ fall
├─ action                          主动动作
│  ├─ dash                         固定时长、特殊取消规则的冲刺
│  │  ├─ forward_dash
│  │  └─ backward_dash
│  └─ attack
│     ├─ ground_attack             具体招式由攻击数据区分
│     └─ air_attack
├─ reaction                        被动/受限行为
│  ├─ hitstun                      地面受击硬直
│  ├─ blockstun                    防御成功后的硬直
│  ├─ launched                     击飞/空中受击
│  ├─ knockdown                    倒地
│  └─ getup                        起身
└─ disabled                        可选
   └─ ko
```

这棵树表示一条活动分支。例如：

```text
fighter_root → action → attack → air_attack
```

这时不会同时激活 `neutral/airborne/fall`。**空中攻击仍需重力和碰撞，由 `air_attack` 调用 FighterMovement 的空中运动接口完成，而不是依赖自由移动分支继续运行。**

### 2.3 为什么不把攻击和受击都放在“基础状态”下面？

“基础状态”容易混淆两种意思：

- 如果指的是共享依赖的 `FighterState` 脚本基类，攻击与受击当然可以继承它。
- 如果指的是“自由移动”这个运行时分组，攻击与受击就不应作为其子状态。它们的输入权限、取消规则和退出条件通常不同。

把 `neutral`、`action`、`reaction` 放在根的同一层，能够清晰表达：角色从自由操作进入攻击，攻击被命中后进入受击，受击结束后再恢复自由操作。

### 2.4 另一种可行方案：先按地面/空中分组

也可以设计为 `grounded/{idle, walk, attack, hurt}` 与 `airborne/{jump, attack, hurt}`。

这适合“所有行为的规则都首先由地面/空中决定”的设计，但容易把攻击取消、受击中断等规则分别维护两套。

本项目已经让 FighterMovement 复用地面/空中物理，因此建议优先采用上面的“控制权分组”。地面/空中是运动事实，不必总是成为最顶层状态。

## 3. 几个容易分错组的行为

| 行为 | 建议位置 | 原因或例外 |
| --- | --- | --- |
| 前进、后退 | `neutral/grounded/walk` | 先用输入轴与朝向选择不同参数；动画、取消规则差异明显时再拆 |
| 普通蹲下 | `neutral/grounded/crouch` | 仍属于自由操作 |
| 持续按住后方向的防御姿态 | 可由 neutral 中的输入/姿态规则处理 | 不等于已经进入防御硬直；有专门防御动作时可独立建状态 |
| 防御成功后的硬直 | `reaction/blockstun` | 暂时受限，不能按普通行走处理 |
| 固定帧数的前冲/后撤 | `action/dash` | 有起手、持续、恢复和取消规则；若只是可随时停止的跑步，可放 neutral |
| 起跳准备 | 先作为独立 `jump_start` 叶子，归 neutral 或 action 取决于取消规则 | 不必为了几帧准备强行创建复合状态 |
| 普通跳跃上升/下落 | `neutral/airborne` | 可先共用 `jump`，需要不同行为再拆 rise/fall |
| 落地恢复 | 可用 `action/landing` 等受限叶子 | 有硬直时不要直接当可自由操作的 idle；无硬直则直接回 grounded |
| 空中攻击 | `action/attack/air_attack` | 攻击规则由状态负责，空中物理由 FighterMovement 负责 |
| 击飞、倒地、起身 | `reaction` | 同属受限行为，但各自计时、重力、碰撞和可受击规则不同 |
| 霸体、无敌、取消窗口 | 动作属性/阶段数据或条件 | 通常可以与攻击并存，不宜全部变成互斥顶层状态 |
| Hitstop（命中停顿） | 独立的暂停/时间控制机制 | 它可以作用于任意攻击或受击阶段，不宜为了停顿丢失原活动状态 |

Hitstop 若使用状态机 `active = false` 暂停，恢复计时必须由没有一起停掉的外部逻辑推进，并统一处理动画与输入缓冲策略。不能让被暂停状态自己负责解除暂停。

## 4. FighterMovement 的调用约定：每帧只移动一次

### 4.1 由当前叶子状态选择运动分支

建议制定统一规则：

> 每个正常模拟的物理帧，只有当前叶子状态提交一次运动；复合父状态和 Fighter 不再次提交。

例如：

```text
idle         → step_grounded(0, delta)
walk         → step_grounded(axis, delta)
rise/fall    → step_airborne(axis, delta)
forward_dash → step_fdash(delta)
backward_dash→ step_bdash(delta)
hitstun      → step_restricted(delta)
```

以上接口来自当前 `scripts/fighter/fighter_movement.gd` 的骨架，但大部分尚未实现。每个 `step_xxx()` 应约定完成“速度更新 → 必要约束 → 一次碰撞移动 → 更新碰撞后的事实”，而不是有的函数仅改速度，有的函数却偷偷移动两次。

攻击运动接口尚需设计：地面攻击可以使用无自由输入的受限运动分支，空中攻击则使用保留空中惯性/重力的分支。若有突进招式，单独传入动作位移规则，不要默认所有攻击都立刻把水平速度清零。

`start_jump()`、`start_fdash()` 等启动接口只设置初速度/计时等，不立即执行额外的碰撞移动。真正的位置更新仍由该帧的 `step_xxx()` 统一完成。

### 4.2 为什么父状态不能也调用移动？

当前 Fray 的 `FrayCompoundState.physics_process()` 是：

1. 更新当前子状态，递归直到叶子。
2. 再调用本复合状态自己的 `_physics_process_impl()`。

因此 `root → neutral → grounded → walk` 这条分支上的回调都可能运行，而且是子状态先于父状态。

如果 Walk 调用 `step_grounded()`，Grounded 再应用重力，Root 再调用 `move_and_slide()`，就会发生重复积分或重复移动。

父状态可以做不重复运动的公共维护，但不要假定它会在子状态之前准备本帧数据。需要在移动前采样的数据，应通过明确的输入/模拟调度准备好。

### 4.3 不要误把“禁止输入”当成“禁止物理”

受击、攻击和落地恢复期间，可能禁止自主行走，但角色仍需要：

- 受重力影响；
- 沿击退速度运动；
- 与地面和场地碰撞；
- 更新落地事实。

所以这些状态仍需要调用适合的 FighterMovement 分支。冻结整个模拟只用于真正的暂停或 Hitstop 等机制。

## 5. 转换应该放在哪一层？

### 5.1 同组转换放在最近的共同父层

| 转换 | 建议归属 |
| --- | --- |
| idle ↔ walk、walk ↔ crouch | `grounded` |
| rise → fall | `airborne` |
| grounded ↔ airborne | `neutral` |
| 普通攻击 → 可取消的后续攻击 | `attack`，配合招式阶段/取消条件 |
| hitstun → launched、knockdown → getup | `reaction` |
| neutral → action、action → reaction、reaction → neutral | 根状态 |
| 任意允许死亡的分组 → disabled | 根层战斗规则 |

跨分组的目标往往不只是一个固定状态。例如攻击结束后，可能回到空中下落，也可能回到地面行走。

建议由根层的转换条件或一个统一的战斗事件处理入口决定恢复目标，不要让每个攻击脚本各自硬编码“结束后一律 Idle”。

### 5.2 推荐的行为流程

```text
neutral/grounded/walk
	├─ 满足攻击条件 → action/attack/ground_attack
	└─ 收到有效命中 → reaction/hitstun

action/attack/ground_attack
	├─ 满足取消条件 → 下一招
	├─ 招式结束且在地面 → neutral/grounded/idle 或 walk
	├─ 招式结束且在空中 → neutral/airborne/fall（或按速度选择 rise）
	└─ 收到允许打断的有效命中 → reaction/hitstun 或 launched

reaction/launched
	└─ 着地且需要倒地 → reaction/knockdown
		└─ 倒地计时结束 → reaction/getup
			└─ 起身恢复结束 → neutral/grounded/idle
```

“有效命中”必须已经经过无敌、霸体、格挡等战斗规则判定。不是任何碰撞信号都无条件进入受击。

### 5.3 强制中断与普通转换分开处理

普通行走、跳跃、招式取消：使用配置好的转换和条件。

已经由战斗逻辑裁定的强制中断：可以由统一入口调用：

```gdscript
# 路径和 args 字段是本项目拟定的约定；目标状态必须已经存在。
state_machine.goto("reaction/hitstun", {
	"hit_data": resolved_hit_data,
})
```

当前 `goto()` 会直接按路径退出/进入状态，不检查普通转换的 `prereqs`、完成条件或取消窗口。因此不要把普通玩家攻击输入全部实现成 `goto()`，否则会绕过战斗规则。

处理命中事件时，先完成当前模拟步骤或将事件排队到约定的结算点，避免在一个状态的物理回调尚未结束时切换状态，旧回调随后又继续提交运动。

## 6. 当前 Fray 源码的关键约束

这些约束直接影响分层方案，不能仅凭其他状态机框架的经验推断。

### 6.1 普通转换优先检查活动后代，再回退父层

修复后的 `FrayCompoundState.advance()` 先尝试活动子组的普通转换；若没有命中，才检查本层规则。一次普通推进只选择一条规则。

因此子层“攻击派生/取消”和根层“离开 action”同时满足时，后代规则优先。受击、死亡等强制中断应由明确的战斗事件调度或互斥条件决定，不能再依赖旧版的父层先检查顺序。

显式 `travel()` 保留为 Fray 扩展，仍在其所属层优先处理；不要把它等同于普通规则的冲突选择。

### 6.2 `AT_END` 不会自动等待最深叶子结束

当前默认转换模式为 `SwitchMode.AT_END`。

- 普通 `FrayState._is_done_processing_impl()` 默认返回 `true`。
- `FrayCompoundState._is_done_processing_impl()` 检查本组是否未设置 `end_state`，或当前直接子状态是否等于 `end_state`。
- 它没有默认递归检查最深层攻击的剩余帧数。

所以，不能只给攻击叶子实现“未完成”，就认为根层离开 `action` 的 `AT_END` 转换会自动等待该攻击。

可选处理：

1. 在离开 action 的转换上增加明确的 `action_finished` 条件。
2. 在适合的组内设计一个真实可达的结束状态，并用 `end_at()` 表达组完成；多层结构仍需逐层考虑完成语义。
3. 自定义复合状态的完成判定，明确是否委托给当前子状态。

项目起步阶段建议采用第一种，最直观。受击/死亡这种允许中断当前动作的转换，则使用经过验证的强制切换，或带完整前置条件的 `SwitchMode.IMMEDIATE`。

### 6.3 `priority` 不能当作普通自动转换的排序保证

当前 `get_next_state()` 依次检查 `get_next_transitions()` 返回的转换；该函数先收集普通转换，再追加全局转换，并没有按 `priority` 排序。

`priority` 在当前源码中被用于路径图相关计算。不要以为给死亡、受击设置更小的数值，就一定会优先于所有普通自动转换。

关键冲突应通过互斥条件、明确的注册顺序或统一事件决策处理。尤其不能假设“全局受击转换”天然优先于同层普通转换。

### 6.4 Global transitions 是本复合状态内的标签规则

每个 `FrayCompoundState` 自己保存状态标签、全局转换和规则。它不是全项目的任意叶子跳转广播。

例如根层的 `action` 可以打上 `can_be_hit` 标签，让根层统一处理 action 分组的受击出口。但标签不会自动代表所有内部叶子都可受击；当前招式无敌/霸体仍需额外条件判断。

想在 attack 内使用普通技取消到特殊技的标签规则，就在 attack 这一层配置对应规则。

### 6.5 真实入口直接初始化，不再依赖兼容类

本项目已使用修复后的 Fray 插件，并移除业务层的入口兼容脚本和 bootstrap 占位状态。

```gdscript
state_machine.initialize(context, root, loadout.entry_path)
```

- 所有状态先完成 `ready(context)`，再按完整目标路径从外向内执行进入回调。
- 显式指定叶子时，只进入这条路径，不提前启动中间组的其他默认分支。
- 目标停在复合状态时，由插件补全默认/持久入口，最终叶子的 `_enter_impl()` 执行一次。
- 不传第三个参数时，沿根的默认入口进入；本项目显式传入角色配置的 `entry_path`。
- 不再在初始化后额外调用一次 `goto()`，也不要手动补调用叶子的 `_enter_impl()`。
- `goto(当前叶子)` 是导航，不保证重新进入；普通规则的 external 自转移会退出并重新进入。
- 无效默认入口会在退出旧状态前被拒绝。空骨架组可以存在，但不能作为最终可进入目标。
- 进入/退出回调内不能同步递归调用 `goto()` 或 `travel()`；后续切换应留到下一次推进或明确的延迟调度。

插件修复对应文档见仓库级 [Fray 复合状态生命周期修复对比](../../addons/fray/Fray_复合状态生命周期修复对比.md)。该插件参考 SCXML 的部分层次状态语义，不是完整 SCXML 实现。

### 6.6 物理更新与转换推进不是同一开关

- `FrayStateMachine.active` 默认是 `false`，初始化不会自动把它改成 `true`。
- `advance_mode` 默认是 `IDLE`；本项目已使用 `MANUAL`，由 Fighter 在状态物理更新后统一推进。
- `MANUAL` 仅表示手动调用 `advance()`，不代表停止状态的物理回调。
- 当前显式顺序为 Fray 采样 → FighterInput 采样 → 状态物理更新 → Fighter 普通推进；新状态通常在下一次物理更新提交移动。插件 advancer 继续暂停，避免第二个推进来源。

场景中还有 `FrayBufferedInputAdvancer`。它可以额外调用状态机 `advance()`，不能假定与状态机自动推进合用后“每物理帧只切换一次”。第一阶段先不接入缓冲推进；后续接入时统一决定推进顺序、输入消费和一帧允许的转换次数。

## 7. 起步版本：只做 neutral/grounded/idle 与 walk

不建议现在就创建整棵扩展树。先验证分层和 FighterMovement 的闭环。

```text
fighter_root
└─ neutral
   └─ grounded
	  ├─ idle
	  └─ walk
```

### 7.1 组装示例

下面是 `scripts/state_machine/sm_builder.gd` 的替换思路，不是已经写入脚本的代码。示例中的 `move_left`、`move_right` 是拟定输入名称，使用前必须通过 Fray 输入注册流程配置；不能因为写了字符串就认为已有绑定。

```gdscript
class_name FighterSMBuilder
extends RefCounted

func build(controller: FrayController) -> FrayCompoundState:
	var grounded_builder = FrayCompoundState.builder()
	grounded_builder.add_state("idle", IdleState.new())
	grounded_builder.add_state("walk", WalkState.new())
	grounded_builder.register_conditions({
		"has_move_input": func() -> bool:
			return absf(controller.get_axis("move_left", "move_right")) > 0.1,
	})
	grounded_builder.transition("idle", "walk", {
		"auto_advance": true,
		"advance_conditions": ["has_move_input"],
	})
	grounded_builder.transition("walk", "idle", {
		"auto_advance": true,
		"advance_conditions": ["!has_move_input"],
	})
	grounded_builder.start_at("idle")

	var neutral_builder = FrayCompoundState.builder()
	neutral_builder.add_state("grounded", grounded_builder.build())
	neutral_builder.start_at("grounded")

	var root_builder = FrayCompoundState.builder()
	root_builder.add_state("neutral", neutral_builder.build())
	root_builder.start_at("neutral")
	return root_builder.build()
```

这里仅用持续输入决定 idle/walk，不依赖“按下事件必须刚好到达”的输入转换。以后从攻击恢复时，即使方向键一直按住，也能重新进入 walk。

每个角色应各自调用组装函数创建新的状态对象，不要把同一套有计时和依赖引用的状态实例挂给两个角色。

### 7.2 叶子状态示例

沿用当前 `FighterState._ready_impl(context)` 注入 `fighter/controller/movement`。

```gdscript
# idle_state.gd
class_name IdleState
extends FighterState

func _physics_process_impl(delta: float) -> void:
	movement.step_grounded(0.0, delta)
```

```gdscript
# walk.gd
class_name WalkState
extends FighterState

func _physics_process_impl(delta: float) -> void:
	var axis := controller.get_axis("move_left", "move_right")
	movement.step_grounded(axis, delta)
```

以后子类若覆盖 `_ready_impl(context)`，需要调用 `super(context)` 保留基础依赖注入。Context 字典在 Fray 初始化时会变成只读，但其中引用的 FighterMovement/Fighter 对象仍可以通过自己的接口修改。

### 7.3 Fighter 初始化与调度

当前实现位于 `scripts/fighter/fighter.gd`：构建器直接装配固定招式依赖（假设配置有效），FighterInput 配置本角色识别规则；initialize 注入 fighter_input 等 context 后，状态机设置 MANUAL。Fighter 在 priority 50 的物理回调内统一推进，候选先通过来源、前置条件和完成条件，接受后才消费。

完整脚本职责、资源配置方法和时序见 [固定招式输入接入说明](固定招式输入接入说明.md)，不要再复制旧 PHYSICS 自动推进的初始化片段。

## 8. 攻击状态要不要拆成起手、有效、恢复三个子状态？

> 2026-10-25 产品与实现约定：每个特殊技由作者固定方向序列＋指定攻击按钮，不自动提供轻／中／重数值版本。默认每招专用叶子、完整路径和脚本，普通三阶段在这个叶子内部推进。固定输入不意味着技术上不能复用脚本，公共基类与小工具仍可复用，不建设万能多招执行器。
>
> 当前 Demo 移除未使用的 AnimationPlayer 节点，现有动画仍由 AnimatedSprite2D.play() 播放。后续招式使用逻辑帧控制阶段、判定、取消与正常完成，不以动画轨／图片帧事件作为战斗时钟。精确攻击显示与 Hitstop 同步是待实现能力。完整说明见 [疑难解答](招式装配与判定时序疑难解答.md)。

**第一版不必。** 建议先使用一个攻击叶子状态，通过攻击数据与阶段计时描述：

```text
startup → active → recovery
```

在同一个叶子里，根据阶段：

- 开关攻击判定；
- 决定是否允许取消；
- 选择位移曲线/运动模式；
- 判断动作是否结束。

只有当三个阶段存在明显独立的进入/退出行为、复杂分支或大量可复用阶段逻辑时，才考虑将“一次攻击”做成复合状态。

每招默认一个专用脚本，不机械创建三份阶段脚本。伤害、起手／有效／恢复帧数、击退和取消规则仍以只读数据表达；状态保存运行进度，不写回资源。攻击叶子必须覆盖完成判定，恢复结束前不能沿用 FrayState 默认的 true。

同样，不要因为有前跳、后跳、垂直跳，就一定创建三棵完整子树；可以先由同一个跳跃状态接收不同方向/初速度参数。

## 9. 清理、恢复与重复受击

进入攻击时启动的判定、取消窗口和运动覆盖，必须有明确的清理归属。

- 招式专属资源由攻击叶子退出时清理。
- 整个 attack 分组共有的临时规则，可以由 attack 复合状态退出时清理。
- FighterMovement 的冲刺/动作位移取消接口由状态或战斗事件入口调用。
- 不要在退出攻击时无条件把所有速度清零；击退或空中惯性可能需要保留。
- 状态间的临时参数可用进入参数传递，长期共享对象通过 context 注入；避免让一个状态直接修改另一个状态的私有计时。

角色已经在 hitstun 时再次被命中，不能仅依赖 `goto("reaction/hitstun")` 重新触发进入逻辑。应显式设计“更新受击数据/重置硬直与冲量”的接口，或有经过验证的重入机制。

从 reaction/action 返回 neutral 时，根据碰撞后的接地结果和当前输入选择目标。不要默认恢复到离开前保存的历史状态；例如空中受击落地后恢复旧的空中攻击，通常不是想要的结果。

Fray 的复合状态 `is_persistent` 默认关闭。除非确实需要恢复组内历史状态，否则先保持默认，并显式选择恢复路径。

## 10. 调试与验收

### 10.1 查看完整活动路径

`state_machine.get_current_state_name()` 只返回根的当前直接子状态，例如 `neutral`，不是最深处的 `walk`。

可用：

```gdscript
var info := state_machine.get_root().get_active_states_info()
print(info["path"])
# 例如：neutral/grounded/walk
```

`FrayStateMachine.state_changed` 只直接连接根复合状态的 `transitioned`。子复合状态自己的转换不会自动全部上报为这个根节点信号。排查组内转换时，可以连接对应组的 `transitioned` 或比较完整活动路径。

### 10.2 按顺序验收

- [ ] 初始路径正确，FighterMovement 拿到本角色及环境资源。
- [ ] 按住方向能行走，松开能停止，前后速度符合朝向规则。
- [ ] 每个普通模拟物理帧只执行一次实际碰撞移动。
- [ ] 父状态没有重复施加重力、摩擦或位移。
- [ ] 空中攻击仍有重力，受击仍有击退与地面碰撞。
- [ ] 攻击未结束时不会被根层宽松条件提前切回 neutral。
- [ ] 允许打断时，命中能够中断攻击并关闭旧攻击判定。
- [ ] 无敌/霸体等例外不会错误触发受击转换。
- [ ] 同帧攻击结束、取消输入、命中发生时，决策结果符合预定规则。
- [ ] 连续受击会更新硬直和冲量，而不是因为已在同名状态而失效。
- [ ] 每个关键状态进入/退出的实际调用次数经过日志验证。
- [ ] 两个角色的状态对象、计时、控制器和 FighterMovement 不互相污染。

## 11. 当前项目的实施顺序

截至本指南编写时，`Fighter` 已继承 `CharacterBody2D`，场景已经绑定环境资源；`FighterMovement.init_movement(move_env, fighter)` 已保存成员引用。无需重新采用旧的单参数初始化方案。

下一步建议：

1. 完成 `step_grounded()`、基础重力和唯一的实际移动提交入口。
2. 完成 Idle/Walk，按第 7 节建立最小分层闭环。
3. 加入自由跳跃，验证地面与空中切换。
4. 加入一个攻击叶子和一个受击叶子，验证跨组中断与退出清理。
5. 再加入冲刺、空中攻击、防御硬直、倒地和起身。
6. 最后逐步完善输入缓冲、连招取消、标签规则和复杂动作阶段。

**最终原则：按行为规则分组，用 FighterMovement 复用物理；不要为了复用重力而扭曲状态树，也不要为了展示分层功能而提前建立大量空分组。**
